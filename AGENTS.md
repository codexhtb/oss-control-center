# OSS Control Center — правила разработки

## Источник решений

- Читайте `docs/architecture/README.md` перед изменением домена, workflow, API или схемы данных. Утверждённые решения Phase 0 важнее прежних предположений в старых текстах.
- OSS Control Center — самостоятельная система заявок. PostgreSQL — единственный source of truth для обращений, комментариев, решений, истории, аудита и диагностических snapshots.
- ServiceDesk Plus относится только к AS-IS и временному процессу миграции. Не создавайте интеграцию или синхронизацию с ним для TO-BE.
- Phase 1 использует mock `BillingProvider`. Не блокируйте MVP отсутствием production API NetUP. Будущий NetUP-адаптер допускает только чтение.

## Границы фаз

- Phase 1: Service Desk foundation, PostgreSQL, RBAC, Subscriber 360 с mock BillingProvider.
- Phase 2: реальный read-only NetUP и сопоставление подключений.
- Phase 3: Telegram `field_dispatch`. Монтажникам не нужен кабинет OSS Control Center.
- Phase 4: Network Diagnostics из LibreNMS, Icinga и BDCOM collectors.
- Phase 5: массовые аварии, корреляция и аналитика.
- Не подключайте реальный NetUP, Telegram-ботов, группы или оборудование без отдельного задания и согласованных реквизитов.

## Доменные инварианты

- Поддерживайте Ethernet, EPON и GPON. ONU необязателен; не придумывайте сетевые идентификаторы и результаты диагностики.
- Отделяйте данные биллинга, мониторинга и ручной проверки. Финансовое состояние не является техническим состоянием. Отсутствующее техническое наблюдение показывайте как `UNKNOWN`.
- Статус заявки, состояние Telegram-доставки и состояние выездных работ независимы. Ответ монтажника не закрывает заявку: решение и закрытие выполняет только инженер OSS.
- Не добавляйте подразделения, роли или маршруты эскалации сверх call-центра, двух сетевых инженеров OSS и монтажного сектора.

## Изменения и проверка

- Миграции PostgreSQL должны быть версионированы; изменения заявки, истории и аудита выполняются согласованно в транзакции.
- Применяйте RBAC на сервере, а не только в интерфейсе. Не записывайте секреты и полные персональные данные в общие логи.
- При изменении поведения обновляйте API contracts, data model, workflow и acceptance criteria в том же изменении.
- Проверяйте минимум: контракт mock BillingProvider, права оператора и инженера, создание/закрытие заявки, сохранность истории и разделение статусов.
