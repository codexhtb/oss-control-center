# Вклад в OSS Control Center

## Рабочий процесс

1. Сверьте `git status`, текущую ветку и задачу. Не включайте в commit не относящиеся к ней изменения.
2. Прочитайте `AGENTS.md`, `docs/README.md` и страницу затрагиваемого модуля.
3. Изменяйте только нужный модуль; избегайте параллельного workflow и необоснованного рефакторинга.
4. При изменении поведения обновите API/data/workflow docs вместе с кодом. Старые фазовые спецификации лежат в `docs/archive/`.
5. Запустите целевые проверки и затем минимально необходимую регрессию. Никогда не направляйте тестовую конфигурацию на рабочую БД.
6. Посмотрите `git diff --check`, `git diff --stat`, полный staged diff и секреты/PII до commit.
7. Commit должен объяснять изменение. Push, merge и deployment выполняются только в пределах явного разрешения задачи.

## Миграции и рабочие данные

Новая схема требует новой Alembic revision; миграции проверяются на отдельной тестовой PostgreSQL. Не применяйте migration к runtime без отдельного явного разрешения. Не пересоздавайте volumes и не удаляйте/переписывайте исторические данные.

## Минимальные проверки

```bash
python -m pytest tests/test_<area>.py
ruff check app tests
cd frontend && npm test -- --run
cd frontend && npm run typecheck && npm run build
```

Команды выбирайте по затронутой области; это не замена целевой проверки миграции или интеграции. Используйте установленные в `pyproject.toml` и `frontend/package.json` команды.
