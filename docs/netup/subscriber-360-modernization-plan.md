# Subscriber 360: аудит UTM5 и план модернизации

Статус первоначального аудита: исследование, **без изменения приложения и NetUP**. Проверка выполнена
2026-11-03 только `SELECT` по лабораторной восстановленной копии UTM5. Это
**резервная база**, а не работающая реплика: опубликованная дата копии —
2026-10-10, точное время снимка неизвестно. Control Center ещё не production.
После появления репликации все выводы о полноте, задержке и связях надо
повторить на новой read-only реплике. PostgreSQL OSS остаётся источником истины
для заявок; данные NetUP только читаются.

**Реализация после аудита (2026-11-04):** адаптер сохраняет неизвестные типы
неудалённых связей как наблюдения с неопределённой активностью; карточка
получила вкладки «Обзор», «Услуги», «Платежи», «Подключения», «Обращения».
Услуги сгруппированы по фактической связи с подключением, без догадки о
числовом типе или признаке «основная». Финансовая история, цены, периоды и типы блокировок остаются недоступными до
подтверждения кодов и единиц по установленной версии UTM5. Фраза ниже о
неизменённом frontend относится к дате первоначального аудита.

## Что читает действующий адаптер

`app/modules/billing/netup/repository.py` читает `users` → `users_accounts` →
`accounts`, действующие `service_links` → `services_data` **только при**
`service_type IN (2,3)` и совпадающий `periodic_service_links`, текущий тариф
через `account_tariff_link` → `tariffs`, IP-группы и ограниченные поля счёта
(`balance`, `credit`, `is_blocked`). `normalizer.py` отображает
`periodic_service_links.is_blocked` как блокировку услуги. Адаптер не читает
`accounts.int_status`, `accounts.flags`, `accounts.block_id`/`blocks_info`,
стоимость, период тарификации, операции и историю услуг. Состояние услуги в
биллинге не является состоянием сети.

В копии все 2 961 неудалённых текущих связей имеют тип 2 (120) или 3
(2 841) и периодическую запись. Каталог содержит две записи с названием,
совпадающим с «Внешн… IP»; у них тип 2 и 119 неудалённых связей. Таким
образом, **сам фильтр `IN (2,3)` сейчас не исключает «Внешний IP»**.
Отдельно проверять результат API и карточку конкретного абонента: дополнительная
услуга может теряться из-за остальных условий активности, лимита ответа либо
представления. Исторические связи типа 1 есть (2 865, сейчас неудалённых 0);
использовать текущий фильтр для истории нельзя. Для будущей реплики не считать
множество типов закрытым: неизвестный тип выдавать с `UNKNOWN`-семантикой,
а не молча отбрасывать. Числовые коды типов не переименовывать по догадке.

## Источники и доказанная семантика

| Область | Таблицы и поля | Что подтверждено и что остаётся неизвестным |
|---|---|---|
| Интернет | `accounts.int_status` | В копии значения 0 (2 219 счетов) и 1 (2 736). Руководство UTM5 различает переключатель «Интернет» и тип блокировки. **Соответствие кода 0/1 GUI «Включён» не проверено**; поле-кандидат, не готовый булев статус. |
| Блокировки счёта | `accounts.is_blocked`, `flags`, `block_id`; `blocks_info.id`, `account_id`, `block_type`, `start_date`, `expire_date`, `is_planning`, `is_deleted`, `flags` | `is_blocked` имеет коды 0, 16, 48, 256, 768; `blocks_info.block_type` — 1 и 2. Среди 4 955 счетов `is_blocked<>0` у 110, актуальная запись `blocks_info` у 1 890, совпадение у 26. Это разные сигналы; **битовые значения и коды причин не расшифрованы**. Нельзя из двух кодов вывести все три вида блокировки. |
| Блокировка услуги | `periodic_service_links.is_blocked` | У всех 2 961 текущих периодических связей значение 0. Не подменяет блокировку счёта или интернет-переключатель. |
| Экземпляры услуг | `service_links.id`, `user_id`, `account_id`, `service_id`, `tariff_link_id`, `is_deleted`; `services_data.id`, `service_name`, `service_type`, `tariff_id` | `service_links.id` — ключ экземпляра; один каталожный ID может быть подключён многократно. Для полного списка проверять все типы и правила актуальности каждой subtype-таблицы. |
| Цена и период | `periodic_services_data.cost`; `periodic_service_links.cost_coef`, `discount_period_id`, `start_date`, `expire_date`, `last_charge_date`; `discount_periods.periodic_type`, `discount_interval`, `canonical_len`, `start_date`, `end_date`; `account_tariff_link`, `tariffs`; для разовых — `once_service_data.cost`, `once_service_links.cost_coef` | У всех 2 961 текущих периодических связей есть строка цены, период и коэффициент. В копии `discount_periods.periodic_type` принимает 3 (2 955 связей) и 1 (6). **Реальная стоимость, единица, валюта, налог, скидка, пропорциональное начисление и смысл кодов периода не подтверждены**. Наличие `cancel_id` само по себе не признак отмены: оно заполнено и у остальных. **Знак/вид возврата и единицы сумм не доказаны**. | Начисления и списания | `discount_transactions_all.account_id`, `service_id`, `slink_id`, `service_type`, `discount_period_id`, `discount_date`, `charge_type`, `discount`, `discount_with_tax`, `incoming_rest`, `outgoing_rest`; `dtagg_periodic`; `invoice_entry`, `invoices`; `balance_history` | 1 540 459 строк транзакций; встречаются `charge_type` 1, 2, 3, 16, 17, 18, 22, 23. **Значения кодов и знак операции не доказаны**. `invoice_entry`/`invoices` — кандидаты для документальной сверки, не замена ledger. |
| История услуг | `tariffs_history.account_id`, `tariff_id`, `link_date`, `unlink_date`, `tariff_name`; `user_log.user_id`, `date`, `action`, `what`; `service_links`, `periodic_service_links` | `tariffs_history` содержит 15 183 строк, `user_log` — 354 260. История тарифов не равна полной истории подключений и отключений услуг. `user_log` имеет свободный текст: нужна проверка структуры, прав доступа и полноты без вывода персональных данных. Это кандидаты, а не автоматически подтверждённая дата начала обслуживания. |

Временной диапазон в копии по числовым Unix timestamps: `users.create_date`
1281945304–1791281377, `users.connect_date` 1281902400–1791234000,
платежи 1281950276–1791576536, начисления 1281949970–1791576538,
тарифная история 1281949950–1790415200. Эти границы показывают наличие старых
записей, **не доказывают непрерывную полную историю каждого абонента**.
Особенно нельзя восстанавливать ранние подключения только из нынешних
`service_links`. Сначала проверить в UTM5 миграции/архивирование и полноту
ledger по отдельным счётам в неперсонализированной тестовой выборке.

Руководство производителя описывает **административную**, **пользовательскую**
и **системную** блокировки, а также отдельный переключатель «Интернет»;
после снятия блокировки интернет может требовать отдельного включения.
Источник: [официальное руководство UTM5 5.5-019](https://www.netup.ru/ru/utm5/utm5docs/5.5-019-release-web/index.html).
Руководство описывает поведение интерфейса, но не подтверждает соответствие
числовых кодов именно этой схеме. Для такого соответствия нужны документация
версии установленной UTM5 и сверка с GUI на безопасных тестовых счетах.

## Предлагаемая модель и интерфейс (после подтверждения)

- **Обзор:** личность, ЛС, контакты, адрес и отдельно дата начала обслуживания
  с указанным источником. Не повторять ЛС/имя в нескольких информационных
  панелях; короткая шапка остаётся контекстом всех вкладок.
- **Услуги и доступ:** каждый `service_links.id` отдельной строкой, название,
  тип (только после расшифровки), тариф, проверенная цена/валюта/период,
  даты, блокировка услуги. Отдельно блокировки счёта с причиной/интервалом
  и переключатель интернета. Не объединять их в один «активен».
- **Финансы:** счета, текущий баланс/кредит и хронология платежей, начислений,
  возвратов и корректировок с типом, единицей, датой операции и датой внесения.
  Доступ через существующее `subscribers.finance.read`; не выводить сумму,
  пока формат/валюта не подтверждены.
- **Подключение:** существующие IP-группы, адресация, порт и VLAN. Не
  интерпретировать это как текущую доступность линии.
- **История:** изменения услуг и тарифов, затем история заявок OSS с явным
  разделением источников. История заявок остаётся в PostgreSQL OSS.

Сейчас `frontend/src/pages/SubscriberPage.tsx` показывает имя и ЛС в шапке,
ещё раз ЛС в «Счета и договоры», «Финансовые сведения» и у каждой услуги;
тариф присутствует в строке услуги, а отдельной истории NetUP нет. Финансовая
блокировка показана рядом с балансом, хотя связана с доступом. Контакты и
адреса остаются в одной группе; «История обращений» относится к OSS, а не к
UTM5. При реализации убрать повторяющиеся полные подписи в пользу контекстного
ЛС и ясных групп, сохранив показ ЛС там, где несколько счетов необходимо
различать. **Frontend на этом этапе не менялся.**

Контракт-кандидат: `AccountAccessState` с **раздельными**
`internet_enabled`, `account_block_flags`, `active_blocks[]`,
`service_blocks[]`; `SubscribedService` по `service_link_id` с ценой как
типизированным `Money(amount, currency, unit)` **только после валидации**,
`BillingPeriod` и датами; `LedgerEvent` с исходным ID/типом и временем;
`ServiceHistoryEvent` с проверенным источником. У каждого поля и у каждой
коллекции хранить `FieldOrigin(source=NETUP, observed_at, quality)`, а также
`source_snapshot_at` и `replica_lag` отдельно от времени чтения. При
неизвестном коде, неполной истории или расходящихся источниках использовать
`UNKNOWN`/`CONFLICT`, при старой копии `STALE`, при недоступности источника
`UNAVAILABLE`. Не превращать пустой список в доказанное отсутствие событий.

## Последовательность реализации и ворота проверки

1. Получить схему/документацию **той версии UTM5**, которая станет источником
   реплики; подтвердить числовые коды блокировок, `int_status`, типов услуг,
   `charge_type`, единицы/валюту и формулу итоговой цены по тестовым счетам и GUI.
2. Проверить полноту архива с момента `connect_date`: наличие удалённых
   связей, событий подключения/отключения, возвратов, отмен и начальных
   остатков. Утвердить, какие события действительно доступны, какие показывать
   как неполные. Зафиксировать задержку реплики и момент последнего обновления.
3. Обновить API contracts, data model, workflow и acceptance criteria вместе
   с поведением. Уточнить RBAC для истории финансов и чувствительных данных.
4. Реализовать новые read-only запросы адаптера пакетно, с фильтрацией по
   подтверждённым ключам, датам и удалению; ограничить страницы истории,
   проверить индексы/план на реплике и стабильность чтения. Не менять NetUP.
5. Ввести типы API и преобразование с качеством каждого поля. Миграции
   PostgreSQL **для NetUP-данных не нужны**, если остаётся read-through;
   если будут сохранённые snapshots/кэш, подготовить отдельную версионированную
   миграцию только после согласования срока хранения и обратной совместимости.
   Существующие заявки и их snapshots не переписывать.
6. Затем изменить вкладки Subscriber 360, добавив тесты на дополнительные
   услуги, независимость трёх блокировок и интернет-переключателя, цену,
   неполную историю, качество данных, RBAC, задержку реплики. Повторить аудит
   на реплике до допуска результата к использованию.

До выполнения пунктов 1–2 **не показывать неподтверждённые денежные значения,
не давать оператору итоговый статус доступа и не называть историю полной**.
Действующие экраны и интеграции остаются без изменений.
