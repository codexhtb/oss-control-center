# UTM5 → Subscriber 360: проект сопоставления

Это карта **обнаруженной схемы**, не спецификация production API NetUP и не
реализация адаптера. Лабораторная копия датирована 2026-10-10. Source of truth
для заявок остаётся PostgreSQL; NetUP — будущий read-only источник биллинга.
Существующий контракт: `app/modules/billing/provider.py`, `source_dto.py`,
`quality.py`, `app/modules/network/models.py`.

## Источник и время каждого поля

Будущий live-адаптер присваивает каждому полю `FieldOrigin(source='NETUP',
observed_at=<UTC time of read>, quality=...)`. Это **время чтения**, поскольку
UTM5 не предоставляет дату изменения для каждого поля. `Subscriber360.fetched_at`
фиксирует тот же согласованный read snapshot. Отдельно хранить дату копии/
источника, если работа ведётся с восстановленной базой: такие данные нельзя
представлять как live. Недоступность базы → `BillingUnavailable`/HTTP 503, а
не успешная пустая карточка. Биллинговые блокировки не меняют
`technical_state=UNKNOWN`.

Для 8 конфликтных IP-групп нельзя отдавать выбранный `MIN(switch_id/port_id/
vlan_id)` как `KNOWN`: кандидат может вычисляться только для проверки
`COUNT(DISTINCT)=1`. При `>1` значение `null`, метка `CONFLICT`. При нуле —
`null`, `UNKNOWN`. Поля с неподтверждённой семантикой остаются `UNKNOWN` даже
если ненулевое число доступно в UTM5.

Текущий контракт не содержит метаданных качества **пустых коллекций**.
`contracts=[]` и `connections=[]` сами по себе не различают «в источнике
доказанно нет» и «сведения отсутствуют». Перед реальной интеграцией нужно
согласовать метку качества коллекции; иначе UI должен явно объяснять, что
пустой список в лабораторной схеме не доказывает отсутствие договора или линии.
