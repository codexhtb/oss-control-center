# UTM5: проверенные связи Subscriber 360

Источник: восстановленная копия `UTM5` от 2026-10-10, MariaDB 10.11.19,
`codex_ro@localhost`. Проверка проведена 2026-10-13 только через read-only
`netup-sql`. Результаты относятся **только к этой копии**. В схеме нет объявленных
FOREIGN KEY, поэтому каждое ребро ниже проверено агрегатным JOIN. SQL:
[`10_identity_accounts.sql`](sql/10_identity_accounts.sql),
[`20_services.sql`](sql/20_services.sql),
[`30_network.sql`](sql/30_network.sql).

## VERIFIED

| Связь | Фактическая проверка |
|---|---|
| `users.basic_account = accounts.id` | У всех 4 955 неудалённых пользователей найден неудалённый основной счёт. |
| `users_accounts.uid = users.id`, `account_id = accounts.id` | Все 5 099 связей находят обе записи; 4 955 неудалённых связей соединяют неудалённые записи. Для основного счёта каждого неудалённого пользователя есть неудалённая связь. Среди этих связей нет многосчётных пользователей или счетов с несколькими пользователями. |
| `service_links.user_id/account_id` | Все 21 048 связей услуг находят пользователя, счёт и их пару в `users_accounts`; 2 961 неудалённая связь имеет неудалённые user/account/service/pair. |
| `service_links.service_id = services_data.id` | Все 21 048 ссылок разрешаются. Среди 2 961 неудалённой связи: 120 с `service_type=2`, 2 841 с `service_type=3`. |
| Подтипы каталога по общему `id` | Все 43 строки `services_data` типа 1 имеют `once_service_data`, все 7 типа 2 — `periodic_services_data`, все 221 типа 3 — `iptraffic_services_data`. Это проверка JOIN, а не внешний ключ. |
| `periodic_service_links.id = service_links.id` | Все 2 961 неудалённые связи имеют неудалённую периодическую запись. Таблица используется как для типа 2, так и для типа 3; считать её исключительно типом 2 нельзя. Две строки периодической таблицы не находят родительскую связь. |
| `iptraffic_service_links.id = service_links.id` | Все 2 841 неудалённые связи типа 3 имеют неудалённый IP-подтип. Две строки IP-подтипа не находят родительскую связь. |
| `iptraffic_service_links.ip_group_id = ip_groups.ip_group_id` | 2 841 активная IP-связь ссылается на 2 841 разные группы, каждая имеет хотя бы одну неудалённую строку. Одна группа не разделяется между активными услугами или счетами. |
| `ip_groups.switch_id = switches.id` | Все 2 876 неудалённых строк IP-групп с положительным `switch_id` находят неудалённый коммутатор. У всех 296 неудалённых коммутаторов найден неудалённый `switch_types` по `type_id`. |
| `service_links.tariff_link_id = account_tariff_link.id` | Все 2 841 неудалённые связи типа 3 находят неудалённый тарифный link того же счёта; `account_tariff_link.tariff_id` совпадает с `services_data.tariff_id`, тариф существует и неудалён. У 120 связей типа 2 `tariff_link_id` не задан. |

**INFERRED:** `users.id` — внутренний идентификатор абонента;
`service_links.id` — идентификатор экземпляра услуги, а не строки каталога;
`ip_groups.ip_group_id` — идентификатор группы технических параметров. Эти роли
поддерживаются кардинальностью JOIN, но внешнее бизнес-наименование полей UTM5
не подтверждено документацией владельца биллинга.

## Множественность и противоречия

- **VERIFIED:** из 4 955 неудалённых счетов 2 114 не имеют неудалённых услуг,
  2 746 имеют одну, 95 — несколько (до 11). Все 2 841 счёта с услугой типа 3
  имеют ровно одну такую связь. У всех 95 многосервисных счетов есть типы 2 и 3.
- **VERIFIED:** 2 841 IP-группа представлена 4 920 неудалёнными строками.
  У 1 705 групп строк больше одной, максимум 68. Прямой JOIN без свёртки
  размножит карточки подключений.
- **CONFLICT:** у восьми IP-групп больше одной различной полной тройки
  `switch_id/port_id/vlan_id`. У трёх групп конфликтует switch, у пяти port,
  у восьми VLAN. Такие значения нельзя выбирать через `MIN()` как фактическое.
- **CONFLICT:** у 212 активных IP-связей положительные `users.remote_switch_id`
  и `users.port_number` не совпадают с единственным ненулевым значением
  соответствующей IP-группы; совпадений нет. Ещё у двух группа не имеет
  switch/port. Эти поля `users` не следует подставлять вместо IP-группы.

## Индексы и планы

Планы безопасно воспроизводятся через [`50_explain.sql`](sql/50_explain.sql).

| Шаг | EXPLAIN на копии | Следствие |
|---|---|---|
| Поиск `accounts.id` | `PRIMARY`, `const`, 1 строка | Быстрый только после подтверждения, что этот ID и есть внешний лицевой счёт. |
| Обратный поиск пользователя по счёту | Оптимизатор сканирует `users` (оценка 5 005) и использует уникальный индекс `users_accounts(uid, account_id, is_deleted)` | Индекса с ведущим `users_accounts.account_id` нет; на текущем объёме скан ограничен, на росте нужен отдельный план с владельцем UTM5. |
| Услуги счёта | Индекс `service_links(account_id, tariff_link_id, id, is_deleted, user_id)`, оценка 2 строки; каталог и periodic link через `PRIMARY` | Не сканирует журнал услуг целиком. |
| IP-группа | `service_links.account_id` → `iptraffic_service_links.PRIMARY` → индекс `ip_groups(ip_group_id, ip_type, is_deleted)`, оценка 1 строка на JOIN | План индексный, но фактическая кратность группы может быть до 68 строк. |

**UNKNOWN:** `accounts.id` пока только кандидат на номер, который диктует оператор.
`accounts.account_name` пуст во всех 5 099 строках; у всех неудалённых счетов
пуст `external_id`. `users.login` совпадает с десятичным `accounts.id` лишь
у трёх из 4 955 неудалённых абонентов. Нужна проверка формата лицевого счёта
в UI/документации UTM5 владельцем биллинга без передачи нам реальных значений.
