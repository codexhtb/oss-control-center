# ADR-001: NetUP provider и кратность IP-групп

Статус: принято для ветки реализации NetUP Provider 1.0; включение адаптера
в эксплуатацию требует отдельного read-only канала. Основание —
[`relationships.md`](relationships.md), [`network-mapping.md`](network-mapping.md)
и [`lookup-by-account.md`](lookup-by-account.md).

## Compatibility review

Существующий `BillingProvider.lookup_by_account(str) -> Subscriber360 | None`
работает для mock; `None` означает отсутствующий ЛС, `BillingUnavailable` —
недоступный источник. Он не выражает неоднозначный ЛС или неполную связь.
HTTP `/subscriber-lookups` и PostgreSQL `subscriber_snapshots`/
`connection_snapshots` хранят один `billing_account`, плоские `Connection`
и `ip_group`. Связь выбранной услуги и подключения не проверяется. База
содержит immutable snapshots; миграции 0001–0004 уже применялись и не меняются.

## Решение

1. Сохранить прежний метод и поля. Добавить типизированные исключения для
   неоднозначного/неполного результата, не превращая их в `None` или 503.
   NetUP adapter по умолчанию не подключён к HTTP API; mock остаётся dev
   провайдером до отдельного включения.
2. Добавить к `Subscriber360` и HTTP-карточке `accounts[]` с признаком
   основного счёта; к `Connection` — `service_id` и `ip_groups[]`. Каждый
   `IpGroup` имеет исходный ключ и массив отдельных строк с ID, `ip_type`,
   адресацией, DHCP-пулом и биллинговой тройкой. Эти поля добавочные:
   старые mock и старые snapshots читаются с пустыми списками. Snapshot
   хранит структуры как JSONB; новые значения не редактируются после записи.
3. Не декодировать `ip/mask` в IPv4 и не называть адрес публичным или
   статическим без подтверждённого правила. Исходные числа сохраняются в
   защищённом snapshot с `quality=UNKNOWN`; UI не должен представлять их как
   готовый сетевой адрес. `switch/port/VLAN` сохраняются **строкой одной
   исходной записи**, а не как независимые `MIN`. Если группе нужна одна
   плоская тройка и есть несколько вариантов, у полей качество `CONFLICT`.
4. NetUP SQL port читает только разрешённые таблицы параметризованными
   запросами в одной read-only транзакции, с лимитами и таймаутами. Он не
   читает пароли, не использует административную учётную запись, не
   изменяет UTM5. Исследовательский `netup-sql` wrapper не является
   runtime-каналом и не подключается к API.
5. Биллинговая тройка — заявленная конфигурация, а не подтверждённое
   сетевое подключение. `access_type` и техническое состояние остаются
   `UNKNOWN`. Network Inventory и Diagnostics позже добавят отдельные
   наблюдения; они не перезаписывают исходный billing snapshot.

## Неопределённости и развёртывание

- Ведущие нули ЛС не нормализуются. NetUP SQL lookup принимает только
  каноническую десятичную запись `accounts.id`; иной ввод получает явную
  ошибку формата до обращения к базе. Это защищает от ложного совпадения.
- Официальный смысл кодов `ip_type`, числового IP/маски, VLAN/port, а также
  правила для восьми многотопологических групп остаются неизвестными.
- Одному `service_links.id` в копии соответствует один ключ
  `iptraffic_service_links.ip_group_id`, но многие строки `ip_groups`.
  Source DTO допускает несколько ключей для будущих источников, не
  утверждая, что текущая схема их содержит.
- Новые JSON поля сохраняются отдельной миграцией с `[]` по умолчанию.
  Старые snapshots не переписываются. Текущие клиенты видят прежние поля;
  строгим клиентам нужно принять добавочные JSON ключи.
