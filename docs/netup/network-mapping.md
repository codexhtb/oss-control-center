# UTM5: технические параметры и границы их значения

Проверки выполнены на копии UTM5 от 2026-10-10. Метаданные и агрегаты:
[`30_network.sql`](sql/30_network.sql) и
[`70_ip_group_semantics.sql`](sql/70_ip_group_semantics.sql). Ни один IP, MAC, hostname или строка
конкретного абонента не сохранены в этом репозитории.

## Проверенная цепочка

`service_links.id` (тип 3) → `iptraffic_service_links.id` →
`iptraffic_service_links.ip_group_id` → `ip_groups.ip_group_id`.

**VERIFIED:** 2 841 неудалённая IP-связь имеет одну ссылку на группу; ссылки
уникальны между активными услугами. Группа содержит от 1 до 68 неудалённых
строк. `ip_groups.id` — ID отдельной строки, **не** ID всей группы. Сверенная
с GUI сервисная связка имеет две строки одного ключа группы: одна содержит
пул, другая адресацию. В интерфейсе такие строки могут отображаться как
несколько IP-групп; SQL-кратность требует хранить обе.

Для повторной точечной сверки ID связки из GUI использовать только связанные
параметры и агрегаты, не выводя ID группы или адреса:

```sql
SELECT COUNT(DISTINCT sl.id) AS link_matches,
       COUNT(DISTINCT isl.ip_group_id) AS group_keys,
       COUNT(g.id) AS live_group_rows,
       SUM(g.pool_id>0) AS pool_rows,
       SUM(g.ip<>0) AS address_rows
FROM service_links sl
LEFT JOIN iptraffic_service_links isl ON isl.id=sl.id AND isl.is_deleted=0
LEFT JOIN ip_groups g ON g.ip_group_id=isl.ip_group_id AND g.is_deleted=0
WHERE sl.id=:gui_service_link_id;
```

На копии счётчики равны соответственно 1, 1, 2, 1, 1.

| Наблюдение на 2 841 группах | Число | Оценка |
|---|---:|---|
| Нет ненулевых switch/port/VLAN | 9 | **UNKNOWN** для этих полей |
| Ровно одна различная полная тройка | 2 824 | **INFERRED** единая биллинговая привязка; не физически проверенное подключение |
| Несколько полных троек | 8 | **CONFLICT** только для проекции в одно подключение; сохранять все строки |
| Группы с более чем одной строкой | 1 705 | Хранить кратность; 1 695 групп содержат и заполненные, и нулевые `switch_id` в разных строках |

Среди 4 920 неудалённых строк групп у 2 876 одновременно указаны положительные
switch/port/VLAN; все 2 876 `switch_id` находят неудалённый `switches.id`.
Все положительные `port_id` находятся в пределах `switches.ports_count`, все
положительные `vlan_id` — в диапазоне 1–4094 (**VERIFIED** как числовая
проверка; это всё ещё не доказательство физического обозначения порта/VLAN).
У всех 296 неудалённых коммутаторов есть неудалённый `switch_types`.

**CONFLICT:** `users.remote_switch_id/port_number` заполнены у 214 активных
IP-связей; для 212 соответствующая IP-группа имеет единственные ненулевые
switch/port, но оба значения расходятся с `users`. Совпадений нет. Не
использовать эти пользовательские поля как fallback для топологии.

## Адресация, DHCP и поля интерфейса

| Элемент вкладки NetUP | Кандидат в UTM5 | Доказательство и граница |
|---|---|---|
| Статический IP и маска | `ip_groups.ip`, `mask` на конкретной строке | **VERIFIED:** ненулевые поля всегда встречаются вместе в live строках. Кодирование signed BIGINT, публичность адреса и точный смысл `ip_type` **UNKNOWN**. |
| Дополнительный IP и маска | `ip_ext`, `mask_ext` | **VERIFIED:** нулевые во всех 4 920 live строках; назначение **UNKNOWN**. |
| Коммутатор | `ip_groups.switch_id` → `switches.id/name` | **VERIFIED** JOIN и существование; соответствие видимому полю вкладки DHCP **INFERRED** по структуре/наблюдению GUI, не по выгруженным абонентским значениям. |
| Порт и VLAN | `ip_groups.port_id`, `vlan_id` той же строки | **VERIFIED** совместная заполненность и числовые диапазоны; точное экранное/физическое обозначение **INFERRED**. |
| Динамический DHCP-пул | `ip_groups.pool_id` → `dhcp_pool_info.id` → `dhcp_pool_ranges.pool_id` | **VERIFIED:** все 2 738 live строки с `pool_id>0` находят неудалённый пул и хотя бы один live диапазон. Значения диапазона не выгружались. `pool_name` заполнен в 10 строках, но только одна имеет `pool_id>0`; не считать поле заменой связи. |
| Роль строки | `ip_groups.ip_type` | **INFERRED:** код 4 всегда встречается с `ip/mask` и без switch/port/VLAN/pool; коды 0/1 могут содержать пул с топологией либо адрес с топологией. Официальная расшифровка кодов **UNKNOWN**. |

В live строках `ip_type=0`: 2 709 содержат пул, 269 адрес; у `ip_type=1`:
29 пул, 8 адрес; у `ip_type=4`: 1 896 адрес без топологии. В одной строке
`pool_id>0` и `ip<>0` не встречаются. При этом 1 682 группы содержат и пуловую
строку, и строку типа 4 с адресом; ещё 35 групп сочетают пул со строкой
типа 0/1 с адресом. Следовательно, DHCP-настройки и назначенный адрес могут
сосуществовать в одной сервисной связке. Считать такой адрес именно
«статическим публичным IPv4» на основании чисел пока нельзя.

У восьми групп с несколькими сетевыми тройками все 46 строк неудалённые,
`create_date/delete_date` в live строках нулевые. Семь групп имеют несколько
троек даже среди строк с пулом; шесть — несколько адресов. Это не объясняется
удалёнными историческими строками. Множественная адресация возможна, но
правило выбора одной текущей топологии не установлено: статус плоской
проекции `CONFLICT`, строки сохраняются раздельно.

## IP, MAC и тип доступа

- **VERIFIED:** 1 806 из 2 841 живых групп имеют хотя бы одно ненулевое
  `ip_groups.ip`, 1 035 — ни одного. У 128 групп несколько разных IP.
  `ip_ext` и `mask_ext` не заполнены ни в одной живой строке.
- **UNKNOWN:** `ip_groups.ip` хранится числом; 140 живых строк имеют
  отрицательное значение при signed BIGINT. Способ декодирования IP и
  официальная семантика `ip_type` (коды 0, 1, 4) не подтверждены. Не печатать
  и не преобразовывать IP в карточке до проверки формата владельцем UTM5.
- **VERIFIED:** `ip_groups.mac` пуст во всех 4 920 живых строках.
  `dhcp_leases` содержит 1 815 записей с MAC, но лишь 85 арендами, не
  истёкшими к концу дня копии. Связь по IP есть у 1 737 групп за всё время,
  но динамическая аренда не доказывает постоянный MAC подключения. Для
  Subscriber 360 MAC пока **UNKNOWN**.
- **UNKNOWN:** ни один столбец схемы не содержит `onu`, `olt`, `epon` или
  `gpon`; единственный столбец с `serial` относится к `accounts` и
  обозначает `irdeto_stb_serial_number`. `slink_tech_param` пуст. ONU ID
  нельзя извлекать из этого поля или придумывать.
- **UNKNOWN:** две живые модели `switch_types.name` содержат `BDCOM` и
  используются 25 живыми коммутаторами, но нет проверенного правила,
  позволяющего назвать их Ethernet, EPON или GPON; названия типов OLT/EPON/GPON
  не встречаются. В NetUP-карточке `access_type=UNKNOWN` до отдельного
  источника/правила сопоставления. BDCOM само по себе не равно EPON.

## Проекция в существующий `Connection`

| Поле | Источник-кандидат | Правило/ограничение |
|---|---|---|
| `ip_group` | `iptraffic_service_links.ip_group_id` | **VERIFIED** связь; строковое представление ID группы, если подтверждена его внешняя семантика. |
| `device` | `switches.name` по `switch_id` конкретной строки | JOIN и актуальность строки **VERIFIED**; имя и тип не доказывают Ethernet/EPON/GPON. |
| `port`, `vlan` | `ip_groups.port_id/vlan_id` той же строки | Сохранять связанную тройку. Физический формат и назначение — **INFERRED**. Несколько разных троек при плоской проекции → `CONFLICT`. |
| `access_type` | Нет достоверного поля | `UNKNOWN` для Ethernet/EPON/GPON. |
| `onu_id` | Нет достоверного поля | `null`, `UNKNOWN`. |
| `address` | `users.actual_address` присутствует у многих пользователей | Это адрес пользователя, не доказанный адрес конкретного подключения. В `Connection.address` пока `null`; нужна модель адреса уровня абонента или подтверждение. |

Текущий `Connection` не имеет полей для отдельных адресаций, DHCP-пулов или
нескольких строк `ip_groups`. Перед NetUP-адаптером нужна отдельная
source-модель `ServiceLink → IpGroupKey → IpGroupRow[]`, а затем согласованная
проекция для API и snapshot. Назначенная IP-адресация, DHCP-настройки,
заявленная в биллинге тройка switch/port/VLAN и фактически подтверждённое
сетевое подключение — разные сущности. Последнего UTM5 здесь не даёт.
