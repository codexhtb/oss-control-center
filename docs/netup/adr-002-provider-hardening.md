# ADR-002: NetUP Provider 1.1 — безопасность и жизненный цикл lookup

**Статус:** утверждённые владельцем решения A1/B1/C, реализация в ветке
`codex/netup-provider-1.1-hardening`. Не разрешает production deployment.

## Контекст

NetUPBillingProvider читает UTM5 без изменения источника. PostgreSQL остаётся
единственным source of truth для заявок и их immutable snapshots. Lookup
может не привести к заявке, но содержит персональные данные. Старый плоский
`phone` не выражает несколько исходных номеров. IP-группа содержит несколько
строк, а `dhcp_ranges[]` пока имеет provenance на уровне массива.

## Решения

1. **A1:** lookup без заявки хранится 24 часа от `fetched_at`. `expires_at`
   остаётся только 15-минутным окном создания заявки. Процедура в миграции
   `0006_lookup_cleanup` блокирует кандидатов `FOR UPDATE SKIP LOCKED`,
   удаляет дочерние connection snapshots и затем родительские строки в одной
   транзакции, повторно проверяя отсутствие ticket. FK остаются последним
   барьером гонки. Snapshot заявки, комментарии и история бессрочны.
   `lookup_cleanup_audit` хранит время, cutoff и количество, без ЛС/PII.
   `EXECUTE` отозван у `PUBLIC`; production runtime роль должна быть
   невладельцем таблиц и не иметь `DELETE`/`EXECUTE`. Maintenance grants
   оформляются отдельно перед deployment. В рабочей БД процедура сейчас
   не запускается.
2. **B1:** additive `subscriber.contacts[]` содержит тип исходного телефона,
   значение до подтверждённого размера UTM5 (255 символов), source column,
   `observed_at` и качество. Разные номера сохраняются без выбора
   предпочтительного; плоский `phone` остаётся `null`/`CONFLICT`. Миграция
   `0007_contacts` даёт старым snapshots `[]`. Оператор и инженер с
   `subscriber.read` видят все варианты; Identity admin прав не получает.
3. **C:** сырой `dhcp_ranges[]` не выводится в первом Web UI. Пока его
   значения наследуют `IpGroupRow.field_meta['dhcp_ranges']` для массива;
   поэлементная provenance потребует отдельного технического API-контракта.
4. NetUP lookup не удерживает PostgreSQL-транзакцию во время внешнего I/O;
   роль и активность пользователя повторно проверяются непосредственно
   перед snapshot INSERT. Пакетный SQL использует ограниченные выборки и
   параметризованные списки ID; превышение лимита даёт явную ошибку.
5. Все приватные API ответы получают `no-store`; access log Uvicorn исключает
   query string. Reverse proxy должен применить эквивалентные правила.

## Границы и последствия

Уточнение `contacts[]` не меняет существующие ключи, но строгим клиентам
нужно разрешить добавочное поле. Прямой SQL writer в JSONB способен обойти
структурную валидацию; он не является поддерживаемым application-путём.
Runtime API и maintenance должны иметь разные PostgreSQL-роли до production.
Текущий dev Compose с одной DB-ролью не подтверждает эту границу.
Production TLS-канал, EXPLAIN на production данных, нагрузочные p95/p99 и
полный PostgreSQL прогон 1.1 остаются отдельными gates.
