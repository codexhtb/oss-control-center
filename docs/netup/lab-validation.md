# NetUP provider 1.0: проверка на восстановленной UTM5

Дата: 2026-10-13. Проверка выполнена с `oss-control-dev` через отдельный
TCP-канал к лабораторной копии UTM5 на `172.17.7.1:3306`. Подключение
выполнено пользователем `oss_netup_lab` с правами `SELECT, SHOW VIEW`.
Лабораторная MariaDB не поддерживает TLS; `purpose=lab` и
`allow_plaintext_lab=true` применены только к этому private IP. Production
конфигурация по-прежнему требует TLS CA и проверку сертификата и имени.

## Результаты

- PyMySQL подключился к ожидаемой базе под ожидаемой учётной записью;
  `Ssl_cipher` пуст только для лабораторного подключения.
- Поиск существующего ЛС вернул карточку с сервисной связкой и IP-группой,
  содержащей две исходные строки. Значения ЛС, абонента, адресов и
  технических идентификаторов в отчёт и тестовый вывод не включались.
- Параметризованные запросы внутри тестов выбрали контрольные случаи
  отсутствующего и удалённого ЛС, конфликтующей биллинговой топологии и
  нескольких действующих сервисных связок. Все четыре сценария проверены
  через `NetUPBillingProvider` без публикации выбранных ID.
- Отдельный тест сравнил наборы сервисных связок, ключей IP-групп и ID их
  исходных строк в карточке с независимыми read-only SQL-запросами.
  Сравнение выполнялось в памяти; в pytest отображались только булевы
  результаты.
- `pytest -q tests/test_netup.py -m integration`: **6 passed**.
- Полный доступный `pytest`: **45 passed, 38 skipped, 1 warning**. Пропуски
  относятся к PostgreSQL-тестам, требующим Docker Compose; доступ к Docker
  socket у `codexdev` отсутствует. Ruff, форматирование, `pip check`,
  `docker compose config --quiet` и `git diff --check` прошли.

## Граница готовности

Лабораторный NetUP read-only путь проверен. Миграция `0005_netup_groups`,
атомарное сохранение нового snapshot и HTTP API с реальным PostgreSQL ещё
не прошли интеграционную проверку из-за недоступности Docker socket.
Проверка production TLS-канала также впереди: лаборатория его не
предоставляет. Merge, push и deployment не выполнялись.
