# NetUP UTM5 ↔ LibreNMS: исследование соответствия портов

Дата исследования: 2026-10-14 UTC. Источники: восстановленная UTM5 от
2026-10-10 на `172.17.7.1` (учётная запись только для чтения), LibreNMS
`/api/v0` на `172.17.7.70` (токен только для чтения), действующий локальный
реестр устройств `.dev-secrets/monitoring-mappings.json`. Это исследование
**не добавляет** сопоставлений в реестр и не меняет данные источников.

## Главный вывод и границы доказательства

**VERIFIED:** 48 устройств уже однозначно сопоставлены по *точному,
регистрозависимому* `switches.name = devices.sysName`. Из них 45 имеют
актуальные IP-группы с указанными `switch_id` и `port_id`. На этих устройствах
найдено 254 различных пары `(switch_id, port_id)` и 678 строк IP-групп.

**VERIFIED как совпадение данных двух источников:** для **221** пары Ethernet
кандидатный физический интерфейс LibreNMS определяется однозначно, а его
`ifVlan` совпадает со *всеми* VLAN активных строк NetUP этой пары и уникален
среди физических интерфейсов данного устройства. Это 223 строки IP-групп и
219 экземпляров услуг. Среди этих 221 пар нет пары, разделённой разными
экземплярами услуг. Правило воспроизводимо, но сопоставления относятся к
разным моментам времени: UTM5 — снимок 10 октября, LibreNMS — текущий опрос.
`ifVlan` сам по себе не доказывает физическую коммутацию или текущее состояние
абонента. Перед записью в эксплуатационный реестр инженер должен проверить
модель порта на конкретном оборудовании и актуальность привязки.
Из 219 затронутых услуг у **трёх** есть другая отличающаяся
`(switch_id, port_id)` в строках той же IP-группы: для диагностики этих услуг
результат **CONFLICT**, даже если одна пара прошла VLAN-проверку.
Без такой неоднозначности остаются **216** услуг-кандидатов.

**UNKNOWN:** сейчас в runtime-реестре **0** подтверждённых пар портов.
Числовое равенство `NetUP.port_id = LibreNMS.ifIndex` нельзя применять ко
всем классам оборудования. ONU ID, абонентский UNI-порт и оптика конкретной
ONU из проверенных источников не установлены.

## Методика и генеральная совокупность

Услуга считалась действующей **на момент копии** `2026-10-10 12:00 UTC`, если
не удалены пользователь, счёт, каталог, `service_links`, периодическая и IP
записи; `service_type=3`, `is_planned=0`, `need_del=0`, а момент находится в
`[start_date, expire_date)`. Связь строк: `service_links.id =
iptraffic_service_links.id`, затем `ip_group_id` к **каждой** неудалённой строке
`ip_groups`. Блокировку биллинга не использовали как признак работы сети.
Выборка содержала только технические целые идентификаторы; имена абонентов,
адреса, IP, MAC, телефоны, пароли и значения `ifAlias` не выгружались.

|---|---:|

Первое число 2 876 **не** является числом абонентов или портов: у одной

CiscoSB — 36, BDCOM — 409, generic/Eltex — 6.

поэтому оно не служит второй независимой проверкой имени NetUP. Модель
(`hardware`) у части устройств заполнена, у части нет.

## Реальные классы интерфейсов

Список читался через `GET /api/v0/devices/{device_id}/ports` с явными
`columns=port_id,ifIndex,ifName,ifDescr,ifAlias,ifType,ifAdminStatus,ifOperStatus,ifVlan`.
`ifAlias` сознательно не печатался: свободный текст может содержать
персональные сведения. `port_id` — внутренний ID порта LibreNMS; `ifIndex` —
SNMP-индекс. Они не являются номером порта NetUP по определению.

| Образец | Физические интерфейсы | Логические/ONU-подобные | Проверенное расхождение идентификаторов |
|---|---|---|---|
| BDCOM EPON, Libre ID 6 (`P3310`), 143 интерфейса | 6 `GigaEthernet0/n`, 4 `EPON0/n` | 131 `EPON0/n:m`, 2 VLAN | `EPON0/1..4`: `ifIndex=15..18`, Libre `port_id=808..811`; NetUP на этом устройстве хранит порты `7..10`. |
| BDCOM GPON, case-only кандидат ID 20, 533 интерфейса | 13 Ethernet uplink, 16 `GPON0/n` | 501 `GPON0/n:m`, 2 VLAN, 1 иной | `GPON0/1..16`: `ifIndex=110..125`, Libre `port_id=2246..2261`; NetUP `14..29`. |
| SNR, ID 31, 30 интерфейсов | 28 `Ethernet1/0/n` | 2 `VlanN` | `Ethernet1/0/1`: `ifIndex=1`, Libre `port_id=2983`; номер NetUP `1` встречается на этом устройстве. |
| CiscoSB, ID 69, 19 интерфейсов | `e1..e8`, `g1..g2` | 9 VLAN | `e1`: `ifIndex=1`, Libre `port_id=6907`; у другой модели ID 71 есть `fa1..fa8` и `gi1..gi2`, причём `gi1` имеет `ifIndex=49`. |
| Eltex MES2124F, Libre OS `generic`, ID 75, 99 интерфейсов | 28 `gi1/0/n` | 71 `propVirtual` | `gi1/0/1`: `ifIndex=49`, Libre `port_id=7053`; NetUP использует номера портов `2..28`. |

`ifType=ethernetCsmacd` помог отделить Ethernet от `propVirtual`,
`l3ipvlan` и loopback. У BDCOM физические PON и ONU-подобные интерфейсы оба
имеют `ifType=other`, поэтому дополнительно нужен точный шаблон `ifName` и
исключение двоеточия. Наличие `EPON0/n:m` или `GPON0/n:m` **не** означает,
что NetUP указал ONU `m`. Состояние `ifOperStatus` конкретной ONU нельзя
выдавать за состояние услуги без такой связи.
`ifDescr` у BDCOM и SNR повторяет имя интерфейса, у CiscoSB иногда является
общим описанием вроде `Ethernet Interface`; самостоятельного доказательства
связи с NetUP оно не даёт. `ifAdminStatus/ifOperStatus` действительно
возвращаются раздельно: у ID 6 из 143 интерфейсов 113 `up/up`, 29 `up/down`,
1 `down/down`; у SNR ID 31 из 30 — 8/21/1 соответственно. Эти суммы включают
логические и ONU-подобные интерфейсы, поэтому не являются статистикой
абонентских линий.
Дополнительный API `GET /api/v0/devices/{id}/ports?with=vlans` на образцах
SNR ID 31, CiscoSB ID 69 и Eltex ID 75 подтвердил: `ifVlan` всех
проверенных физических интерфейсов присутствует в их VLAN associations
именно как **untagged** (28/28, 10/10 и 28/28 соответственно), а не как
tagged VLAN. Этот read-only результат усиливает смысл совпадения `ifVlan`
на образцах, но не заменяет проверки конфигурации каждого устройства. На
SNR ID 31 API сообщает 1 212 VLAN associations для 30 интерфейсов: простое
«VLAN встречается на порту» было бы слабым критерием, поскольку tagged VLAN
может присутствовать на многих портах.

## Покрытие и строгое правило отбора Ethernet-кандидатов

Для каждой активной строки проверялись: подтверждённое *точное* устройство;
один физический интерфейс (SNR/CiscoSB — `ifIndex=NetUP.port_id`, Eltex —
`ifName=gi1/0/{port_id}`); `ifVlan` этого интерфейса равно **каждому** VLAN
всех активных строк данной пары; тот же `ifVlan` не встречается на другом
физическом интерфейсе устройства. Результат: SNR **182**, CiscoSB **33**,
Eltex **6**, всего **221** пары. Ещё **33** пары из 254 не проходят этот строгий
критерий: 15 BDCOM EPON и 18 Ethernet; нельзя молча относить их к порту по
суффиксу или по одному совпавшему VLAN.

По всей UTM5 у 5 из 2 841 действующих IP-услуг строки одной группы задают
несколько разных коммутаторов и/или номеров портов; у 8 — несколько VLAN.
Это **не обязательно ошибочные записи**: они могут описывать несколько
адресаций/путей. Но одна услуга не получает один интерфейс LibreNMS без
явного выбора и проверки. Три из этих пяти многозначных услуг попали в
множество 219 услуг с одной сильной кандидатной парой, поэтому исключены из
216 однозначных услуг. Несколько VLAN сами по себе не означают физический
конфликт, особенно на PON.

Для понимания потерь: у SNR только 187 из 227 строк имеют равенство VLAN

**кандидатного физического интерфейса**, а не доказательство исправности
линии. В текущей диагностике интерфейс должен оставаться `UNKNOWN`, пока
инженер не внесёт явную проверенную пару в реестр.

## Оптика BDCOM и собственные коллекторы

Через документированный LibreNMS API `GET /api/v0/resources/sensors`
обнаружено 1 444 сенсора, в том числе 216 класса `dbm`. У четырёх точно
сопоставленных EPON ID 6–9 — **0** сенсоров `dbm` в этом API. У GPON
case-only кандидата ID 20 — **34** `bdcom`/SNMP-сенсора: 17 помечены Rx и 17
Tx. Их `entPhysicalIndex` совпадает с `ifIndex` 16 **физических** PON-портов
(32 сенсора) и одного Ethernet uplink (2 сенсора), ни один — с 501
ONU-подобным интерфейсом. Это оптика порта OLT/uplink, **не** ONU Rx/Tx и не
OLT Rx конкретного абонента. Поле `sensor_custom=No` не связывает их с
самописными коллекторами.

У 31 из 34 записей `lastupdate` приходится на 14 октября, у двух — на 13-е,
у одной — на 11-е. Метка времени API не содержит часового пояса; `last_polled`
LibreNMS у проверенных устройств показывает время примерно на три часа
*позже* текущего UTC dev VM. До проверки часового пояса и расписания нельзя
считать даже записи с датой 14 октября «свежими»; суточный коллектор тем
более не подходит для текущего verdict.

Имена `bdcom-epon-signal-collector.php`, `bdcom-gpon-signal` и
`bdcom-onu-collector` проверены в доступных деревьях проекта, home и локальных
systemd units; файлов нет. SSH к `172.17.7.70` с `StrictHostKeyChecking=yes`
отклонил доступ из-за отсутствия доверенного ED25519 host key. API не
предоставляет маршрута к исходникам этих коллекторов. Поэтому **UNKNOWN**:
их исходный код, systemd `.service/.timer`, частота опроса, таблицы хранения,
ключи ONU и связь результатов с UTM5. Не утверждаем, что коллекторы отсутствуют
на LibreNMS-хосте. Для отдельной проверки нужен проверенный host key и
read-only доступ либо безопасный экспорт исходников, units и схемы хранилища
без строк абонентов и секретов.

## Предлагаемый correlation registry

Существующий `MappingRegistry` (`app/modules/diagnostics/config.py`) хранит
явные пары `netup_switch_id → librenms_device_id` и необязательные
`netup_port_id → librenms_port_id`; сегодня списки `ports` пусты. Для
следующего этапа сохранить эту явную границу и добавить к подтверждаемой
записи **метаданные доказательства** (не абонентские данные):

| Поле | Назначение |
|---|---|
| `netup_switch_id`, `netup_port_id`, `librenms_device_id`, `librenms_port_id` | Ключ пары; `librenms_port_id` разрешать на каждом чтении. |
| `ifIndex`, `ifName`, `ifType`, `device_sysName`, `hardware` на момент проверки | Контроль дрейфа после rediscovery/замены устройства. |
| `access_class`, `match_method`, `quality` | `ETHERNET/EPON/GPON/UNKNOWN`; `ifIndex+unique_vlan`, `ifName+unique_vlan`, `manual_verified`; `VERIFIED/INFERRED/CONFLICT/UNKNOWN`. Не выводить тип доступа абонента из имени устройства. |
| `evidence_at`, `netup_as_of`, `librenms_polled_at`, `verified_by`, `verified_at` | Различить время снимков и ручное утверждение. |
| `source_revision`, `review_note`, `status` | Аудит `candidate/approved/revoked`; при изменении имени/индекса/типа автоматически понижать до `UNKNOWN`, не выбирать другую пару. |

Не хранить в реестре `ifAlias`, ФИО, IP/MAC абонента и токены. Для PON
требуется отдельная сущность **ONU identity** с подтверждённым ключом из
коллектора/инвентаризации и явной связью с сервисной строкой NetUP; один
физический PON-порт не равен абонентскому подключению. При неоднозначных
`switch_id`, `port_id` или нескольких IP-строках с конфликтующей привязкой
выдавать `CONFLICT`, а не брать первую строку.

## Воспроизводимость без персональных данных

1. В UTM5 применить фильтр действующих IP-услуг выше, связать `ip_groups`
   по `ip_group_id`, считать отдельно `COUNT(DISTINCT sl.id)`, `COUNT(g.id)` и
   пары `(g.switch_id,g.port_id)`. Для сравнения держать только технические
   целые `sl.id`, `g.switch_id`, `g.port_id`, `g.vlan_id` **в памяти**; не
   сохранять строки абонентов, IP/MAC и `switches.login/password`.

   Безопасный агрегат для проверки первых трёх чисел таблицы:

   ```sql
   SELECT COUNT(*) AS group_rows,
          COUNT(DISTINCT sl.id) AS ip_service_links,
          SUM(st.id IS NOT NULL AND g.port_id > 0 AND g.vlan_id > 0)
            AS rows_with_live_switch_port_vlan
   FROM service_links sl
   JOIN users u ON u.id = sl.user_id AND u.is_deleted = 0
   JOIN accounts a ON a.id = sl.account_id AND a.is_deleted = 0
   JOIN services_data sd ON sd.id = sl.service_id
        AND sd.service_type = 3 AND sd.is_deleted = 0
   JOIN periodic_service_links psl ON psl.id = sl.id AND psl.is_deleted = 0
   JOIN iptraffic_service_links isl ON isl.id = sl.id AND isl.is_deleted = 0
   JOIN ip_groups g ON g.ip_group_id = isl.ip_group_id AND g.is_deleted = 0
   LEFT JOIN switches st ON st.id = g.switch_id AND st.is_deleted = 0
   WHERE sl.is_deleted = 0 AND psl.is_planned = 0 AND psl.need_del = 0
     AND psl.start_date <= :as_of AND psl.expire_date > :as_of;
   ```

   `:as_of` — параметр `2026-10-10 12:00 UTC` как Unix seconds. Для
   устройства/порта число кандидатов надо считать отдельно после пересечения
   с защищённым реестром 48 точных устройств; этот SQL не выбирает ФИО и
   технические значения конкретного абонента.
2. Чтение устройств: `GET /api/v0/devices`, сравнение имени с NetUP строго
   и уникально; сверить с защищённым локальным реестром. Ответ устройства
   может содержать поля SNMP-auth, поэтому логировать только число устройств,
   модель, ОС и безопасные ID. Чтение интерфейсов ограничить `columns=` как
   выше; `ifAlias` обрабатывать как потенциально чувствительный текст.
3. Для каждой пары выполнить строгое правило предыдущего раздела; считать
   пары, строки и услуги отдельно. Не использовать одно лишь совпадение
   номера. Уточнять `ifAdminStatus`, `ifOperStatus` и время *только после*
   подтверждения пары; `DOWN` OLT/коммутатора не означает автоматически
   неисправность конкретного абонента.
4. Оптические сенсоры читать из `/api/v0/resources/sensors` по `sensor_class`,
   `device_id`, `entPhysicalIndex`; проверять соответствие физическому или
   ONU-подобному `ifIndex`, временную метку и зону. Описание сенсора не
   раскрывать в общих отчётах.

[Документация API устройств LibreNMS](https://docs.librenms.org/API/Devices/),
[портов](https://docs.librenms.org/API/Ports/) описывает read-only маршруты,
включая `with=vlans`, и различные поля идентификаторов. Локальная модель
IP-групп и её кратность описаны в
[`../netup/network-mapping.md`](../netup/network-mapping.md),
границы диагностики — в [`../architecture/oss-diagnostics.md`](../architecture/oss-diagnostics.md).

1. Инженер OSS проверяет несколько кандидатов каждого **точного** Ethernet
   типа в NetUP GUI и на сетевом устройстве read-only способом: значение
   номера порта, `ifName/ifIndex`, VLAN и отсутствие LAG/trunk/виртуальной
   подмены. После этого утверждать пары в реестре с датой и основанием;
   строгие 221 кандидатов можно проверять пакетами, не утверждать автоматически.

   устройства, затем семантику чисел `14..29` и `7..10` по GUI/конфигурации.
   До этого физический PON и ONU остаются `UNKNOWN`.
3. Получить доверенный read-only доступ к исходникам трёх BDCOM-коллекторов,
   их systemd units и **схеме** результатов. Найти стабильный ключ ONU,
   фактическую частоту и timestamp каждой точки; проверить его связь с

   проектировать ONU Rx/Tx/OLT Rx в диагностике.

   проверкой дрейфа; добавить тесты на SNR/Cisco/Eltex, EPON/GPON, LAG,
   VLAN/виртуальные интерфейсы, многозначность и старые наблюдения.

   интерфейса и отсутствие оптики абонента.
