# Регрессия сопоставления устройств Subscriber 360

Проверка 2026-11-05, только NetUP Lab и read-only LibreNMS API. Идентификаторы
ниже относятся к сетевому оборудованию, не к абонентам. Данные NetUP взяты из
исторической лабораторной копии и не подтверждают актуальное подключение
абонента.

## Причина и подтверждение

Runtime берёт соответствия только из защищённого реестра
`.dev-secrets/monitoring-mappings.json`. В нём было 48 пар с уникально точным
именем и 15 вручную утверждённых OLT. Обе нужные пары отсутствовали. Скрипт
`dev/build_monitoring_mappings.py` при пересоздании строил только совпадения
имён с учётом регистра и не переносил утверждённые пары. Точную дату потери
двух записей установить по имеющимся копиям нельзя.

| NetUP Lab | LibreNMS | Проверка идентичности | Решение |
| --- | --- | --- | --- |
| switch 319 `bdcom3310C`, `172.17.6.101`, BDCOM3310C | device 3 `bdcom_test`, `172.17.6.101`, P3310C | Владелец подтвердил физическую идентичность; management IP уникален в обеих выборках | `manual_verified` |
| switch 412 `OREHROSCHA`, `172.17.6.195`, BDCOM3310C | device 82 `orehroscha`, `172.17.6.195`, P3310D | Имена совпадают только без учёта регистра; management IP уникален в обеих выборках | `manual_verified` для dev по проверке источников |

У первой пары имена в исходных системах расположены **обратно** относительно
формулировки обращения: NetUP содержит `bdcom3310C`, LibreNMS — `bdcom_test`.
Сопоставление сделано по ID источников, а не перестановкой строк имени.
Отличие модели `OREHROSCHA` (P3310C/P3310D) сохранено в защищённой записи
доказательств; модель не использовалась как самостоятельное доказательство.

## Исправление и границы

Обе пары внесены только в защищённый dev-реестр и отдельный защищённый журнал
доказательств `.dev-secrets/olt-manual-verification.json`. Существующие 63 пары
сохранены. Приложение читает реестр на запросе, поэтому изменение файла на
месте применилось без перезапуска. В будущем пересоздание реестра с
`--preserve-approved-from` сохраняет `manual_verified` только при уникальном
совпадении management IP в обеих актуальных выборках; изменение IP или
дубликат останавливают сборку для ручной проверки. Само по себе совпадение
IP не создаёт новую утверждённую пару.

Ни одна из этих записей не устанавливает соответствие абонентского порта.
Для проверки наблюдений LibreNMS возвращает состояние обоих устройств `UP`.
У `OREHROSCHA` на пяти проверенных существующих snapshots ONU-поиск вернул
`MATCHED_BY_RULE`; у `bdcom3310C` на пяти проверенных snapshots результат
остался `CONFLICT`/`UNCONFIRMED`. Это не скрывается автоматическим выбором ONU.
Время и качество наблюдений LibreNMS остаются отдельными от исторического
NetUP snapshot. Проверка ранее известной пары 417 → LibreNMS 1 также вернула
`UP`; порт без отдельного подтверждения остался `UNKNOWN`.

## Проверка сохранности реестра

Read-only повторная сборка по 296 коммутаторам NetUP Lab и 86 устройствам
LibreNMS дала 48 точных + 17 утверждённых пар = 65; все 65 текущих записей
сохранились без изменения. Синтетический регрессионный тест проверяет
сохранение alias и case-only пар, отказ при изменении management IP и
дублирующем IP.

Защищённые локальные копии реестра и журнала доказательств сохранены в
`.dev-secrets/` с режимом `0600`. Проверенное зашифрованное резервное
копирование за пределы VM остаётся задачей владельца инфраструктуры.
