# OSS Field Work — этап 2: Mini App и отчёты монтажников

## Данные и права

Миграция `0047_field_work_miniapp_reports` расширяет существующие
`field_external_messages` структурированными ссылками на основного монтажника и
необязательного напарника (`field_installers`), снимком имени напарника и UUID запроса.
Уникальные индексы исключают повтор Mini App отчёта для одного handoff и повтор
одного запроса монтажника. Исторические Telegram-отчёты остаются без этих ссылок.
`field_dispatch_updates` принимает `MINIAPP_REPORT`; `field_work_reschedules.source`
принимает `MINIAPP`. Отдельная отрицательная последовательность update ID не
пересекается с Telegram update ID действующего poller.

Подписанный Telegram `initData` и активный реестр этапа 1 обязательны для каждого
запроса. Монтажник видит только SUKHUM/OCHAMCHIRA, разрешённые его записью. Из
очереди и деталей исключаются удалённые и INTERNAL заявки. Общая очередь не
предполагает персонального назначения: любой разрешённый монтажник направления
может отправить отчёт первым. Клиент не выбирает основного исполнителя.

## API contract

Все пути имеют префикс `/api/v1/field-work/miniapp`, заголовок
`X-Telegram-Init-Data`, ответы `Cache-Control: no-store`.

| Метод | Путь | Смысл |
| --- | --- | --- |
| GET | `/partners?direction=SUKHUM` | Активные монтажники направления, кроме текущего. |
| GET | `/handoffs/{id}/reschedules?page=1&page_size=20` | История переносов конкретной передачи с total. |
| POST | `/handoffs/{id}/reschedules` | `{reason, scheduled_for?, scheduled_date?, expected_version}`. UTC+3 для точного времени; отсутствие даты означает ожидание согласования. |
| POST | `/handoffs/{id}/report` | `{client_request_id, partner_installer_id?, work_text}`. Текст обязателен, напарник не может совпадать с автором. |

Повтор отчёта с тем же UUID и тем же содержимым возвращает исходный report ID;
изменение содержимого или другой handoff с тем же UUID даёт `409`. Уже завершённый
handoff также даёт `409`. Запись handoff блокируется до изменения в одной
PostgreSQL транзакции. Перенос использует существующую optimistic version и
неизменяемую историю `FieldWorkReschedule`.

## Workflow и экран

Маршрут `/field-work` — мобильный React интерфейс внутри текущего WEB. Telegram
WebApp SDK передаёт исходный `initData`, синхронизирует светлую/тёмную тему.
Открытые задания показываются от старых к новым; завершённые ждут проверки,
история содержит подтверждённые инженером работы. Карточка показывает сохранённые
контакты, причину, дату и историю переносов. Отчёт и перенос доступны только для
`AWAITING_REPORT`. После отчёта общий обработчик добавляет сообщение, уведомление
инженеру, событие и аудит, переводит только handoff в `REPORTED` и ставит
синхронизацию исходной Telegram-карточки в очередь poller. Статус Service Desk
заявки не меняется. Инженер использует прежний `verify_handoff`, переводя работу
в `VERIFIED`. Ошибка Telegram при редактировании карточки не откатывает отчёт;
действующий poller повторяет синхронизацию.

## Приёмка и внедрение

Проверить подпись и срок `initData`, запрет чужого направления и INTERNAL,
три очереди, два handoff одной заявки, отчёт с/без напарника, запрет выбора себя,
повтор UUID, конкурентную отправку и конкуренцию с Telegram callback, перенос
с датой/без даты и устаревшей версией, уведомление и подтверждение инженером.
Миграцию `0047` сначала применять на изолированной PostgreSQL. Перед внедрением
на рабочем стеке отдельно согласовать backup, миграцию, обновление API/WEB/poller
и адрес запуска Mini App у Telegram-бота. Этап 2 не меняет кнопки групп и не
отправляет тестовые сообщения монтажникам.
