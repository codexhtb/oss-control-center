# Ручная проверка OLT NetUP ↔ LibreNMS/BDCOM

Исследование формировало кандидатов OLT по совокупности признаков, но не утверждало пару автоматически. Удалённая таблица содержала закрытую топологию и поэтому не возвращена в Git.

## Процедура подтверждения

Для каждой пары проверялись read-only:

1. уникальность NetUP switch и LibreNMS/BDCOM OLT;
2. одинаковый management IP после корректного преобразования формата;
3. согласованность модели и PON type;
4. дополнительные inventory признаки;
5. отсутствие дубликата ID/IP в обоих источниках;
6. ручное решение владельца с временем и основанием.

Только после этого stable IDs записывались как `manual_verified` в защищённый registry. Имена сохранялись как исторические attributes, но не служили ключом.

## Граница ONU correlation

Подтверждение OLT не подтверждает конкретную ONU. Для ONU требуются утверждённое правило преобразования NetUP port → PON, VLAN и единственная актуальная collector row на этом OLT. Несколько ONU, отсутствующая ONU, неполный NetUP key или конфликтующие service rows дают `CONFLICT/UNKNOWN`.

`present=1` и совпадение исторического snapshot не доказывают текущее физическое подключение. State/optics показываются с source timestamp и quality. Ручная проверка не переписывает данные NetUP, LibreNMS или BDCOM.

## Хранение доказательств

Evidence journal содержит technical IDs, source names, management identity, type, verifier и дату; права не шире `0600`, Git исключён. Перед изменением registry создаётся защищённая копия, проверяется JSON и сохраняются все прежние approved mappings. Новый инженер не должен восстанавливать пары из этого исторического текста.
