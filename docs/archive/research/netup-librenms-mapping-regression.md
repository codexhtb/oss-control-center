# Регрессия сопоставления устройств NetUP ↔ LibreNMS

Исследование установило, что runtime читает соответствия из защищённого `monitoring-mappings.json`, а старый генератор строил только регистрозависимые совпадения имён и мог не переносить вручную утверждённые aliases. Конкретные device IDs, management IP и имена оборудования удалены из Git как закрытая топология; evidence хранится только в защищённом локальном реестре владельца.

## Сохраняемый технический вывод

- Источник истины для approved mapping — защищённый реестр, не сгенерированный diff и не сходство hostname.
- Ключ пары — постоянные `netup_switch_id` и `librenms_device_id`.
- Case-only совпадение допустимо лишь как кандидат. Для отличающихся имён требуется ручное подтверждение по уникальному management IP и дополнительному inventory evidence.
- Повторная генерация должна принимать предыдущий approved registry и сохранять `manual_verified` только после проверки уникальности обеих сторон. Изменение IP, исчезновение ID или дубликат останавливают сборку.
- Совпадение IP само по себе не создаёт новую approved pair.
- Device mapping не создаёт port или ONU mapping. Эти уровни остаются `UNKNOWN/CONFLICT`, пока нет отдельного доказательства.

## Регрессионные проверки

1. Approved alias и case-only pair переживают повторную генерацию.
2. Изменившийся или дублирующийся management IP отклоняет перенос approval.
3. Одна сторона не может участвовать в двух активных mappings.
4. LibreNMS device observation отображается независимо от ONU match.
5. Port остаётся `UNKNOWN`, если отсутствует отдельное правило/запись.
6. Реестр заменяется атомарно, валидируется как JSON и получает защищённый backup; права файла не шире `0600`.

Исторические фактические пары и размеры инвентаря намеренно не возвращены в Git. Подтверждение конкретного устройства выполняется read-only в обоих источниках и фиксируется в защищённом evidence journal.
