## План отдельных логических коммитов

1. **Stage 0 — этот документ:** доказательства актуальности и решения, требующие владельца. Остановка для архитектурного ревью до изменения схемы или публичного контракта.
2. **Security:** R-02, R-03, R-07; проверка production/lab конфигурации, реального access log, заголовков. Изменения без миграции, если схема не затронута.
3. **Lookup lifecycle:** R-01 после утверждения срока хранения; новая Alembic-ревизия и отдельные PostgreSQL интеграционные тесты на временных БД. Рабочую `oss_control` не мигрировать.
4. **Lookup concurrency и repository:** R-04/R-05; тесты медленного/недоступного UTM5 и конкурентной деактивации; измерение количества SQL, времени, диапазонов и сериализованных байтов до/после. Не создавать индекс UTM5 без отдельного EXPLAIN и нагрузочного обоснования.
5. **Контакты и инварианты:** R-06 после решения по API; additive migration, сохранение mock и старых snapshots. R-08 по решению о показе DHCP ranges; R-10 через валидацию writer-пути.
6. **Сквозная приёмка и эксплуатация:** R-09, R-11; unit/contract/lab/integration тесты, документы API/ADR/deployment/runbook и таблица закрытия R-01–R-11. Каждый этап — отдельный локальный коммит. Merge, push и deployment не выполнять.

## Решение A: срок хранения и способ удаления R-01

Нужен **конкретный срок** для lookup без заявки и согласование, начинается ли он с `fetched_at` или `expires_at`. `expires_at` сейчас означает только конец 15-минутного окна создания заявки; автоматически считать его сроком хранения нельзя.

**Вариант A1 (рекомендуется для 1.1):** оставить идентификаторы и API. Новая ревизия вводит строго ограниченную maintenance-операцию: отдельная роль без обычных API-прав удаляет сначала дочерние строки, затем только snapshot старше утверждённого срока и без `tickets`, в одной транзакции; trigger разрешает это исключение только maintenance-роли/процедуре. Snapshot, связанный с заявкой, остаётся полностью immutable. Очистка блокирует родительскую строку, повторно проверяет отсутствие ticket и считает FK последним барьером от гонки. Сохраняется обезличенный audit-факт очистки (ID события, время, число строк, результат; без ЛС/PII). Нужны отдельные credentials и реестр владельца; до их создания — тестовая роль в изолированной БД. Преимущество: не меняет публичный API и существующие ticket snapshots. Риск: узкое исключение в текущем триггере требует строгого security review.

**Вариант A2:** хранить короткий lookup отдельно от immutable ticket snapshot и копировать подтверждённые данные при создании заявки. Удаление временных данных становится обычным жизненным циклом, но меняются схема, конкуренция создания и реализация `lookup_id`; потребуется отдельная миграция/переходный период и больше тестов. Это сильнее разделяет назначение записей, но шире по объёму изменений.

Оба варианта запрещают удалять или переписывать snapshots, на которые ссылаются tickets. Выбор срока и варианта принадлежит владельцу проекта. Не использовать `ALTER TABLE ... DISABLE TRIGGER` в runtime и не давать приложению привилегии обхода.

## Решение B: альтернативные контакты и публичный API R-06

**Вариант B1 (рекомендуется):** сохранить нынешнее `phone` и его `CONFLICT`, добавить необязательное `contacts[]` с исходным типом (`mobile`/`work`/`home`), полным допустимым значением, `source`, `observed_at` и `quality`. Записывать его в новый nullable/JSONB столбец snapshot с `[]` для старых строк. Для конфликтов не выбирать один номер. Это добавочное поле в HTTP JSON, поэтому требуется согласование: строгие клиенты могут отвергать неизвестный ключ, а оператор получит доступ к нескольким персональным контактам.

**Вариант B2:** хранить варианты только внутри snapshot и показывать их отдельным endpoint. Основной ответ не меняется, но операторский сценарий требует дополнительного вызова и отдельного разрешения; сложнее для Web UI. Хранение без показа не решает задачу контакта.

Нужно утвердить, какие роли видят все альтернативы, правила для значений длиннее текущих 50 символов и необходимость маскирования в UI. Нельзя обрезать номер или выбирать «первый» без правила.

## Решение C: DHCP ranges R-08

Рекомендуется не выводить raw DHCP ranges в первой версии Web UI. Оставить структуру в защищённом snapshot для будущего технического интерфейса и отметить, что метка происхождения наследуется от `IpGroupRow.field_meta['dhcp_ranges']` только для набора в целом. Если ranges будут показаны как отдельные технические факты, сначала согласовать элементную provenance и additive API-расширение.

## Критерии следующего ревью

- Владелец утверждает срок хранения, вариант A1/A2, формат контактов B1/B2 и показ DHCP ranges.
- Для R-04 результат lookup при деактивации во время внешнего вызова — отказ без snapshot; никакого PG lock/transaction в период ожидания NetUP.
- Для R-05 зафиксировать baseline и новое число SQL для одинакового синтетического набора и lab-агрегатов без вывода данных; отдельно измерить p95/p99, max rows/ranges/bytes. Лимит возвращает явную ошибку, без усечения.
- Для R-03 тест поднимает настоящий локальный HTTP-сервер, отправляет синтетический запрос и проверяет отсутствие ЛС в stdout/stderr access log.
- Финальный PostgreSQL Docker-прогон использует только временные `oss_test_*` БД; производственную/рабочую `oss_control` не изменять.

**Секреты:** на Stage 0 не создавались и не изменялись; резервное копирование не требуется.
