# NetUPBillingProvider 1.0 — итоговое архитектурное ревью

**Область:** ветка `codex/netup-provider-1.0`, HEAD `b57b5c1`, 13 октября 2026 года. Ревью основано на исходном коде, миграциях `0001`–`0005`, документации Discovery и эксплуатационных документах. В этом ревью UTM5 и PostgreSQL не опрашивались, данные и код не менялись. Результаты лабораторного и PostgreSQL прогонов ниже предоставлены владельцем проекта; планы EXPLAIN взяты из сохранённой Discovery, без повторного измерения.

**Вердикт: READY WITH CONDITIONS.** Разработку Web UI на mock-данных можно продолжать после устранения общих замечаний о журналировании и кешировании ответов. Включать реальный NetUP provider в Web UI и тем более production нельзя до закрытия замечаний о хранении персональных данных, транспортной конфигурации, нагрузке и сквозной проверке. Успешные тесты не подтверждают эти эксплуатационные свойства.

## Что соответствует требованиям

- `BillingProvider.lookup_by_account(str)` остался независимым от UTM5; mock продолжает работать. UTM5 SQL находится в `NetupRepository`, сырые значения — в source DTO, преобразование — в `normalize_netup`, а Ticket Engine читает только PostgreSQL snapshots. Прямых SQL-запросов к UTM5 из Ticket Engine нет (`app/modules/billing/provider.py:83`, `app/modules/billing/netup/repository.py:40`, `app/modules/billing/netup/dto.py:7`, `app/modules/billing/netup/normalizer.py:166`, `app/modules/tickets/service.py:103`). Это сохраняет границу для будущих Network Inventory, LibreNMS, GPON/EPON collectors и SLA: их наблюдения должны храниться отдельно от биллингового снимка.
- Поиск принимает ЛС строкой и отклоняет ведущие нули без молчаливого преобразования. `accounts.id` проверяется по PK, live owner ищется через `users_accounts`, два разных owner дают явную неоднозначность; SQL-параметры передаются драйверу (`repository.py:30-37`, `79-99`). Подтверждение семантики операционного ЛС ограничено сверенным GUI-примером и агрегатами копии (`docs/netup/lookup-by-account.md:3-8,96-109`).
- Услуги привязаны к счёту и `service_links.id`; отдельные строки IP-группы сохраняются по `ip_groups.id` внутри ключа группы. Плоская тройка switch/port/VLAN выдаётся только при одном непротиворечивом полном варианте. `access_type`, ONU ID и техническое состояние остаются `UNKNOWN`; финансы и блокировки не используются как диагностика (`repository.py:132-165,183-257`, `normalizer.py:104-163`, `docs/netup/service-model.md:51-70`).
- Read-only транзакция UTM5 согласует набор SQL-чтений; лимиты на число счетов, услуг, групп и строк прекращают ответ, а не усекают его. Исключения не раскрывают DBAPI-текст в HTTP (`repository.py:19-26,51-75`, `provider.py:23-31`, `app/modules/billing/service.py:50-110`). `NetupConfig` требует TLS CA по умолчанию; лабораторная учётная запись имеет `SELECT, SHOW VIEW`, а production-права пока только спроектированы (`config.py:34-52`, `docs/netup/provider-security.md:3-14`).
- `0005` только добавляет nullable поля и JSONB с `[]`; старые snapshots читаются без преобразования. `0003` запрещает UPDATE/DELETE исторических фактов, FK связывает дочерний снимок с родительским и заявку с выбранным снимком. `create_lookup` делает `flush()` родителя и записывает дочерние строки и аудит в одной транзакции (`app/db/migrations/versions/0003_ticket_engine.py:34-69,245-259`, `0005_netup_group_snapshots.py:19-33`, `app/modules/billing/service.py:111-150`). Заявка проверяет принадлежность выбранной услуги и подключения сохранённому снимку (`app/modules/tickets/service.py:103-146`).
- RBAC централизован: operator/engineer могут читать разрешённые карточки, admin Identity не получает `subscriber.read`; lookup доступен только автору snapshot. Создание требует серверной сессии и CSRF (`app/modules/identity/roles.py:28-53`, `app/api/v1/billing.py:35-73`, `app/modules/billing/service.py:153-157`).
- Сообщены результаты: UTM5 lab — **6 passed**; PostgreSQL 17 — **39 passed, 6 skipped, 0 failed**, включая `0005`, старые snapshots и IP-группы. Это подтверждает проверенные сценарии, но не production TLS, нагрузку и сквозной HTTP-путь NetUP → PostgreSQL → Ticket.

## Замечания

### R-01 — HIGH — срок хранения lookup snapshots противоречит схеме

- **Severity:** HIGH.
- **Файл и строка:** `app/db/migrations/versions/0003_ticket_engine.py:245-259`; `docs/architecture/data-model.md:187`; `app/modules/billing/service.py:111-150`.
- **Проблема:** каждый успешный поиск сохраняет ФИО, контакт, адрес и сетевые сведения. Архитектура обещает удалять snapshots без заявок по политике хранения, но триггер `immutable_subscriber_snapshots` запрещает любой DELETE, включая несвязанные снимки. `expires_at` ограничивает создание заявки, а не срок хранения.
- **Последствие:** при реальном NetUP персональные данные накапливаются бессрочно даже после простого поиска; штатное выполнение утверждённой политики невозможно. Индекс `account_no,fetched_at` помогает поиску, но не решает жизненный цикл.
- **Способ исправления:** утвердить срок хранения и отдельную контролируемую процедуру удаления *только* несвязанных lookup snapshots вместе с дочерними строками и сохранением обезличенного аудита, либо разделить краткоживущий lookup и долговечный ticket snapshot. Проверить FK, конкуренцию с созданием заявки и невозможность удалить связанный снимок. Ранее применённые миграции не редактировать — решение оформить новой миграцией после ревью.
- **До Web UI:** **да для реальных абонентских данных**; mock-only UI можно разрабатывать параллельно.

### R-02 — HIGH — лабораторный plaintext-режим не привязан к среде приложения

- **Severity:** HIGH.
- **Файл и строка:** `app/modules/billing/netup/config.py:34-52,74-95`; `app/api/v1/billing.py:23-29`.
- **Проблема:** `purpose=lab`, `allow_plaintext_lab=true` и private IP позволяют соединение без TLS. Проверка не сравнивает `NETUP_PURPOSE` с `APP_ENV`; production процесс может быть ошибочно сконфигурирован как lab. Документ утверждает, что лабораторное исключение «никогда не является production конфигурацией» (`docs/netup/provider-deployment.md:16-20`), но код этого не гарантирует.
- **Последствие:** ошибка окружения может передать SQL credentials и персональные данные без TLS в production-сегменте.
- **Способ исправления:** запретить lab/plaintext при `APP_ENV=production` на старте процесса; отдельно проверить безопасный режим по умолчанию, тип TLS endpoint и тесты отказа для смешанных флагов. Production read-only grants и реальный TLS handshake проверить до включения.
- **До Web UI:** **да, если UI использует NetUP**.

### R-03 — HIGH — фильтр ЛС попадает в стандартный access log

- **Severity:** HIGH.
- **Файл и строка:** `app/api/v1/tickets.py:155-177`; `Dockerfile:22`; `app/core/logging.py:20-24`.
- **Проблема:** список заявок принимает `account_no` в query string. Uvicorn запускается с access log по умолчанию; установленная версия пишет путь **вместе с query string** (`uvicorn/protocols/http/h11_impl.py:476-482`). При поиске заявки по ЛС технический лог сохранит идентификатор. Собственный JSON formatter не устраняет это сообщение Uvicorn.
- **Последствие:** нарушение требования не выводить персональные идентификаторы в общие технические журналы; утечка расширяет круг доступа и срок хранения ЛС.
- **Способ исправления:** убрать чувствительный параметр из URL либо настроить проверенный redacted access log, не теряя безопасные метрики. Проверить тестом фактический вывод HTTP-сервера и обратного прокси при запросе с синтетическим ЛС.
- **До Web UI:** **да**, включая mock UI, поскольку реальные описания заявок и ЛС могут появиться позже.

### R-04 — HIGH — PostgreSQL-транзакция удерживается во время внешнего SQL-чтения

- **Severity:** HIGH.
- **Файл и строка:** `app/modules/billing/service.py:29-55,111-150`; `app/modules/billing/netup/repository.py:51-75`; `app/db/engine.py:15-25`.
- **Проблема:** `_actor` берёт `FOR UPDATE` на строку пользователя перед вызовом NetUP, а `db.commit()` выполняется только после ответа провайдера и записи snapshot. Внешний lookup может ждать до нескольких таймаутов; всё это время удерживаются PostgreSQL connection и lock. Пул на процесс ограничен 10 соединениями.
- **Последствие:** повторные запросы одного оператора сериализуются; параллельные сотрудники и масштабирование API могут упираться в пул PostgreSQL из-за задержки UTM5. Ошибка NetUP увеличивает время удержания ресурса.
- **Способ исправления:** завершать короткую фазу авторизации до внешнего I/O, затем в новой транзакции повторно проверить активность/право пользователя и атомарно сохранить snapshot с аудитом. Ограничить параллелизм внешних чтений и нагрузочно проверить конкуренцию, деактивацию пользователя и отказ UTM5.
- **До Web UI:** **да, если UI использует NetUP**.

### R-05 — HIGH — N+1 запросы и отсутствие предела сериализованного ответа

- **Severity:** HIGH.
- **Файл и строка:** `app/modules/billing/netup/repository.py:19-26,131-157,183-239`; `app/modules/billing/service.py:94-106`.
- **Проблема:** услуги запрашиваются по каждому счёту, группы — по каждой IP-связке, строки — по каждой группе, а для каждого нового DHCP-пула делаются ещё два запроса. `range_cache` убирает повторы одного пула, но не N+1. Число строк ограничено, но нет общего лимита DHCP-диапазонов или размера JSON: при 2000 строках и до 50 диапазонов на пул один lookup может многократно сериализовать крупный набор. Дедлайн проверяется перед SQL, а не ограничивает размер ответа/обработки после последнего запроса.
- **Последствие:** высокая задержка, перегрузка MariaDB/API/PostgreSQL JSONB и отказ другим операторам при сложном абоненте. Сохранённые EXPLAIN подтверждают индексы отдельных запросов, но не суммарную стоимость одного lookup (`docs/netup/provider-deployment.md:54-63`).
- **Способ исправления:** измерить число запросов, байты ответа и p95/p99 на синтетических предельных случаях; ввести общий предел диапазонов/байтов и явную ошибку; пакетно читать группы/пулы по ограниченному набору ID внутри одного read-only snapshot. Не создавать индекс UTM5 по одному лабораторному EXPLAIN: сначала измерить типовой и худший поиск owner, затем согласовать индекс или официальный read-only интерфейс.
- **До Web UI:** **да, если UI использует NetUP**.

### R-06 — MEDIUM — конфликт контактов скрывает все доступные номера

- **Severity:** MEDIUM.
- **Файл и строка:** `app/modules/billing/netup/normalizer.py:34-41`; `app/modules/billing/provider.py:47-50`; `docs/netup/data-quality.md:42-51`.
- **Проблема:** при нескольких разных телефонах или значении длиннее 50 символов `_phone` возвращает `None` и `CONFLICT`. Исходные номера остаются только в краткоживущем source DTO; в HTTP-карточке и immutable snapshot нет вариантов. Discovery обнаружила 180 live пользователей с несколькими телефонными полями и четыре значения сверх текущего лимита.
- **Последствие:** оператор видит отсутствие контакта там, где в биллинге есть несколько записей; выбор телефона для заявки или будущего Field Dispatch невозможен без нового запроса. Это потеря информации в нормализации, хотя конфликт обозначен честно.
- **Способ исправления:** согласовать политику контактов: массив значений с исходным полем и quality либо утверждённое правило выбора. Не выбирать номер эвристически и не усекать его. Добавить проверку сохранения альтернатив в snapshot.
- **До Web UI:** **да для NetUP-карточки**, поскольку контакт — часть основного сценария оператора.

### R-07 — MEDIUM — ответы с содержимым заявок не везде запрещают кеширование

- **Severity:** MEDIUM.
- **Файл и строка:** `app/api/v1/tickets.py:127-143,155-177,230-244,257-316`; `app/api/v1/billing.py:63-73`.
- **Проблема:** `Cache-Control: no-store` выставляется на карточке lookup и одиночной заявке через `_etag`, но список заявок, комментарии, решения, диагностика и история возвращаются без этого заголовка. Их тела могут содержать ЛС, описание жалобы и персональные сведения.
- **Последствие:** клиентские или промежуточные кеши могут хранить данные дольше ожидаемого; политика зависит от внешней конфигурации прокси и браузера.
- **Способ исправления:** применять единый `no-store` ко всем авторизованным ответам с Service Desk данными и проверить заголовки тестами, включая ошибки и пагинацию.
- **До Web UI:** **да**.

### R-08 — MEDIUM — provenance DHCP-диапазонов есть только на уровне массива

- **Severity:** MEDIUM.
- **Файл и строка:** `app/modules/network/models.py:12-16`; `app/modules/billing/netup/normalizer.py:44-50,72-86`.
- **Проблема:** `IpGroupRow.field_meta['dhcp_ranges']` даёт общую метку массива, но отдельные `range_id`, `first_ip_raw`, `last_ip_raw` не имеют собственного `source/observed_at/quality`. Остальные существенные технические поля строки имеют метаданные по ключу.
- **Последствие:** UI и будущие collectors не смогут отличить качество каждого диапазона или корректно объединить его с отдельным наблюдением. Это не означает, что текущие raw числа неверны; у них недостаточно детальная provenance.
- **Способ исправления:** до отображения диапазонов как технических фактов согласовать метаданные на уровне `DhcpRange` либо явно документировать наследование метки строки. Не декодировать raw IP без подтверждённого правила.
- **До Web UI:** **да, если UI показывает DHCP-диапазоны**; иначе можно отложить.

### R-09 — MEDIUM — нет сквозного NetUP → HTTP → PostgreSQL → Ticket теста

- **Severity:** MEDIUM.
- **Файл и строка:** `tests/test_netup.py:592-707,708-829`; `tests/test_billing.py:155-320`.
- **Проблема:** шесть lab тестов проверяют NetUP provider и сопоставление с SQL; PostgreSQL тест `0005` вставляет синтетические ORM-объекты; HTTP и создание заявки в `test_billing.py` используют mock. Совместная работа NetUP-нормализатора, сериализации `SubscriberCard`, записи PostgreSQL и выбора услуги/подключения в одном сценарии не проверена.
- **Последствие:** тесты могут проходить при несовместимости на границе слоёв, особенно для нескольких счетов/услуг, конфликтных IP-групп и больших вложенных значений.
- **Способ исправления:** добавить сквозной тест с полностью синтетическим `NetUPBillingProvider`/repository и изолированной PostgreSQL БД: lookup через HTTP, чтение immutable snapshot, выбор услуги и подключения, повтор с `client_request_id`, отказ подмены. Лабораторные PII в fixtures и вывод не переносить.
- **До Web UI:** **да, если UI использует NetUP**; mock UI уже имеет отдельные сквозные тесты.

### R-10 — MEDIUM — связь услуги с IP-группой обеспечена приложением, а не схемой

- **Severity:** MEDIUM.
- **Файл и строка:** `app/modules/tickets/models.py:51-58,89-95,147-149`; `app/modules/tickets/service.py:108-146`; `app/db/migrations/versions/0005_netup_group_snapshots.py:27-33`.
- **Проблема:** `services` и `ip_groups` лежат в JSONB, а `connection_snapshots.service_id` — свободная строка. FK проверяет принадлежность подключения snapshot, но PostgreSQL не может проверить, что `service_id` существует в `services[]` и что каждый IP-group относится к нему. Текущий API проверяет выбор, а новые writer-пути должны повторять это правило.
- **Последствие:** будущий импорт, backfill или collector может создать внутренне противоречивый snapshot при обходе сервисного слоя; исторические записи неизменяемы, исправление трудно.
- **Способ исправления:** закрепить инвариант общим валидатором записи и тестами для каждого нового writer-пути; при росте объёма/числа источников рассмотреть отдельные immutable таблицы service/group с FK. Сейчас новую миграцию или индексы не добавлять без измерений.
- **До Web UI:** **нет**, если единственный writer остаётся `create_lookup`; до нового writer-пути — обязательно.

### R-11 — LOW — часть документов описывает состояние до реализации и до финальной проверки

- **Severity:** LOW.
- **Файл и строка:** `docs/netup/integration-plan.md:3-5,29-33`; `docs/netup/lookup-by-account.md:3`; `docs/netup/subscriber-360-mapping.md:1-7,22-28`; `docs/netup/lab-validation.md:31-35`; `docs/netup/provider-migration.md:8-11`.
- **Проблема:** Discovery-документы всё ещё называют адаптер будущим, а `lab-validation.md` утверждает, что `0005` и HTTP/PostgreSQL не проверены; владелец подтвердил успешный PostgreSQL прогон. Migration guide ожидает строго `0004`, хотя проверен и путь с `0003`. Часть формулировок о плоском Connection устарела после `ip_groups[]`.
- **Последствие:** независимый reviewer или дежурный инженер может принять старые ограничения за актуальные и неверно оценить готовность/порядок обновления.
- **Способ исправления:** сохранить Discovery как исторический факт с явной пометкой «до реализации», а эксплуатационные документы обновить подтверждёнными результатами и допустимыми исходными ревизиями. Не переписывать исходные доказательства схемы.
- **До Web UI:** **нет**, но исправить до эксплуатационного включения NetUP.

## Приоритет перед Web UI

1. **Любой Web UI:** закрыть R-03 (ЛС в access log) и R-07 (кеширование авторизованных ответов).
2. **Web UI с реальным NetUP:** дополнительно закрыть R-01, R-02, R-04, R-05, R-06 и R-09. R-08 обязателен, если показываются DHCP-диапазоны. Production read-only grants и TLS endpoint пока не проверены; лабораторные `SELECT, SHOW VIEW` не являются production-моделью доступа.
3. **Можно отложить:** R-10 до появления второго writer-пути, R-11 до эксплуатационного cutover, а также cache Subscriber 360, SLA и корреляцию до появления подтверждённых источников и правил свежести. Отсутствие кеша сейчас сохраняет честное время чтения; добавлять его без TTL и invalidation не следует.

API остаётся синхронным и не хранит состояние NetUP между процессами, поэтому горизонтальное масштабирование возможно технически, но увеличивает одновременные подключения к UTM5 и конкуренцию за PostgreSQL. Для будущей диагностики следует сохранять `source_kind`, `observed_at`, доступность и связь с конкретным service/connection snapshot, не переписывая billing JSON. SLA и корреляцию нельзя выводить из баланса, `is_blocked` или факта существования сервисной связки.
