# Subscriber 360: история финансовых операций (Phase 2)

`GET /api/v1/subscriber-lookups/{lookup_id}/finance` требует действующую сессию,
`subscribers.read` и `subscribers.finance.read`. Запрос разрешён только для NetUP
lookup, созданного тем же сотрудником. В ответе `Cache-Control: no-store`.

Параметры: `start` и `end` — даты со смещением UTC, полуоткрытый интервал
`[start,end)` до 366 суток; `kind=payments|charges|credit`, `page=1..1000`,
`size=1..50`. Периоды интерфейса задаются в часовом поясе браузера и
передаются как UTC instants. Часовой пояс штатного GUI UTM5 пока не подтверждён.

Сводка берётся непосредственно из read-only реплики, не из текущей цены тарифа:

- `cash`: положительные `payment_transactions.payment_absolute`, исключая
  метод Credit `7`, сторно `8`, `is_canceled` и `cancel_id`;
- `credit`: действующие записи метода `7`, отдельно от денежных поступлений;
- `charges`: фактический `discount_transactions_all.discount` для
  `charge_type IN (1,2,3)`; ledger платежей `16/17/18` сюда не входит;
- корректировки `22/23` и отрицательные неопознанные платежи показаны отдельно.

Отменённые и сторнирующие платежи остаются видимыми в истории. Название услуги
читается по текущему `services_data.id`; если связь не найдена, название не
выдумывается. Денежные значения UTM5 хранятся как `DOUBLE`; API округляет их
на границе до копеек с `Decimal`. Валюта сводки берётся только из подтверждённого
поля snapshot; валюта отдельной операции — из `currency_list`.

Запросы параметризованы, используют индексы дат NetUP, ограниченный интервал,
`LIMIT/OFFSET`, timeout 3 секунды и read-only consistent snapshot. Ошибки
источника не превращаются в нулевые суммы. Новых данных в PostgreSQL нет;
история запрашивается только при открытии вкладки «Платежи».
