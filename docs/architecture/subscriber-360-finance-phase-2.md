# Subscriber 360: история финансовых операций (Phase 2)

`GET /api/v1/subscriber-lookups/{lookup_id}/finance` требует действующую сессию,
`subscribers.read` и `subscribers.finance.read`. Запрос разрешён только для NetUP
lookup, созданного тем же сотрудником. В ответе `Cache-Control: no-store`.

Параметры: `start` и `end` — даты со смещением UTC, полуоткрытый интервал
`[start,end)` до 366 суток; `kind=payments|charges|credit`, `page=1..1000`,
`size=1..50`. Периоды интерфейса задаются в часовом поясе браузера и
передаются как UTC instants. Часовой пояс штатного GUI UTM5 пока не подтверждён.

Сводка берётся непосредственно из read-only реплики, не из текущей цены тарифа:

- `cash`: положительные `payment_transactions.payment_absolute`, исключая
  метод Credit `7`, сторно `8`, `is_canceled` и `cancel_id`;
- `credit`: действующие записи метода `7`, отдельно от денежных поступлений;
- `charges`: фактический `discount_transactions_all.discount` для
  `charge_type IN (1,2,3)`; ledger платежей `16/17/18` сюда не входит;
- корректировки `22/23` и отрицательные неопознанные платежи показаны отдельно.

Отменённые и сторнирующие платежи остаются видимыми в истории. Название услуги
читается по текущему `services_data.id`; если связь не найдена, название не
выдумывается. Денежные значения UTM5 хранятся как `DOUBLE`; API округляет их
на границе до копеек с `Decimal`. Валюта сводки берётся только из подтверждённого
поля snapshot; валюта отдельной операции — из `currency_list`.

Запросы параметризованы, используют индексы дат NetUP, ограниченный интервал,
`LIMIT/OFFSET`, timeout 3 секунды и read-only consistent snapshot. Ошибки
источника не превращаются в нулевые суммы. Новых данных в PostgreSQL нет;
история запрашивается только при открытии вкладки «Платежи».

## Phase 3: услуги и тарифы

`GET /api/v1/subscriber-lookups/{lookup_id}/services` требует сессию,
`subscribers.read`, `subscribers.finance.read` и владение NetUP lookup. Ответ
`Cache-Control: no-store` формируется по текущим `service_links` счёта и
абонента с привязкой к `services_data`, `periodic_service_links`,
`periodic_services_data` и `account_tariff_link`. До 50 экземпляров услуг;
превышение лимита или ошибка реплики дают `503`, а не неполный список.
Основной тариф выделяется только при единственной действующей связи типа 3
с подтверждённым совпадением тарифа и счёта. Остальные экземпляры, включая
несколько одноимённых дополнительных услуг, сохраняются отдельно.

`configured_cost` — текущие `periodic_services_data.cost ×
periodic_service_links.cost_coef`, вычисленные через Decimal и округлённые до
копеек на границе API. При отсутствующей или неоднозначной цене возвращается
`null`. `period=null`, поскольку `discount_periods` недоступна для чтения:
длительность расчётного периода и пропорциональное списание не выводятся из
текущей цены. Валюта передаётся только из подтверждённого поля финансового
snapshot. Время действия связи не выдаётся за дату первого подключения.

`GET /api/v1/subscriber-lookups/{lookup_id}/tariff-history` использует те же
права и запрашивается только при раскрытии истории. `EXPLAIN` ограничивает
неиндексированный поиск по `tariffs_history` (порог 50 тысяч оценённых строк),
затем возвращаются до 50 последних записей. Запись хранит название и интервал;
историческая цена и точное событие перехода не восстанавливаются догадками.

`GET /finance?kind=charges&service_link_id=...` ограничивает только список
начислений конкретным `discount_transactions_all.slink_id` внутри текущего ЛС.
Общая финансовая сводка остаётся сводкой по счёту за период; интерфейс явно
обозначает фильтр списка. Для других `kind` фильтр запрещён (`422`). Услуги
читаются при открытии вкладки, история — по запросу; PostgreSQL schema и
workflow заявок не меняются.
