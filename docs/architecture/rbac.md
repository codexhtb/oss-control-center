# RBAC matrix

Утверждённое дополнение Phase 1.4: `operator` и `engineer` имеют одно централизованное право `ticket.create` для всех трёх типов; обе роли ищут абонента по ЛС и читают разрешённый Subscriber Snapshot. Stage 2 реализует HTTP создание `MANUAL`/`INTERNAL`; Web UI последует в Stage 3. Подробности в [плане типов заявок](phase-1.4-ticket-types.md).

Phase 1.2A использует три роли: `operator`, `engineer`, `admin`. Два сетевых инженера OSS имеют одинаковые права. `admin` — техническая роль управления локальными учётными записями, без прав на операции с заявками и без нового маршрута эскалации. Монтажный сектор не получает учётных записей и работает через Telegram с Phase 3. Права задаются централизованной матрицей в `app/modules/identity/roles.py`; сервер проверяет их при каждом защищённом действии.

| Действие | Оператор call-центра | Инженер OSS | Администратор | Монтажный сектор |
| --- | :---: | :---: | :---: | :---: |
| Войти в OSS Control Center | Да | Да | Да | Нет |
| Управлять пользователями и ролями | Нет | Нет | Да | Нет |
| Найти Subscriber 360 по лицевому счёту | Да | Да | Нет | Нет |
| Читать баланс, кредит и признак блокировки счёта в Subscriber 360 | Да | Нет | Нет | Нет |
| Читать историю связанных заявок абонента | Да | Да | Нет | Нет |
| Просмотреть заявки и историю | Да | Да | Нет | Нет |
| Читать ограниченную ленту последних событий заявок | Да | Да | Нет | Нет |
| Создать заявку любого из трёх типов (Phase 1.4) | Да | Да | Нет | Нет |
| Добавить комментарий к открытой заявке | Да | Да | Нет | Нет |
| Начать работу по заявке | Нет | Да | Нет | Нет |
| Назначить активного инженера | Нет | Да | Нет | Нет |

| Ответить в согласованном Telegram чате (Phase 3) | Нет | Нет | Нет | Да |

Чтение заявок обоими ролями ограничено одним организационным контуром; межорганизационная модель и дополнительные роли не вводятся. Закрытая заявка в Phase 1 доступна для чтения, но не для новых комментариев, наблюдений или решений. Сервер проверяет роль и состояние ресурса при каждом запросе, фиксирует разрешённые изменения и отказы доступа в аудите. Интерфейс скрывает недоступные действия, но не заменяет серверную проверку.

Получение Telegram сообщения от монтажника не даёт отправителю роль `engineer` и не разрешает закрытие заявки. Решение и закрытие требуют аутентифицированного действия инженера в OSS Control Center.
