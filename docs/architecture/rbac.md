# RBAC и персональные разрешения

**Phase 5.7:** новое индивидуальное `tickets.callback` разрешает записывать
контрольный звонок и выполнять переходы связанной заявки из `RESOLVED`.
Требуется также чтение заявки; полный обзор очереди требует
`tickets.read.all`. `operator` и `engineer` не получают право обзвона
автоматически; `admin` получает его в preset. Симе нужны
`tickets.read.all`, `tickets.edit.all`, `tickets.assign`, `tickets.callback`,
`tickets.close` для несвязанных задач; `tickets.resolve` ей не назначается.
Без идентификации её настоящей учётной записи гранты не меняются.

Текущий контракт — [Identity, Permissions & Ticket Editing](phase3-identity-ticket-editing.md).
Роль `operator`, `engineer`, `admin` задаёт начальный профиль при создании сотрудника;
после этого авторизация опирается на сохранённые индивидуальные разрешения. Отзыв
права применяется к действующей сессии при следующем запросе. UI скрывает действия,
но сервер независимо проверяет каждое действие и доступ к ресурсу.

**Phase 5.6:** `tickets.resolve` проверяется отдельно от `tickets.edit.all` и
`tickets.edit.own`; одно лишь редактирование заявки не позволяет менять статус
или создавать инженерный вердикт. Обычный инженер может переводить в `RESOLVED`
только назначенную себе заявку `IN_PROGRESS`; admin с индивидуальным правом
может выполнить исключительный переход, который попадёт в историю и аудит.
`tickets.close` остаётся отдельным индивидуальным правом и применяется только
после `RESOLVED` с текущим вердиктом. Выдача этого права сотруднику контрольного
обзвона не добавляет ему `tickets.resolve`. Существующие сохранённые гранты не
изменяются миграцией автоматически.
| Причина передачи монтажникам | `tickets.field_work` | — | Да | Да |
| Subscriber 360 | `subscribers.read` | Да | Да | Да |
| Финансовые поля биллинга | `subscribers.finance.read` | Да | — | Да |
| Чтение/запуск диагностики | `diagnostics.read` / `diagnostics.run` | Да / — | Да / Да | Да / Да |
| Чтение аудита | `audit.read` | — | Да | Да |

В Phase 5.5 `tickets.start` — существующее индивидуально управляемое право на
инженерское взятие/освобождение; оно не следует из `tickets.read.all` или
`tickets.edit.all`. Только активный инженер может применить его к свободной
или собственной активной заявке. `tickets.assign` отдельно разрешает явное
назначение свободной заявки; переназначить занятую может только admin с этим
правом. Список имён активных инженеров доступен также по `tickets.read.all` или `tickets.read.own`
для фильтра реестра, но это не даёт полномочия назначать.

Права чтения и изменения заявки независимы: `tickets.edit.own` не даёт
возможности прочитать чужую заявку. `tickets.read.own` ограничивает видимость
создателем; назначение исполнителя не делает его автором. Для инженерных
действий нужны соответствующее индивидуальное право и видимость заявки.
Закрытая заявка доступна для чтения и неизменна; решение и закрытие остаются
отдельными действиями с workflow `OPEN → IN_PROGRESS → CLOSED`.

При проверке повторных обращений по абоненту `subscribers.read` разрешает
получить только факт существования недоступной активной заявки. Сводка
доступна по `tickets.read.all` или для своей заявки по `tickets.read.own`.
Создание второй связанной заявки при подтверждённой другой проблеме требует
`tickets.create` и причины; это не расширяет права чтения чужой заявки.

Технический `admin` больше не исключён из Service Desk: владелец проекта
утвердил полный доступ по умолчанию. Это не новое подразделение и не маршрут
эскалации. Запрет удаления/деактивации последнего активного администратора
сохранён; нельзя отозвать последний грант `users.manage`. Административные
действия фиксируются в `identity_audit_events` без секретов.

Монтажный сектор не имеет кабинета OSS Control Center. В Telegram T1 право
`tickets.field_work` позволяет инженеру сохранить причину, проверить preview и
отдельно отправить его в фиксированную LAB-группу. Входящие ответы, ручной
fallback и подтверждение выполненных работ остаются следующими этапами;
Telegram не меняет статус и не закрывает заявку.
