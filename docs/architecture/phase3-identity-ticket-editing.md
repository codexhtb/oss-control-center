# Identity, Permissions & Ticket Editing — текущий контракт

Этот утверждённый этап расширяет прежнюю модель RBAC Phase 1.2A. Роль остаётся
внутренним профилем и шаблоном начальных разрешений. Фактический доступ
определяется строками `app_user_permissions`; изменение прав действует для
существующей сессии при следующем запросе. Для ранее созданных пользователей
миграция `0013_identity_permissions` переносит прежние наборы прав. Пароли и
активные сессии при миграции не меняются. Начальный admin получает полный
набор функций портала; его действия проходят те же серверные проверки и аудит.

## Модель

- `app_users.must_change_password`: новый временный пароль ограничивает сессию
  методами `GET /auth/me`, `POST /auth/password`, `POST /auth/logout`. После
  смены отзываются все прежние сессии, требуется повторный вход.
- `app_user_permissions(user_id, permission)` хранит индивидуальные гранты.
  `permissions_customized=false` остаётся только для учётных записей, созданных
  до персонализации вне новой панели; backfill миграции ставит `true`.
- `identity_audit_events.details` хранит только несекретные old/new сведения
  административных изменений. Пароли, хеши, токены и cookie туда не попадают.
  Последний активный admin с `users.manage` защищён транзакционной блокировкой
  и от прямого удаления последнего гранта — отложенным DB trigger.
- Временный пароль генерируется CSPRNG, возвращается однократно только в ответе
  создания/сброса с `Cache-Control: no-store`; PostgreSQL хранит Argon2id.

## Заявки

`PATCH /api/v1/tickets/{id}` принимает только тему и описание, требует CSRF,
точный Origin и `If-Match` с текущей версией. При `tickets.edit.own` автор
может изменить только свою открытую или находящуюся в работе заявку;
`tickets.edit.all` снимает ограничение по автору, но не по статусу. Для
редактирования нужно также право чтения. Billing snapshot, ЛС, тип заявки,
исполнитель, решения и диагностика не входят в payload. Изменение повышает
версию и атомарно создаёт событие `ticket_edited` с before/after только
изменённых полей и запись аудита. Закрытые заявки не редактируются.

`tickets.read.own` ограничивает список, карточку, ленту, историю и связанные
факты заявками, где `created_by` — текущий сотрудник. Остальные действия
проверяют и право операции, и доступ к конкретной заявке. `tickets.read.all`
разрешает весь единый OSS-контур.

## Безопасность и границы

Cookie session, Origin, Host и CSRF продолжают проверяться на backend.
`/users` доступен только с `users.read`, мутации — с `users.manage`, история
управления — с `users.manage` и `audit.read`. `diagnostics.read` контролирует
чтение сохранённых диагностических фактов; `diagnostics.run` — новый опрос.
Неактивный сотрудник не проходит даже по старой cookie. Временные тестовые
пользователи и заявки создаются в `oss_test_*`; dev-база мигрируется после
проверенного backup. Рабочая `oss_control` не мигрируется.
