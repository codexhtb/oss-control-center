# OSS Diagnostics — первая read-only интеграция

## Граница данных

`BillingProvider` и исторические NetUP snapshots описывают **заявленную в биллинге**
связку. LibreNMS и Icinga2 дают наблюдения мониторинга; они не меняют биллинг,
заявку или техническое состояние линии автоматически. Ни баланс, ни наличие
сервисной связки не являются диагностикой. Оптические параметры не выдаются
как факт измерения **абонентской** ONU без доказанного соответствия; значения
кандидатных ONU явно помечаются неподтверждёнными.

Проверка разрешена только активному инженеру с `diagnostics.run`. `POST` требует
cookie-сессию, CSRF и точный Origin. Вызов к мониторингу выполняется после
закрытия PostgreSQL-транзакции; перед записью результата права и версия заявки
проверяются повторно. Оператор и технический admin не получают это право.

## Корреляция

`NetUP service → connection_snapshot → ip_groups[].rows[] → switch_id/port_id`
сохраняет всю кратность. Несколько разных `switch_id` дают `CONFLICT` и запрещают
автоматический выбор устройства. Несколько `port_id` дают `CONFLICT` для
интерфейса. Разные VLAN остаются явным ограничением, а не сворачиваются в
один VLAN. `ifIndex` LibreNMS никогда не принимается равным `port_id` NetUP.

Рабочее соответствие задаётся только проверенным локальным реестром
`netup_switch_id → librenms_device_id / icinga_host`, а порт — отдельной парой
`netup_port_id → librenms_port_id`. Адаптер дополнительно проверяет, что API
вернул ровно указанное устройство и порт принадлежит ему. Неоднозначность,
отсутствие mapping, отсутствие источника или timestamp остаются видимыми
`UNKNOWN`, `CONFLICT`, `UNAVAILABLE` или `STALE`.

Первоначально владелец утвердил сопоставление по **уникальному точному**
`switches.name == devices.sysName`. На текущих выгрузках обнаружено 48 таких
пар из 296 активных именованных коммутаторов NetUP Lab и 81 устройства
LibreNMS. Ранее подсчитанные 71 совпадение получались только при сравнении
без учёта регистра; из них 15 PON OLT отдельно проверены и утверждены
владельцем. Защищённый локальный реестр содержит 48 пар с
`match_basis=unique_exact_sysname` и 15 PON OLT с `manual_verified`;
портовых пар нет. Результат проверки отображает основание сопоставления и
помечает привязку как `STALE`, если исходный NetUP snapshot исторический.
Наблюдение LibreNMS сохраняет собственное время и качество, независимо от
давности NetUP. Реальный read-only API LibreNMS доступен: API root, устройство
и список портов проверены без вывода сетевых идентификаторов. Icinga2 endpoint
и credentials отсутствуют.

## Наблюдения и сохранение

Каждое наблюдение содержит источник, объект, результат, nullable время
измерения, время получения и качество. Если LibreNMS возвращает локальное
время без timezone, оно не трактуется как UTC: измерение остаётся без
доказанного времени. Значение `DOWN` устройства или порта не означает
неисправность конкретной абонентской линии. Icinga `UNREACHABLE` не
приравнивается к `DOWN`.

Проверка Subscriber 360 возвращает preview без записи в заявку. Проверка
связанной заявки сохраняет immutable `diagnostic_checks` с 15-минутным сроком
подтверждения; она **не** создаёт историю заявки. Только отдельный запрос
инженера при `IN_PROGRESS` записывает `AUTOMATED` snapshot, событие истории и
аудит одной транзакцией. Один check подтверждается не более одного раза.
Старые `MANUAL` snapshots остаются без `check_id` и не изменяются. Ревизия
`0012_oss_diagnostics` меняет только новую таблицу и ограничения автоматических
snapshots. Все сохранённые записи заявки и её история остаются бессрочно.

## API

Компактная BDCOM ONU карточка использует отдельный read-only доступ только
к `bdcom_onus` и `bdcom_onu_olts`. До готовности учётной записи ответ
`UNAVAILABLE`. VLAN без утверждённого OLT и полного PON-ключа показывает
только **неподтверждённых кандидатов**. По утверждённому владельцем правилу
GPON `NetUP.port_id−13` и EPON `NetUP.port_id−6` выдаётся
`MATCHED_BY_RULE`, только если OLT утверждён и для OLT+PON+VLAN найдена
ровно одна действующая ONU и только одна сервисная связка абонента с этим
ключом. 15 case-only пар OLT из
[таблицы проверки](../research/olt-manual-verification-candidates.md)
утверждены владельцем и активированы в защищённом dev-реестре.
У GPON поле `mac` таблицы является суррогатом serial, поэтому MAC в карточке
не заполняется из него. Коллекторы сохраняют `state` и `reason` независимо:
после восстановления Online может остаться причина прежнего отключения.
Normalizer выдаёт `reason` только для Offline/Deregistered; интерфейс также
не показывает его для Online. Время опроса ONU и оптики показывается отдельно;
из-за неизвестной зоны и суточного сбора состояние/оптика не называются
свежими без проверки. Эти GET-запросы не создают snapshot и не меняют
заявку. Подробности — в [read-only runbook](../operations/bdcom-onu-readonly.md).

В связанной заявке ONU и мониторинг оборудования находятся в одном разделе
«Диагностика подключения». Для EPON/GPON состояние и оптика ONU видны сразу,
дополнительная проверка оборудования доступна по раскрытию; её результат
сохраняется в историю только отдельным подтверждением инженера.

Phase 4.3 уточняет представление без изменения HTTP-контракта: ONU Rx и OLT Rx
стоят рядом, ONU Tx — третий показатель, без цветовых порогов мощности.
VLAN подключения из подтверждённого match/NetUP snapshot виден рядом с MAC/Serial.
Время опроса и оптики показывается отдельно и без преобразования часового пояса.

Phase 4.4 добавляет быстрые действия в карточке подтверждённой ONU: копирование
OLT, интерфейса, MAC и/или Serial, VLAN и сводки. Для неоднозначных кандидатов
копирование отключено. Сводка формируется в браузере из текущего ответа API,
не сохраняется в историю заявки и не делает выводов о физическом состоянии по
давней оптике. «Обновить данные» повторяет существующий read-only GET к
`bdcom_onus`/`bdcom_onu_olts`; SNMP и коллекторы не запускаются. Время получения
HTTP-ответа отдельно от времени опроса ONU и измерения оптики. В текущем
NetUP-контракте `connection.address` — адрес подключения, а числовой `ip_raw`
не имеет подтверждённой семантики IP-адреса. Поэтому кнопка копирования IP
пока не выводится: нужен подтверждённый нормализованный IP с provenance.
Метка «Ранее даты получения» означает разницу календарных дат источника и
`retrieved_at` не менее двух дней; это не TTL и не вывод о свежести или состоянии
линии. При меньшей разнице актуальность также не утверждается. Одна компактная
пометка сохраняет предупреждение об исторической лабораторной копии NetUP.

Для PON раздел «Проверка OLT в мониторинге» показывает наблюдения устройства,
а технические ID, `interface_match` и ограничения остаются в раскрываемых
сведениях. Неизвестный интерфейс общего мониторинга не отменяет подтверждённую
ONU-корреляцию. Представление Ethernet не меняется.

| Endpoint | Право | Результат |
| --- | --- | --- |
| `POST /api/v1/subscriber-lookups/{lookup_id}/diagnostics/check` | `diagnostics.run`, владелец lookup | Preview для выбранного `connection_snapshot_id` |
| `POST /api/v1/tickets/{ticket_id}/diagnostics/check` | `diagnostics.run`, `If-Match` | Preview и одноразовый `check_id` |
| `POST /api/v1/tickets/{ticket_id}/diagnostics/confirm` | `diagnostics.run`, `If-Match`, `IN_PROGRESS` | `201` immutable snapshot, история, аудит |

Ответы и ошибки помечаются `Cache-Control: no-store`. Query string не содержит
ЛС, персональных данных или токена. В HTTP-транспорт допускается только `GET`,
запрещены redirects и proxy, ответ ограничен 2 МБ, таймаут 1–10 секунд,
TLS проверяется штатно. HTTP разрешается только в `APP_ENV=dev` при явном
`MONITORING_ALLOW_HTTP_DEV=true`; production требует HTTPS.
