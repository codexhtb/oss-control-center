# Внутренние поручения по заявкам — подготовка к внедрению

Состояние: миграция `0043` и первая версия работают в `oss-control-dev`. Упрощение UX разворачивается поверх неё без миграции и без изменения существующих поручений.

## Домен и данные

- Поручение принадлежит одной существующей заявке (`ticket_id`), имеет автора, исполнителя, текст и версию для конкурентных изменений. Заголовок новых поручений автоматически получается из первой строки текста. Поля срока и прежние статусы остаются в схеме исключительно для чтения старых записей.
- `internal_task_events` — последовательность `CREATED`, `MESSAGE`, `COMPLETED`, `NO_ANSWER`, `REOPENED` с автором и временем. Записи не редактируются через API. Повторный `client_request_id` для того же действия не добавляет событие.
- `internal_task_notifications` хранит уведомление получателя о каждом событии и его индивидуальное `read_at`. Счётчик и колокольчик читают PostgreSQL; toast показывается только при появлении нового непрочитанного события в текущей вкладке браузера.
- Основная заявка сохраняет назначение, статус и версию. Создание и действия поручения добавляют факт в существующие историю и аудит заявки в той же транзакции. Они не запускают решение инженера, контрольный обзвон или Telegram workflow.
- Новое поручение переходит только `OPEN → COMPLETED`: исполнитель отправляет обязательный текст ответа и завершает его одним запросом. Старые `MESSAGE`, `NO_ANSWER` и `REOPENED` остаются в истории и доступны для чтения, но новые такие действия больше не принимаются. Для старых поручений со сроком значение сохраняется в PostgreSQL.
- При окончательном удалении заявки её поручения, события и уведомления удаляются вместе с остальными дочерними данными в существующей операции purge. Обычная корзина скрывает поручения удалённой заявки.

## Права и API

`tasks.create` даёт право создать поручение по доступной заявке. `tasks.execute` даёт право исполнителю ответить и завершить его. Engineer и admin получают оба права по умолчанию; operator не получает их автоматически. Администратор может выдать Симе `tasks.execute` через существующий редактор сотрудника. Дополнительно исполнитель должен иметь существующее право чтения самой заявки. Оператор никогда не видит поручения по `INTERNAL`, даже если ему выдали оба новых права. Отключённый сотрудник не может пользоваться API.

Контракт `/api/v1/tasks`:

- `GET /assignees?ticket_id=…`: активные сотрудники с `tasks.execute`, которым видна заявка.
- `POST /`: `{ticket_id, assignee_id, description, client_request_id}`. Сервер формирует заголовок. Старые `title` и `due_at` остаются допустимыми для совместимости API. Требует CSRF и `tasks.create`; ответ 201 с поручением.
- `GET /?scope=assigned|created|all&state=active|completed|overdue|all&ticket_id=…&page=…&size=…`: постраничный список с серверной фильтрацией прав.
- `GET /{id}` и `GET /{id}/events`: детали, сохранённые в заявке ФИО, телефон и ЛС (если есть), история; недоступное поручение возвращает 404. В списке завершённых доступен `latest_answer` для показа ответа прямо в карточке заявки.
- `POST /{id}/events`: `{kind: "COMPLETED", body: "Ответ", client_request_id}` и заголовок `If-Match: "<version>"`; требует CSRF, проверки исполнителя и допустимого перехода. Ответ и завершение сохраняются одной транзакцией. Конфликт версии — 409.
- `GET /notifications` и `POST /notifications/{id}/read`: личные уведомления; запись прочтения требует CSRF.

Все записывающие запросы используют существующую сессию, Origin/CSRF защиту и сохранённые персональные permissions. Получатель не выбирается по клиентскому role или sender ID. Автор и исполнитель не получают через поручение доступ к скрытой заявке.

## Критерии приёмки

1. Инженер выбирает Симу и вводит один текст по доступной заявке; Сима с `tasks.execute` получает колокольчик и запись в «Мне поручили».
2. Сима видит подтверждённые данные абонента, вводит ответ (в том числе «Не дозвонилась») и нажимает «Завершить поручение». Инженер видит ответ в исходной заявке и уведомлении.
3. После завершения все предыдущие сообщения и события остаются доступными для чтения. Повторное открытие нового поручения не допускается.
4. Повторный запрос с тем же `client_request_id` не создаёт дубль. Конкурентная запись с устаревшей версией отклоняется.
5. Оператор без разрешения, посторонний сотрудник, отключённый аккаунт и оператор с `INTERNAL` не получают данные через прямой URL, список, счётчик или уведомления.
6. Статус и назначение заявки, контрольный обзвон, история Field Dispatch и Telegram не изменяются.

## Безопасное внедрение и откат

Для UX-обновления: проверить ревизию `0043`, отсутствие миграций в diff, тесты, собрать и обновить только API/WEB в `oss-control-dev`. Проверить readiness, права и сценарий на разрешённых тестовых аккаунтах. PostgreSQL volume, poller, BDCOM и старый стек не пересоздавать.

При ошибке нового API/WEB: вернуть прежние образы API/WEB, оставив схему `0043` на месте. Downgrade `0043` удаляет все поручения и уведомления, поэтому не применять его при откате UI. Секреты для этой функции не требуются.
