# Внутренние поручения по заявкам

Состояние: базовая схема введена миграцией `0043`. Миграция `0053` добавляет ответы без завершения и устойчивые отложенные напоминания, не изменяя существующие поручения и их историю.

## Домен и данные

- Поручение принадлежит одной существующей заявке (`ticket_id`), имеет автора, исполнителя, текст и версию для конкурентных изменений. Заголовок новых поручений автоматически получается из первой строки текста. Поля срока и прежние статусы остаются в схеме исключительно для чтения старых записей.
- `internal_task_events` — неизменяемая последовательность `CREATED`, `MESSAGE`, `COMPLETED`, исторических `NO_ANSWER`/`REOPENED` и служебного `REMINDER` с автором и временем. Повторный `client_request_id` для того же действия не добавляет событие.
- `internal_task_notifications` хранит уведомление получателя, индивидуальное `read_at` и `available_at`. Обычные события доступны сразу; напоминание становится видимо не раньше заданного времени. Счётчик, колокольчик и оранжевая индикация читают PostgreSQL через существующий polling каждые 15 секунд и после возврата фокуса.
- Основная заявка сохраняет назначение, статус и версию. Создание и действия поручения добавляют факт в существующие историю и аудит заявки в той же транзакции. Они не запускают решение инженера, контрольный обзвон или Telegram workflow.
- Поручение переходит только `OPEN → COMPLETED`. Пока оно открыто, автор и исполнитель могут добавлять `MESSAGE`; каждый ответ уведомляет второго участника и не меняет статус. Завершить поручение с обязательным итоговым текстом может только исполнитель. Исторические `NO_ANSWER` и `REOPENED` доступны для чтения, но новые такие действия не принимаются.
- При создании можно указать одно будущее `reminder_at`. Сервер сразу сохраняет событие и уведомление с будущим `available_at`; отдельный scheduler не нужен, поэтому напоминание переживает перезапуск. Доставка в интерфейс зависит от штатного polling и может произойти с задержкой до следующего цикла.
- При окончательном удалении заявки её поручения, события и уведомления удаляются вместе с остальными дочерними данными в существующей операции purge. Обычная корзина скрывает поручения удалённой заявки.

## Права и API

`tasks.create` даёт право создать поручение по доступной заявке. `tasks.execute` даёт право исполнителю ответить и завершить его. Engineer и admin получают оба права по умолчанию; operator не получает их автоматически. Администратор может выдать Симе `tasks.execute` через существующий редактор сотрудника. Дополнительно исполнитель должен иметь существующее право чтения самой заявки. Оператор никогда не видит поручения по `INTERNAL`, даже если ему выдали оба новых права. Отключённый сотрудник не может пользоваться API.

Контракт `/api/v1/tasks`:

- `GET /assignees?ticket_id=…`: активные сотрудники с `tasks.execute`, которым видна заявка.
- `POST /`: `{ticket_id, assignee_id, description, client_request_id, reminder_at?}`. Сервер формирует заголовок. Напоминание должно содержать timezone и находиться в будущем. Старые `title` и `due_at` остаются допустимыми для совместимости API. Требует CSRF и `tasks.create`; ответ 201 с поручением.
- `GET /?scope=assigned|created|all&state=active|completed|overdue|all&ticket_id=…&page=…&size=…`: постраничный список с серверной фильтрацией прав.
- `GET /{id}` и `GET /{id}/events`: детали, сохранённые в заявке ФИО, телефон и ЛС (если есть), история; недоступное поручение возвращает 404. В списке завершённых доступен `latest_answer` для показа ответа прямо в карточке заявки.
- `POST /{id}/events`: `{kind: "MESSAGE"|"COMPLETED", body: "Ответ", client_request_id}` и заголовок `If-Match: "<version>"`. `MESSAGE` доступно автору и исполнителю, `COMPLETED` — только исполнителю. Событие, аудит и уведомление сохраняются одной транзакцией; конфликт версии возвращает 409.
- `GET /notifications` возвращает только наступившие уведомления. `POST /notifications/{id}/read` и `POST /{id}/read` требуют CSRF и не позволяют заранее отметить будущее напоминание прочитанным.

Все записывающие запросы используют существующую сессию, Origin/CSRF защиту и сохранённые персональные permissions. Получатель не выбирается по клиентскому role или sender ID. Автор и исполнитель не получают через поручение доступ к скрытой заявке.

## Критерии приёмки

1. Инженер выбирает Симу и вводит один текст по доступной заявке; Сима с `tasks.execute` получает колокольчик и запись в «Мне поручили».
2. Сима видит подтверждённые данные абонента, может нажать «Ответить» без смены статуса либо отправить итоговый текст кнопкой «Завершить поручение». Инженер видит ответы в исходной заявке и получает уведомление.
3. После завершения все предыдущие сообщения и события остаются доступными для чтения. Повторное открытие нового поручения не допускается.
4. Повторный запрос с тем же `client_request_id` не создаёт дубль. Конкурентная запись с устаревшей версией отклоняется.
5. Оператор без разрешения, посторонний сотрудник, отключённый аккаунт и оператор с `INTERNAL` не получают данные через прямой URL, список, счётчик или уведомления.
6. Статус и назначение заявки, контрольный обзвон, история Field Dispatch и Telegram не изменяются.

## Безопасное внедрение и откат

Для обновления: проверить текущую ревизию и последовательно применить `0053` после проверенного backup/restore. Затем собрать и обновить только API/WEB в утверждённом Compose-проекте. Проверить readiness, права, ответы, наступившее напоминание и отсутствие изменений статуса заявки. PostgreSQL volume, poller, BDCOM и старый стек не пересоздавать.

При ошибке нового API/WEB вернуть прежние образы API/WEB, оставив схему `0053` на месте: добавленные поля обратно совместимы с прежним чтением. Downgrade `0043` удаляет все поручения и уведомления, поэтому его нельзя применять для отката UI. Downgrade `0053` допустим только после проверки отсутствия созданных напоминаний; иначе он удалит их служебные события. Секреты функции не требуются.

## Индикация новых поручений

Личные notifications остаются единственным источником прочтения. API списка/деталей добавляет `is_unread` при любом доступном непрочитанном событии, включая ответ и наступившее напоминание; inbox возвращает общий `unread_count` независимо от страницы. `new_assignments_count` сохранён в контракте для совместимости. Проверки прав и запрет INTERNAL сохраняются.

При показе поручения UI вызывает защищённый `POST /tasks/{id}/read`; GET не меняет состояние. Прочтение сохраняется в существующем read_at, повторный POST идемпотентен. Колокольчик и меню используют одну существующую polling-query (15 секунд/focus), оранжевый акцент есть только для новых адресованных поручений. После прочтения обновляются inbox и списки. Миграция для индикации не требуется.
