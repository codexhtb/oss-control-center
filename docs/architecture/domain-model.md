# Доменная модель Phase 0

## Сущности

| Сущность | Смысл и данные | Источник / правило |
| --- | --- | --- |
| Абонент | ФИО, телефон | BillingProvider: mock в Phase 1, read-only NetUP с Phase 2; значения могут отсутствовать |
| Лицевой счёт | Ключ поиска абонента оператором | BillingProvider; production формат и правило уникальности подтверждаются в Phase 2 |
| Договор | Договор абонента | BillingProvider; production состав полей подтверждается в Phase 2 |
| Услуга | Услуги абонента | BillingProvider; не выводить техническое состояние из финансовых атрибутов |
| Подключение / сервисная связка | Тип Ethernet, EPON или GPON; доступные сведения об устройстве, порте, VLAN и параметрах подключения | BillingProvider; production кратность и структура связок подтверждаются в Phase 2 |
| Идентификатор ONU | Доступный идентификатор ONU для EPON/GPON | Необязателен; не создаётся для Ethernet и не угадывается при отсутствии в источнике |
| Заявка | Номер, лицевой счёт, ссылка на сохранённый снимок данных абонента и выбранное подключение при наличии, описание проблемы, приоритет, назначенный инженер, статус и версия | Создаётся оператором; PostgreSQL — source of truth |
| Комментарий | Запись участника процесса в заявке | PostgreSQL; автор и время обязательны |
| Решение | Проверенный инженером итог и выполненные действия | PostgreSQL; отдельная запись, необходимая перед закрытием |
| История и аудит | Доменные события заявки и след действий пользователя/системы | PostgreSQL; сохраняются транзакционно с изменениями |
| Диагностический snapshot | Значение или `UNKNOWN`, источник, время и контекст | PostgreSQL; автоматические источники вводятся в Phase 4 |
| Автоматическое диагностическое наблюдение | Проверяемый параметр, значение или UNKNOWN, время, источник, привязка к подключению при наличии | LibreNMS, Icinga или специализированный коллектор |
| Ручная проверка | Зафиксированный инженером результат проверки оборудования, время и автор | Сетевой инженер OSS; хранится отдельно от автоматических наблюдений |
| `FieldWorkHandoff` | Конкретная передача одной заявки монтажному сектору: подготовка сообщения, состояние доставки, состояние работ, ответы | Вводится в Phase 3; обе оси состояния независимы от статуса заявки |
| Внешнее сообщение | Ответ монтажника на исходное сообщение Telegram, добавленный в историю заявки | Отдельно от результата диагностики и решения инженера; текст не управляет закрытием |
| Аудит передачи | Кто и когда подготовил, проверил, отправил или вручную передал сообщение; результат попытки | Доступен по правам; полное содержимое с персональными данными не пишется в общие логи |

Это логическая модель. Физические таблицы и ERD — в [модели данных](data-model.md). Названия полей не являются схемой NetUP. ServiceDesk Plus не входит в TO-BE. Детали передачи — в [модуле field_dispatch](field-dispatch.md).

## `FieldWorkHandoff`

| Группа атрибутов | Логический состав и ограничение |
| --- | --- |
| Идентификация | Внутренний `handoff_id`, обязательный `ticket_id`, инженер-инициатор, время создания. Одна заявка может иметь несколько передач; правила повторной передачи согласуются перед Phase 3. |
| Снимок сообщения | Проверенный инженером набор: ID заявки, ФИО, контакт, адрес, описание. Передаётся минимально необходимое для выезда; источник адреса и правила проверки ещё не определены. |
| Доставка | Утверждённый адресат `chat_id`; после подтверждённой отправки — `message_id` исходного сообщения и время. Пара `chat_id` + `message_id` задаёт связь для ответа. |
| Состояние доставки | Подготовлена, подтверждена инженером, отправлена, ошибка, исход неизвестен либо ручной fallback. Не выражает выполнение работ. |
| Состояние работ | Ожидается отчёт, отчёт получен, отчёт проверен инженером. Не выражает доставку сообщения или закрытие заявки. |
| Ручной fallback | Причина, время, инженер, согласованный способ передачи и подтверждение факта. `chat_id`/`message_id` не заполняются, если бот ничего не отправил. |
| Ответы | Внешние сообщения с `chat_id`, `message_id`, временем, Telegram sender ID при допустимости хранения и ссылкой на `handoff_id`; фиксируются как полученные сообщения, а не проверенный итог работ. |

Для входящего события хранится ключ дедупликации `update_id` в контексте бота. Дополнительно пара `chat_id` + `message_id` защищает историю от повторного импорта одного сообщения. Ответ связывается с передачей только при совпадении разрешённого чата и ссылки ответа на исходный `message_id`; неоднозначные или несвязанные сообщения не прикрепляются к заявке автоматически. Точная политика допустимых отправителей и вложений утверждается перед Phase 3.

## Разделение происхождения данных

| Класс данных | Примеры | Что разрешено заключать |
| --- | --- | --- |
| Биллинг / сервисная связка | ФИО, телефон, договор, услуги, тип подключения, устройство, порт, VLAN, доступный ONU ID | Идентификация и описание подключения; не доказательство его текущей работоспособности |
| Мониторинг | Доступные измерения и состояния из LibreNMS, Icinga и коллекторов | Только наблюдаемое техническое состояние с указанием источника и времени |
| Ручная проверка | Результат проверки оборудования инженером | Зафиксированный вывод инженера с временем и автором |
| Внешнее сообщение монтажника | Ответ в Telegram о выполненной работе | Сообщение третьей стороны, ожидающее проверки инженером; само по себе не является решением или основанием для закрытия |

Финансовые сведения, если они присутствуют в BillingProvider, хранятся и показываются отдельно от технических наблюдений. Они не меняют технический статус подключения автоматически. Снимок ответа mock/NetUP хранится в PostgreSQL для воспроизводимости заявки, но не объявляется первичным источником актуальных данных биллинга.

## Правила достоверности и UNKNOWN

- Каждое диагностическое наблюдение содержит источник, время получения и связь с заявкой; связь с конкретным подключением добавляется только при подтверждённом сопоставлении.
- `UNKNOWN` означает, что достоверного значения нет: источник недоступен, не предоставляет параметр либо подключение нельзя надёжно сопоставить с записью мониторинга. Это не равно `DOWN`, неисправности или отсутствию услуги.
- Отсутствующие устройство, порт, VLAN или ONU ID показываются как неизвестные/недоступные поля; значения не выводятся из косвенных признаков.
- Устаревшие или противоречивые данные помечаются отдельно; новая выборка не должна без следа перезаписывать исходные сведения заявки и результаты ручной проверки.
- Автоматические данные и ручной вывод инженера хранятся раздельно. Результат ручной проверки не маскируется под данные мониторинга.
- Если в сохранённом снимке несколько подключений, оператор явно выбирает одно при создании заявки. Все услуги сохраняются в снимке; сопоставление конкретной услуги с подключением не выводится из предположений и будет уточнено при согласовании NetUP.

## Инварианты

1. Заявка связана с лицевым счётом, указанным при поиске, и описанием жалобы.
2. Карточка подключения отображает только полученные и достоверно сопоставленные данные.
3. Тип подключения определяется данными источника; ONU не является обязательным атрибутом.
4. Результат диагностики и решение сохраняются в заявке с указанием автора/источника и времени.
5. Передача в монтажный сектор не подменяет результат диагностики и не происходит автоматически по `UNKNOWN`.
6. Каждая подтверждённая ботом отправка `FieldWorkHandoff` имеет `ticket_id`, `chat_id` и `message_id`; неопределённый исход отправки не помечается как успешный.
7. Ответ монтажника не изменяет решение и не закрывает заявку без действия инженера OSS, включая ответ «Готово».
8. PostgreSQL — единственный source of truth для заявок, комментариев, решений, истории, аудита и диагностических snapshots; ServiceDesk Plus не синхронизируется.
9. Статус заявки, состояние доставки и состояние работ меняются независимо; переходы между ними не выводятся автоматически из текста сообщения.
