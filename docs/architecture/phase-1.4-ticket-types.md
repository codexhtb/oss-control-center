# Phase 1.4 — три типа создания заявок

Статус: архитектура утверждена. Stage 1 ввела централизованное право создания для инженера, миграцию `0008_ticket_types`, ORM и безопасное чтение заявок без snapshot. Stage 2 вводит HTTP создание `MANUAL`/`INTERNAL` через общий Ticket Engine; Web UI остаётся для Stage 3. Этот документ дополняет исторические контракты Phase 1.2B/1.3, где каждая заявка создавалась из Subscriber 360.

## Доменная модель

| Тип | Основание создания | Данные абонента | Минимальный ввод создателя |
| --- | --- | --- | --- |
| `SUBSCRIBER_LINKED` | Подтверждённый `lookup_id` и immutable Subscriber Snapshot | ЛС, услуга и подключение только из snapshot; прежние проверки кратности сохраняются | Описание обращения; выбор услуги/подключения только при неоднозначности |
| `MANUAL` | Обращение, которое нельзя или не требуется связать с NetUP | Snapshot и подтверждённый ЛС отсутствуют; сообщённые человеком реквизиты, если добавлены позднее, должны иметь происхождение `MANUAL` и не считаться проверенным биллингом | Описание обращения |
| `INTERNAL` | Внутренняя задача OSS без абонента | Нет snapshot, ЛС, услуги или подключения | Описание задачи |

`ticket_type` задаётся при создании и после этого не меняется. У всех типов одна сущность `Ticket`, номер, приоритет (по умолчанию `NORMAL`), создатель, исполнитель, версия и общий жизненный цикл `OPEN → IN_PROGRESS → CLOSED`. Используются те же таблицы комментариев, версий решения, истории и аудита. Закрывает только инженер OSS после фиксации решения. Запрос выездных работ остаётся отдельным событием, а состояния будущего `FieldWorkHandoff` независимы от статуса заявки. Категория или шаблон не являются условием создания и не создают новый workflow.

Перед Stage 3B ревизия `0009_ticket_subject_feed` добавляет для всех типов необязательную тему `subject` (до 160 символов). Старые заявки сохраняют `NULL`; старые клиенты могут не передавать поле. Тема учитывается при проверке `client_request_id`. Новый Web UI предлагает ввод темы свободным текстом. Та же ревизия индексирует существующую историю для ограниченной ленты Dashboard; отдельной таблицы событий нет.

Если для передачи монтажникам у manual/internal заявки нет контакта или адреса, инженер должен явно заполнить и проверить эти данные в будущем `field_dispatch`; система не берёт их из несуществующего Subscriber Snapshot и не отправляет выдуманные значения.

Биллинг не обязателен для `MANUAL` и `INTERNAL`. Неизвестный технический параметр остаётся `UNKNOWN`; отсутствие snapshot не означает ни отсутствие услуги, ни неисправность линии. Ни оператор, ни инженер не должны подделывать NetUP snapshot для ручной заявки. История, комментарии, решения, аудит и диагностические записи, относящиеся к **любой** созданной заявке, хранятся бессрочно. Существующее правило очистки через 24 часа касается только lookup snapshots **без** заявки.

## План схемы и миграции

Stage 1 добавляет **новую** Alembic-ревизию `0008_ticket_types` после `0007_contacts`; `0001`–`0007` не редактируются. Ревизия:

1. Добавить `tickets.ticket_type` с допустимыми значениями трёх типов, проставить всем существующим заявкам `SUBSCRIBER_LINKED`, затем запретить `NULL`. Ограничить смену типа после создания на уровне записи, согласованно с остальными immutable-фактами.
2. Делает `tickets.subscriber_snapshot_id` и `tickets.account_no` nullable. Сохраняет FK на snapshot, уникальность `(created_by, client_request_id)`, FK выбранного подключения к его snapshot и индексы старых заявок. `CHECK` требует snapshot и подтверждённый ЛС для `SUBSCRIBER_LINKED`, запрещает их, услугу и подключение для `MANUAL`/`INTERNAL`. Дополнительный составной FK подтверждает равенство ЛС номеру счёта в snapshot. Если понадобится хранить сообщённый вручную ЛС, потребуется **отдельное** необязательное поле с явным происхождением.
3. Развязывает `diagnostic_snapshots` от обязательного subscriber snapshot для заявок без абонента. Прямой FK `diagnostic_snapshots.ticket_id → tickets.id` добавляется **до** ослабления nullable-ограничения: старый составной FK с `NULL` уже не гарантировал бы наличие заявки. `CHECK` и триггер требуют соответствия snapshot заявке и диагностического подключения выбранному подключению заявки; у записи без snapshot запрещён `connection_snapshot_id`. Существующие диагностические записи не переписываются.
4. Проверить влияние nullable ЛС на фильтр и индекс списка, а также на `lookup_cleanup`: только linked ticket защищает использованный snapshot от очистки. Не удалять старые snapshots и историю; не создавать синтетические snapshots для новых типов.

Отдельные таблицы `manual_tickets` или `internal_tickets` не нужны: общие факты остаются привязанными к `tickets.id`. Миграция выполняется и проверяется только на изолированных PostgreSQL базах до разрешения deployment.

## Проект API и совместимость

Сохранить `POST /api/v1/tickets`. Добавить типизированный вариант запроса с дискриминатором `ticket_type`. Для **старых клиентов**, не передающих дискриминатор, трактовать запрос с прежним `lookup_id` как `SUBSCRIBER_LINKED`; не менять семантику проверки срока lookup, автора, услуги и подключения. Новый клиент передаёт тип явно. Для `MANUAL` и `INTERNAL`: обязательны только `description` и `client_request_id`, опционален `priority`; `lookup_id`, `selected_service_id`, `connection_snapshot_id` и подтверждённый `account_no` отвергаются, а не игнорируются. Строгая Pydantic-валидация ограничивает размер текста и запрещает лишние поля.

В ответах `TicketView`/`TicketDetail` добавить `ticket_type`; `subscriber_snapshot_id`, `account_no` и `subscriber` сделать nullable для двух новых типов. Существующие linked ответы сохраняют прежние значения и форму вложенной карточки. Список допускает фильтр по типу; текущие фильтры, пагинация и сортировка сохраняются. `GET /tickets/{id}` для manual/internal возвращает `subscriber: null`, `selected_connection: null`, `technical_state: UNKNOWN`. Запросы назначения, комментариев, истории, решения и закрытия применяют одинаковые правила ко всем типам. У ручной диагностики нет обязательного `connection_snapshot_id`; при его наличии сервер проверяет принадлежность linked snapshot. При конфликте `client_request_id` проверяется тип и все поля запроса; повтор идентичного запроса возвращает исходную заявку, включая старую форму linked запроса.

API не принимает произвольный JSON как «подтверждённый snapshot». Клиентский `ticket_type` не расширяет права: все варианты проверяются по одной серверной permission matrix, с проверкой CSRF/Origin и `Cache-Control: no-store` для приватных ответов.

## RBAC и Web UI

| Операция | Оператор | Инженер OSS | `admin` |
| --- | --- | --- | --- |
| Создать любой из трёх типов | Да | Да | Нет |
| Найти абонента по ЛС и прочитать разрешённый Subscriber Snapshot | Да | Да | Нет |
| Читать заявку и историю в разрешённом контуре | Да | Да | Нет |
| Добавить комментарий к открытой заявке | Да | Да | Нет |
| Назначить инженера, начать работу, записать диагностику/решение, закрыть | Нет | Да | Нет |

Разрешённый контур остаётся текущим единым контуром Phase 1; новые подразделения, роли и маршруты не вводятся. Одно централизованное право `ticket.create` предоставляется оператору и инженеру для всех трёх типов. Обе роли имеют необходимые права на NetUP lookup и чтение разрешённого Subscriber Snapshot для `SUBSCRIBER_LINKED`; авторство и срок lookup проверяются для обеих ролей одинаково. Инженер сохраняет свои права на назначение, диагностику, решение и закрытие, оператор их не получает. Технический `admin` не получает доступа к заявкам или абонентским данным. Frontend предлагает три понятных варианта создания. Для subscriber-linked сначала поиск ЛС и выбор связки; для manual/internal простая форма с описанием и необязательным приоритетом. `client_request_id` может создавать сам интерфейс. Шаблоны и категории могут подставлять текст и подсказки, но не требуют выбора, не скрывают свободное создание и не меняют RBAC/workflow. Персональные данные не попадут в URL/query logs или общий аудит.

## Порядок реализации

1. **Stage 1 — backend foundation:** централизованное право `ticket.create` инженеру, сохранение `subscriber.read` для обеих ролей, миграция `0008`, nullable ORM/response и чтение карточки без Subscriber Snapshot. На этом этапе HTTP `POST /tickets` требовал `lookup_id`.
2. **Stage 2 — Ticket Engine API:** строгая request-схема и создание manual/internal в Ticket Engine с общей транзакцией, idempotency, history/audit, блокировками и версией. Безусловное предположение о Subscriber Snapshot осталось только внутри linked-пути; replay различает типы.
3. Stage 2 добавляет фильтр `ticket_type` и применяет общие writer/read пути ко всем типам; прежний linked запрос без дискриминатора остаётся совместимым.
4. Добавить простые формы Web UI и подсказки; не создавать десятки обязательных полей и не требовать NetUP для manual/internal.
5. Выполнить приёмку на временных PostgreSQL БД, Ruff и полный pytest, затем отдельное UI и security ревью перед deployment.

## Обязательные проверки

- Миграция текущего head с существующими linked заявками, комментариями, решениями и диагностикой сохраняет все строки и ссылки; чистая база до head также проходит. Старый HTTP запрос и MockBillingProvider сохраняют поведение.
- Создание каждого типа, чтение списка и detail, фильтры, назначение, комментарий, история, начало, решение и закрытие проходят один общий workflow; `admin` и неаутентифицированный клиент не получают доступа.
- И оператор, и инженер создают каждый тип; для `SUBSCRIBER_LINKED` обе роли выполняют lookup и читают разрешённый snapshot. Оператор не может назначать исполнителя, вести диагностику, фиксировать решение или закрывать; `admin` не видит заявку или Subscriber 360.
- Manual/internal создаются при недоступном NetUP, без `lookup_id` и ЛС. Они не получают выдуманный snapshot, абонента, услугу, подключение или технический диагноз. Некорректная смесь полей разных типов отвергается.
- Повтор одинакового `client_request_id` не создаёт дубль; другая нагрузка с тем же ID даёт конфликт. Проверить конкурентные запросы, откат атомарной записи и `If-Match` для всех типов.
- Прямой INSERT не может создать диагностическую запись без существующей заявки или связать её с чужим snapshot/подключением. Очистка lookup удаляет только неиспользованные snapshots и не затрагивает связанные старые заявки.
- После перезапуска все три типа, решения и история читаются из PostgreSQL; тесты не удаляют созданные заявки и не сокращают бессрочный срок хранения их истории.

Stage 2 не вводит Web UI. Миграция рабочей БД, merge, push и deployment выполняются только по отдельному разрешению.
