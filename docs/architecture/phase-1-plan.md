# Phase 1 implementation plan — mock-based MVP

Цель: работающая самостоятельная Service Desk система с PostgreSQL, RBAC и Subscriber 360 на mock BillingProvider. Отсутствие production API NetUP не блокирует ни один шаг Phase 1. Этот документ описывает следующие работы; в Phase 0 приложение и зависимости не создаются.

Phase 1.1 выполняет только foundation: модульный каркас backend, Compose, соединение с PostgreSQL, базовую миграцию и health endpoints. Service Desk таблицы и бизнес-операции из шагов ниже остаются для следующего шага Phase 1.

## Порядок работ

1. **Основа проекта.** Выбрать серверный и клиентский стек при начале реализации; закрепить версионированные миграции PostgreSQL, конфигурацию окружений, безопасное хранение локальных учётных данных и единый формат ошибок API. Не добавлять адаптеры реальных внешних систем.
2. **Данные и транзакции.** Реализовать таблицы Phase 1 из [data model](data-model.md): пользователи, billing snapshots, подключения, заявки, комментарии, решения, диагностические snapshots, история и аудит. Закрепить внешние ключи, версии заявок, уникальность `client_request_id` и атомарную запись истории/аудита.
3. **Аутентификация и RBAC.** Предварительно создать локальные учётные записи оператора и двух инженеров OSS; защищать сессии, CSRF и каждый API метод по [матрице прав](rbac.md). Процедура создания/отключения учётных записей находится вне продуктового кабинета.
4. **BillingProvider и Subscriber 360.** Реализовать внутренний интерфейс из [API contracts](api-contracts.md) и детерминированный mock с только синтетическими данными. Сценарии mock: Ethernet, EPON, GPON, несколько подключений, неполные поля, ненайденный счёт и недоступность провайдера. Маркировать данные `MOCK`; не имитировать NetUP API или реальные сетевые идентификаторы.
5. **Service Desk API.** Поиск, создание заявки из сохранённого snapshot, список/карточка, комментарии, ручное диагностическое наблюдение, версия решения, начало работы и закрытие инженером. Реализовать серверные проверки инвариантов и идемпотентность создания.
6. **Интерфейс оператора и инженера.** Оператор ищет лицевой счёт, видит источник данных, явно выбирает подключение при неоднозначности и создаёт заявку без повторного ввода ФИО/телефона. Инженер видит карточку, добавляет ручные наблюдения, решение и закрывает заявку. Отсутствующие технические сведения обозначаются `UNKNOWN`.
7. **Проверка и выпуск MVP.** Выполнить проверки из [acceptance criteria](acceptance-and-testing.md), проверить миграцию на чистой БД, восстановление после перезапуска, журналирование без PII/секретов и запрет доступа между ролями. Зафиксировать ограничения Phase 1 в пользовательской документации.

## Границы Phase 1

В Phase 1 нет реального NetUP, Telegram Bot API, автоматических данных LibreNMS/Icinga/BDCOM, корреляции аварий и синхронизации с ServiceDesk Plus. При необходимости выезда инженер пользуется ручным процессом миграционного периода и фиксирует итог в OSS заявке; автоматический `FieldWorkHandoff` вводится в Phase 3.

## Результат этапа

Реализация Phase 1 принимается, когда два инженера OSS и оператор могут пройти путь от mock-поиска до закрытой заявки, а после перезапуска все заявки, комментарии, решения, история, аудит и snapshots остаются в PostgreSQL. Ни один вызов production NetUP не нужен для этого результата.
