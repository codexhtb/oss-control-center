# Phase 1.4 Stage 3 — Web UI

## Этапы

| Этап | Объём | Критерий промежуточной приёмки |
| --- | --- | --- |
| 3A Foundation | React + TypeScript strict, Vite, React Router, TanStack Query, сессионный HTTP-клиент, CSRF, локальный proxy, layout и базовые компоненты | Build, typecheck, unit tests, локальный HTTP smoke; без чтения/записи рабочих заявок |
| 3B ServiceDesk | Список, фильтры, создание трёх типов, карточка, комментарии, назначение, статусы, диагностика, решения и закрытие | Полный workflow обеих ролей на временных `oss_test_*` базах, конфликт `If-Match`, ошибки и RBAC |
| 3C Subscriber 360 | Поиск по ЛС, контакты, услуги, подключения, несколько IP-групп, качество и происхождение данных, переход к linked заявке | Контрактные тесты на mock и синтетическом NetUP DTO; `UNKNOWN`/`CONFLICT`/`STALE` без догадок |
| 3D Stabilization | E2E, доступность, адаптивность, безопасность и инструкция развёртывания | Отдельное UI/security ревью перед deployment |

## Проверка текущего backend-контракта

- Авторизация: `POST /api/v1/auth/login`, `GET /api/v1/auth/me`, `POST /api/v1/auth/logout`; cookie-сессия HttpOnly, CSRF cookie и заголовок, точная проверка `Origin` и `Host`. В браузере не хранится токен сессии.
- Роль и полномочия берутся из `/auth/me`; UI скрывает недоступные действия, а backend проверяет их повторно. Технический `admin` не получает экран заявок.
- `GET /tickets` возвращает страницу и `total`, фильтры по статусу, приоритету, типу, номеру, исполнителю, `unassigned` и ЛС. Для Dashboard доступен `GET /tickets/events/recent` с ограниченной страницей метаданных из истории; без текста `event_data`.
- `POST /tickets` поддерживает `SUBSCRIBER_LINKED`, `MANUAL`, `INTERNAL` и необязательный `subject` до 160 символов для любого типа. Новые формы Stage 3B дают ввод темы; старые заявки могут иметь `subject=null`.
- `GET /tickets/assignable-engineers` даёт инженеру список активных исполнителей с `id` и `display_name`; оператору и admin этот список не выдаётся. UI не требует ручного ввода ID.
- У Subscriber 360 есть immutable lookup, источники и качество полей, множественные услуги, подключения и IP-группы. Сырые DHCP ranges в первой версии UI не показываются.

## Реализация Stage 3B

- Реестр читает `GET /tickets` с серверной пагинацией и фильтрами по статусу, типу, приоритету, исполнителю и `unassigned`. Инженер получает имена исполнителей через разрешённый ему `GET /tickets/assignable-engineers`; оператору API этот список не выдаёт, поэтому для назначенных заявок он видит сокращённый ID.
- Форма создаёт `MANUAL`, `INTERNAL` и `SUBSCRIBER_LINKED` через настоящий HTTP. Для linked она сначала создаёт immutable lookup по ЛС, показывает источник и время, требует явный выбор при нескольких услугах или подключениях и передаёт серверу только `lookup_id` и выбранные ID. Снимок формирует backend. Ключ `client_request_id` остаётся тем же при повторе неизменённого запроса и меняется после правки формы.
- Карточка читает сохранённую заявку, отдельные страницы комментариев, диагностики, решений и истории. Изменения прав и переходов проверяет сервер. Для назначения, начала работы, запроса выездных работ и закрытия UI передаёт `If-Match`; конфликт `409` вызывает обновление карточки и требует повторного решения пользователя.
- Dashboard использует только `GET /tickets`, `/tickets/events/recent` и health API. Admin не запрашивает сведения ServiceDesk. Ни один показатель не вычисляется из вымышленных значений.
- Stage 3B не реализует отдельный полный экран Subscriber 360 с деталями контактов, provenance и IP-групп: это Stage 3C. Значения `UNKNOWN` не трактуются как техническая неисправность. UI не обращается к MariaDB/PostgreSQL напрямую и не содержит реквизитов подключения.
