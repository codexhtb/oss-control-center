# Общий чат сотрудников (Phase 1)

## Домен и данные

Чат независим от Service Desk и Telegram. PostgreSQL хранит комнаты (`chat_rooms`),
сообщения (`chat_messages`) и индивидуальные курсоры чтения (`chat_reads`). Миграция
`0029_staff_chat` создаёт одну комнату `staff`; `room_id` и `kind` позволяют позже
добавить личные диалоги с отдельной моделью участия. Все активные учётные записи
автоматически имеют доступ к общей комнате; отключённые аккаунты не имеют доступа.
Имя отправителя сохраняется как снимок на момент отправки. Тело сообщения ограничено
2000 символами. Сообщения не меняют заявку или её историю. Миграция
`0030_chat_moderation` добавляет журнал событий `chat_events` и поля удаления
сообщения. При удалении тело очищается, запись сохраняет ID для идемпотентности,
а событие и ID сообщения заносятся в аудит без текста.

## API и доставка

Все маршруты ниже требуют действующей сессии активного сотрудника. Записи требуют
Origin и CSRF из существующего механизма авторизации.

- `GET /api/v1/chat/summary` → `latest_id`, `latest_event_id`, `last_read_id`, `unread_count`.
  Собственные сообщения не входят в число непрочитанных.
- `GET /api/v1/chat/messages?before=<id>&limit=40` → `items` в порядке ID по
  возрастанию и `next_before` для следующей страницы. `before` — исключающий.
- `POST /api/v1/chat/messages` с `client_id: UUID`, `body: string` → сообщение,
  `201` для нового, `200` для идемпотентного повтора; повтор ID с другим текстом
  даёт `409`. Отправитель определяется только из сессии. Лимит — 12 новых
  сообщений за минуту на отправителя, превышение даёт `429`.
- `POST /api/v1/chat/read` с `through_id` → обновлённый summary. Курсор
  монотонен; значение впереди последнего сообщения даёт `422`.
- `DELETE /api/v1/chat/messages/<id>` → `204`. Требуются роль администратора,
  сохранённое разрешение `chat.messages.delete`, активная сессия, Origin и CSRF.
  Повторный запрос возвращает `204` без нового события. Удалённые сообщения
  отсутствуют в истории и счётчике непрочитанных.
- `GET /api/v1/chat/events?after=<id>` → SSE `message` или `delete` с ID события.
  При переподключении браузер отправляет `Last-Event-ID`; сервер отдаёт
  события строго после него, пачками по 100, и регулярно перепроверяет
  сессию и активность пользователя. Клиент также сверяет summary по таймеру
  и при возвращении на вкладку.

Отправка и удаление сериализованы транзакционной блокировкой PostgreSQL: порядок
ID событий совпадает с порядком фиксации, поэтому SSE-курсор не пропускает
конкурентные изменения. Чтение индивидуально и не удаляет историю.

## Acceptance

Оператор, инженер и администратор видят одну историю. Каждый может отправить
сообщение; другой получает его без перезагрузки. После переподключения клиент
получает пропущенные ID без дублей. Повтор `client_id` не создаёт вторую запись.
Старые страницы и курсоры чтения переживают перезапуск. Отключённый сотрудник
не может читать, отправлять или продолжать SSE. CSRF, лимит длины и частоты
проверяются сервером. На мобильном экране редактор остаётся доступен, а
добавление ранней страницы не смещает текущую позицию чтения.
Администратор может удалить своё или чужое сообщение; оператор и инженер не
могут. После удаления текст исчезает у подключённых клиентов, не возвращается
после переподключения и не учитывается как непрочитанный. Повторное удаление
не создаёт дубль события, а повторная отправка с прежним `client_id` отклоняется.
