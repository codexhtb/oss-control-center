# Удаление заявок — ревизия 0014

PostgreSQL остаётся источником истины. Обычное удаление является обратимым: `tickets.deleted_at`, `deleted_by` и необязательная `delete_reason` меняются вместе с версией, событием `ticket_deleted` и аудитом в одной транзакции. При восстановлении причина сохраняется в защищённой истории события, а поля удаления заявки очищаются. Комментарии, решения, диагностика и исторические Subscriber Snapshots сохраняются. В обычном списке, ленте, поиске по абоненту и карточке удалённая заявка недоступна. Корзина показывает удалённые заявки пользователям с `tickets.read.all` и `tickets.restore` либо `tickets.purge`.

`tickets.delete.own` разрешает удаление только при совпадении `created_by`, `tickets.delete.all` — любой видимой заявки. `tickets.restore` возвращает заявку с сохранённой историей, `tickets.purge` разрешает окончательное удаление после soft delete. Для просмотра корзины и выполнения восстановления/purge требуется также `tickets.read.all`. Администраторы получают четыре права при миграции; другим сотрудникам их можно выдавать индивидуально. Все операции требуют активной сессии, CSRF, допустимого Origin и актуального `If-Match`; БД блокирует строки заявки и пользователя перед изменением. Номер заявки подтверждается повторно перед purge. UI показывает номер и тему до удаления, а для purge требует ввод номера и второе подтверждение.

API: `DELETE /api/v1/tickets/{id}` с необязательным JSON `reason` и `If-Match`; `GET /api/v1/tickets/trash?page=&size=`; `POST /api/v1/tickets/{id}/restore` с `If-Match`; `DELETE /api/v1/tickets/{id}/purge` с `If-Match` и JSON `confirm_number`. Старые маршруты создания и чтения не меняются. Повтор с прежним `client_request_id` удалённой заявки возвращает `409`, не создаёт дубль.

**Явное исключение из бессрочного хранения:** уполномоченный пользователь может необратимо удалить содержимое конкретной soft-deleted заявки. Purge удаляет её дочерние записи в явном порядке с учётом FK, без каскадов; unrelated Subscriber/Connection Snapshots не удаляются. Триггеры immutable допускают DELETE только в одной транзакции с локальным контекстом выбранной заявки и активного пользователя с `tickets.purge`. Остаётся `ticket_purge_audit`: UUID и номер заявки, UUID исполнителя и время, без описания, ФИО, ЛС и причины. Запись immutable. Резервные копии могут содержать ранее удалённые данные до окончания собственного срока хранения.

Приёмка: миграция `0013 → 0014` сохраняет все существующие записи; прямой SQL DELETE без контекста блокируется; soft delete/restore сохраняют дочерние записи; purge удаляет только одну подтверждённую заявку; неверный номер, устаревшая версия, чужая заявка и отсутствие CSRF/Origin/прав отклоняются; обычные списки/лента не показывают корзину. Тесты выполняются только в `oss_test_*`, браузерные удаления — только по специально созданным тестовым заявкам.
