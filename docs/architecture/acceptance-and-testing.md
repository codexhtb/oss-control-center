# Acceptance criteria и стратегия тестирования

## Удаление заявок (`0014`)

- Upgrade `0013 → 0014` сохраняет существующие заявки, выдает новые права admin и не удаляет историю.
- `delete.own` не удаляет чужую заявку, `delete.all` может удалить видимую заявку; без прав, CSRF, Origin или актуального `If-Match` изменение отклоняется.
- Soft delete скрывает заявку из списка, ленты, поиска по абоненту и карточки; корзина показывает её уполномоченному пользователю. Restore сохраняет комментарии, историю, решения и диагностику.
- Purge требует soft delete, `tickets.purge`, совпадающий номер и актуальную версию; удаляет дочерние записи без каскада и оставляет только минимальный immutable audit. Прямой SQL DELETE без транзакционного контекста запрещён.
- Chromium проверяет удаление специально созданной собственной и отказ по чужой заявке, корзину, восстановление и двойное подтверждение purge на отдельной временной БД. Существующие заявки dev не используются.


## Текущий Identity, Permissions & Ticket Editing

- Миграция `0012 → 0013` переносит права существующих пользователей, сохраняет
  их Argon2id хеши, сессии и исторические заявки. Для новых сотрудников пароль
  генерируется один раз, хранится только как Argon2id; первый вход требует
  смены, которая отзывает все прежние сессии.
- Администратор видит Web UI сотрудников, создаёт, редактирует, деактивирует и
  включает их, меняет гранты и сбрасывает пароль. Обычный сотрудник не может
  выполнить эти HTTP операции. Последний активный admin и его последний
  `users.manage` грант защищены, включая прямой SQL и конкурентные операции.
- Изменения грантов видны действующей сессии без нового входа. Отключённый
  сотрудник теряет доступ даже со старой cookie. Origin, Host, CSRF, Secure,
  HttpOnly и no-store остаются обязательными.
- `tickets.edit.own` изменяет только заявку с `created_by` текущего пользователя;
  `tickets.edit.all` разрешает другую незакрытую заявку при отдельном праве
  чтения. Конфликт `If-Match` даёт `409`; чужой ресурс недоступен; изменение
  snapshots или закрытой заявки отклоняется. История содержит старое и новое
  значение, автора и время, в одной транзакции с изменением заявки.
- В Chromium проверяется цепочка admin → временный сотрудник → смена пароля →
  создание и редактирование своей заявки → отказ для чужой → отзыв права →
  отключение. Тестовые данные создаются в `oss_test_*` либо документированно
  удаляются без затрагивания пользовательских заявок dev-базы.

Разделы прежних фаз ниже фиксируют исторические критерии на момент их
принятия; текущие права admin и персональные гранты определяет этот раздел.

## BDCOM ONU read-only preview

- Только инженер OSS видит ONU-карточку в Subscriber 360 и связанной заявке;
  оператор и технический admin не получают `diagnostics.run`.
- Без готового SELECT-only доступа к двум кастомным таблицам LibreNMS API
  возвращает `UNAVAILABLE`, UI не подставляет mock-наблюдения.
- У GPON суррогат `lower(serial)` из `bdcom_onus.mac` не отображается как MAC;
  Serial показывается. EPON MAC показывается только из фактического поля
  collector. ONU без обоих идентификаторов не выдаётся как кандидат.
- VLAN или описание ONU по отдельности не подтверждают связь с абонентом.
  `MATCHED_BY_RULE` требует утверждённого OLT, полной тройки NetUP с
  provenance, преобразования порта по правилу EPON/GPON и ровно одной
  действующей ONU по OLT+PON+VLAN и отсутствие второй сервисной связки
  абонента с тем же ключом. Неутверждённый OLT, ноль или несколько
  ONU и конфликт NetUP не выбираются автоматически. 15 case-only пар
  проверены владельцем и внесены в защищённый dev-реестр.
  Время inventory и оптики раздельно, неизвестная зона источника и возраст
  отдельного оптического значения явно ограничены.
- При Online сохранённая коллектором причина прежнего отключения не выдаётся
  как текущая; при Offline/Deregistered причина показывается. В заявке один
  раздел диагностики подключения показывает ONU первым, а проверка устройства
  остаётся доступной по раскрытию с отдельным подтверждением сохранения.
- Контрактные тесты используют только синтетические строки; реальный MariaDB
  прогон допустим после готовности credentials и проверки схемы.

Утверждённое дополнение Phase 1.4: [приёмка трёх типов заявок](phase-1.4-ticket-types.md). Stage 1 ввела право создания для инженера и схему трёх типов; Stage 2 вводит HTTP создание `MANUAL`/`INTERNAL`. Для linked обе роли выполняют lookup и читают разрешённый Subscriber Snapshot. Инженерные действия остаются недоступны оператору, технический `admin` не видит заявки. Все созданные заявки и их история хранятся бессрочно. Критерии прежних этапов ниже описывают их историческое поведение.

## Критерии промежуточного шага Phase 1.1

- Compose config валиден: PostgreSQL доступен только во внутренней сети и хранит данные в volume; API опубликован лишь на `127.0.0.1` и работает не от root.
- Liveness отвечает `200` без БД. Readiness выполняет ограниченный по времени запрос к PostgreSQL: `200` при доступной БД, `503` при недоступной.
- Пустая базовая миграция применима к чистой PostgreSQL БД и оставляет только служебную таблицу Alembic.
- Unit тесты конфигурации и health, интеграционные тесты соединения и миграции, Ruff запускаются в Docker. Отсутствие доступа к Docker socket фиксируется как ограничение проверки, без обхода прав.
- Не создаются production-данные и подключения к NetUP, Telegram, LibreNMS, Icinga или BDCOM.

## Критерии приёмки Phase 1

1. **Поиск.** Оператор и инженер находят синтетический лицевой счёт через mock BillingProvider. Экран показывает `source=MOCK`, время получения, договор, услуги и доступные подключения. Неизвестный счёт даёт «не найдено», недоступность mock — отдельную ошибку без выдуманных данных.
2. **Типы подключения.** Синтетические сценарии Ethernet, EPON и GPON отображаются по типу. Для Ethernet ONU ID не обязателен. При нескольких подключениях создание заявки требует явного выбора; отсутствующие устройство, порт, VLAN или ONU ID показываются как неизвестные.
3. **Создание заявки.** Оператор добавляет описание и создаёт заявку из сохранённого snapshot без повторного ввода ФИО/телефона. PostgreSQL атомарно сохраняет заявку, историю и аудит. Повтор с тем же `client_request_id` не создаёт вторую заявку.
4. **Работа инженера.** Инженер открывает заявку, начинает работу, добавляет комментарий и ручной диагностический snapshot, записывает решение и закрывает заявку. Закрытие без решения, с чужим `decision_id` или не инженером отклоняется.
5. **Права.** Оператор не может записывать решение, ручную диагностику или закрывать заявку; монтажники не могут войти в приложение. Запрет обеспечивается API, даже если запрос отправлен без интерфейса.
6. **Разделение данных.** Billing snapshot, ручная проверка и будущие автоматические наблюдения различаются по происхождению. Финансовые сведения не превращаются в технический статус; отсутствие наблюдений отображается `UNKNOWN`.
7. **Source of truth.** После перезапуска приложения заявки, комментарии, решения, история, аудит и диагностические snapshots читаются из PostgreSQL. Приложение не создаёт и не закрывает записи в ServiceDesk Plus и не синхронизирует их.
8. **Границы интеграций.** Phase 1 не обращается к реальному NetUP, Telegram, LibreNMS, Icinga или BDCOM. Все данные mock явно синтетические; секреты и полные персональные данные отсутствуют в общих технических логах.
9. **Конкурентность.** Конфликт версии при изменении статуса возвращает `409` без потери истории. Закрытая заявка остаётся доступной для чтения и не принимает новые комментарии или решения в Phase 1.

## Стратегия тестирования при реализации

### Phase 1.2B — Ticket Engine

- Миграция `0002_identity_rbac → 0003_ticket_engine` сохраняет существующих пользователей и добавляет snapshot, ticket, comment, decision, history, audit и manual diagnostic таблицы. Тесты используют только временные базы проекта.
- Оператор создаёт заявку из действующего snapshot, принадлежащего ему. Несколько подключений требуют явного выбора; повтор `client_request_id` с тем же содержимым возвращает исходную заявку, с другим — `409`.
- Инженер назначает активного инженера, начинает работу, фиксирует причину выездных работ отдельным событием, ручную проверку и решение, затем закрывает заявку. Статус проходит `OPEN → IN_PROGRESS → CLOSED`; событие выездных работ статус не меняет.
- Изменения сериализуются строковой блокировкой, версия проверяется для назначения, начала, запроса выездных работ и закрытия. Заявка, история и аудит откатываются вместе при ошибке записи. Закрытые записи остаются только для чтения.
- API проверяет права, CSRF, строгий ввод и пагинацию. `admin` не читает и не меняет заявки. Чтение `GET /tickets` и детальной карточки доступно operator/engineer в единственном контуре Phase 1.
- Phase 1.2B не содержит HTTP поиска абонента; mock BillingProvider и Subscriber 360 добавляются следующим шагом Phase 1 без изменения модели заявки.

### Phase 1.3 — Subscriber 360 и mock BillingProvider

- Контракт mock покрывает Ethernet, EPON, GPON, несколько услуг и подключений, отсутствующие ONU/порт/VLAN, ненайденный счёт, отказ источника, устаревшие и конфликтующие поля. Все значения явно синтетические; нет реальных IP, телефонов, лицевых счетов и сетевых идентификаторов.
- `POST /subscriber-lookups` сохраняет нормализованный snapshot и аудит атомарно; `GET /subscriber-lookups/{id}` возвращает исходный снимок только его автору. `404` и `503` различаются, при отказе источника snapshot не создаётся. Размер тела запроса ограничен 2048 байт, лицевого счёта — 100 символов.
- Карточка содержит `subscriber_id`, лицевой счёт, ФИО/организацию, контакт, адреса, договоры, услуги, подключения, источники, времена и качество полей. Неизвестные и конфликтующие идентификаторы не угадываются, биллинг не меняет `technical_state=UNKNOWN`.
- Оператор создаёт заявку по `lookup_id`; при нескольких услугах/подключениях выбор обязателен. Клиент не может подменить сохранённые PII или сетевые данные. Проверяются срок 15 минут, владелец снимка, идемпотентность `client_request_id` и конкурентное создание.
- Миграция `0003 → 0004` сохраняет существующие заявки и пустые новые поля. Полный mock-поиск → решение инженера → закрытие проходит с PostgreSQL. Роли `operator`/`engineer` могут искать, `admin` не имеет доступа; PII не выводится в общие логи.

### Phase 1.2A — Identity & RBAC

- Миграция `0001_foundation → 0002_identity_rbac` создаёт только таблицы идентификации; основная БД не получает фиктивных пользователей. Первый администратор создаётся интерактивно при пустой таблице.
- Вход с верным паролем выдаёт серверную сессию; неправильный пароль и неактивный пользователь получают `401`. Истёкшая, отозванная или деактивированная сессия не даёт доступа; logout отзывает её в PostgreSQL.
- Роли и permissions соответствуют [матрице](rbac.md). Оператор и инженер не создают пользователей и не меняют роли, включая собственную. Самостоятельной регистрации нет; `admin` не имеет прав на заявки.
- Все изменяющие identity запросы проверяют CSRF, `Origin` и `Host`; production cookies имеют `HttpOnly`, `Secure`, `SameSite=Strict`. HTTP допустим только для явного dev loopback.
- Неудачные попытки входа ограничены по логину и прямому адресу источника в PostgreSQL и остаются ограниченными после перезапуска клиента/API. Поддельный `X-Forwarded-For` не меняет ключ лимита.
- Деактивация/понижение последнего активного администратора запрещены на уровне сервиса и БД, включая конкурентные операции. Изменение роли и деактивация отзывают сессии цели.
- Аудит входов, смены роли, деактивации и отзывов не содержит пароль, токен или полный IP; ошибки API не возвращают хэши. Интеграционные тесты используют только временную БД Compose.

| Уровень | Проверки |
| --- | --- |
| Unit / contract | Один набор контрактных проверок для BillingProvider и mock: найдено, не найдено, недоступно, неполные поля, три типа подключения, несколько связок. Проверка доменных переходов и `UNKNOWN`. |
| API + RBAC | Табличные положительные и отрицательные проверки всех методов для `operator`, `engineer`, `admin` и неаутентифицированного запроса. Отдельно проверить подделанный `decision_id`, устаревший `If-Match`, повтор `client_request_id`. |
| PostgreSQL integration | Миграция с чистой БД; внешние ключи и уникальность; атомарность заявки/истории/аудита; сохранность после перезапуска; append-only решений и событий. |
| End-to-end | Оператор ищет mock абонента и создаёт заявку; инженер фиксирует ручной результат, решение и закрывает; оператор видит итог. Проверить отсутствие повторного ручного заполнения ФИО/телефона. |
| Security / privacy | Сессия и CSRF, серверное RBAC, отсутствие секретов и полного PII в технических логах, отказ доступа монтажнику. |

Для Phase 3 отдельно проверяются дедупликация Telegram обновлений, сопоставление ответа по `chat_id`/`message_id`, независимость состояний доставки/работ/заявки и запрет автозакрытия по «Готово». Для Phase 4 отдельно проверяется происхождение каждого наблюдения и корректное `UNKNOWN`. Эти проверки не требуют подключения реальных систем в Phase 1.

Для NetUP provider 1.0 дополнительно проверить синтетически: канонический
ЛС и отказ для ведущих нулей без подтверждённого правила, отсутствующий и
неоднозначный счёт, удалённые связи, несколько счетов/услуг/строк группы,
конфликт нескольких троек, сохранение `UNKNOWN` для типа доступа и IP-кода,
отказ БД без секретов в журнале. Миграцию `0004 → 0005` проверять на
временной PostgreSQL базе с существующим snapshot. Интеграционные проверки
UTM5 требуют отдельного lab read-only канала и не используют
исследовательский wrapper как runtime API.

### Phase 1.4 — три типа заявки и RBAC

- Stage 1: временная PostgreSQL база проходит `0007 → 0008` с существующей linked заявкой, комментариями, решениями, историей и диагностикой; чистая база достигает head без ORM/schema drift.
- Stage 1: прямые SQL INSERT подтверждают все три типа, CHECK/FK, защиту типа от изменения, прямой FK диагностики на заявку и запрет чужого snapshot/подключения. Оператор и инженер имеют `ticket.create` и `subscriber.read`, `admin` их не имеет; инженер создаёт linked заявку через старый HTTP контракт.
- Stage 2: HTTP создание всех типов обеими ролями, фильтр `ticket_type`, nullable detail, отрицательные проверки смешанных полей, прежний запрос без дискриминатора, отказ создания при отсутствии прав, идемпотентность и общий жизненный цикл проверяются на временных PostgreSQL БД. Создание manual/internal не вызывает BillingProvider.
- Оператор и инженер каждый создают `SUBSCRIBER_LINKED`, `MANUAL` и `INTERNAL`; для linked оба выполняют разрешённый lookup и чтение Subscriber Snapshot. Подмена чужого или просроченного snapshot отклоняется для обеих ролей.
- Для manual/internal NetUP недоступен без влияния на создание. ЛС и snapshot не обязательны и не подставляются фиктивно; смешение полей разных типов отклоняется. Прежний запрос без `ticket_type` с `lookup_id` работает по старому контракту.
- Все три типа проходят общие назначение, `OPEN → IN_PROGRESS → CLOSED`, комментарии, историю и версии решения. Только инженер назначает, диагностирует, фиксирует решение и закрывает. Оператор не получает инженерных прав, `admin` не читает и не меняет заявки или Subscriber 360.
- Повтор `client_request_id`, конфликт payload, конкурентное изменение, откат транзакции, FK диагностики и очистка только lookup без заявки проверяются для всех применимых типов. Заявки и их история сохраняются бессрочно.
- Web UI предлагает свободное создание каждого типа без обязательного шаблона или категории и с короткой формой. Проверки прав выполняются API независимо от интерфейса.

### Backend API completion перед Stage 3B

- `0008 → 0009` и чистая база → head проходят на отдельных `oss_test_*`; исторические заявки, события и ссылки сохраняются, историческая тема остаётся `NULL`.
- У каждого типа заявки необязательная тема видна в create/list/detail; старый linked POST без темы работает. Пустая, слишком длинная или содержащая управляющие символы тема отклоняется; повтор `client_request_id` с другой темой даёт `409`. CSRF и RBAC сохраняются.
- Список исполнителей доступен только роли с `ticket.assign`, содержит лишь активных инженеров и минимальные поля. Фильтр `unassigned` работает с прочими фильтрами и пагинацией; сочетание с `assignee` отклоняется.
- Лента последних событий доступна только с `ticket.read`, ограничена размером и номером страницы, сортируется детерминированно и не выдаёт `event_data`, комментарии или текст жалобы. `admin` и неавторизованный клиент не видят её.
- Полный pytest в PostgreSQL, Ruff, frontend TypeScript typecheck и build проходят без изменения рабочей базы.

### Phase 1.4 Stage 3A — Web UI foundation

- Сборка frontend, TypeScript strict и unit tests проходят из воспроизводимого `npm ci`, в том числе в отдельном Docker-образе. Рабочий API и PostgreSQL не перезапускаются.
- При `GET /auth/me → 401` показывается вход; при отказе API не подставляется фиктивная сессия. Вход и выход используют реальные cookie-контракты, CSRF для logout, `Origin`/`Host` через ограниченный loopback dev proxy. Пароли и session tokens не записываются в браузерные хранилища.
- Страница «Мой доступ» показывает только роль и permissions из `/auth/me`. Технический `admin` не получает навигацию к заявкам. Обзор читает `/health/ready` и не показывает вымышленные показатели заявок.
- Для приватных запросов задан `cache: no-store`; query cache живёт только в памяти и очищается при выходе. Отклонения `401`, `403`, `404`, `409`, `422`, `503` отображаются без текста, способного раскрыть персональные данные.

### Phase 1.4 Stage 3B — ServiceDesk Web UI

- Component tests проверяют фильтрацию реестра, три формы создания, явный выбор нескольких связей, отображение карточки и разрешённые действия, показатели Dashboard из API и отсутствие запросов ServiceDesk у admin.
- Chromium с доверенным лабораторным CA проверяет реальные HTTP-вызовы для `MANUAL`, `INTERNAL`, `SUBSCRIBER_LINKED`; операторский комментарий; инженерные назначение, начало работы, ручную диагностику, решение и закрытие каждого типа; повторное чтение сохранённого статуса. Отрицательные проверки подтверждают CSRF, Origin, RBAC и устаревший `If-Match`.
- Dev PostgreSQL содержит head `0009`; предварительный дамп проверен восстановлением в изолированной базе. Полный backend pytest создаёт и удаляет только `oss_test_*` базы. После перезапуска только dev-стека подтверждаются существующие заявки и авторизация.
- Chromium проверяет структуру стандартной HTML-формы для менеджера паролей. Фактический prompt сохранения и автоподстановка в Chrome/Edge/Firefox на компьютере владельца требуют ручной проверки; пароль не хранится в web storage.

### NetUP Provider 1.1 — дополнительные регрессии

- `APP_ENV=production` отклоняет lab/plaintext; настоящий локальный Uvicorn
  access log не содержит query string с синтетическим ЛС. Авторизованные
  ответы API и ошибки содержат `Cache-Control: no-store`.
- `0005 → 0006 → 0007` на временной PostgreSQL БД сохраняет старый ticket
  snapshot. Контролируемая очистка удаляет лишь lookup без заявки спустя
  24 часа от `fetched_at`, пишет обезличенный аудит и пропускает строку,
  занятую конкурентной транзакцией. Прямой DELETE остаётся запрещён.
- Повторная проверка роли после медленного provider запрещает сохранение
  lookup для деактивированного/перероленного пользователя без удержания
  PostgreSQL row lock во время ожидания NetUP.
- Синтетический NetUP DTO проходит HTTP lookup → immutable PostgreSQL
  snapshot → создание ticket → повторное чтение; контакты, связи service/group
  и все строки IP-групп совпадают. Mock и исторические snapshots читаются.
- Лабораторные read-only UTM5 tests, Ruff, `pip check` и полный pytest с
  изолированными PostgreSQL БД — обязательные gates до Web UI с NetUP.

### Phase 1.4 Stage 3C — Subscriber 360

- Проверенные JOIN для тарифов и отдельные финансовые наблюдения проходят read-only тесты восстановленной UTM5; источник и дата лабораторной копии дают `STALE`. Тип доступа и ONU остаются `UNKNOWN`, конфликтующие IP-группы сохраняют все строки.
- Оператор получает `financial_accounts[]`, инженер получает пустой массив, технический admin не получает карточку. Роли проверяются API; финансовые поля не входят в техническое состояние и не появляются в общих логах.
- История по `subscriber_id` и источнику возвращает ограниченную страницу связанных заявок из разных lookup; чужой lookup даёт `404`, некорректная пагинация — `422`.
- `0009 → 0010 → 0011` и старые snapshots проходят миграцию на временных PostgreSQL БД; новый индекс проверяется после upgrade. Ticket snapshots остаются immutable.
- React component tests и Chromium через HTTPS проверяют поиск по ЛС, provenance, множество контактов/IP-групп, переход в связанную заявку, её создание и жизненный цикл, RBAC, CSRF и Origin. Browser URL не содержит ЛС.

### OSS Diagnostics — первая read-only интеграция

- Синтетические unit tests проверяют однозначное соответствие устройства и порта, конфликт нескольких NetUP `switch_id`/`port_id`, отсутствие mapping, отказ источника, устаревшее измерение и различие Icinga `UNREACHABLE`/`DOWN`. Совпадение NetUP `port_id` с LibreNMS `ifIndex` само по себе не даёт соответствия.
- Opt-in integration test читает только LibreNMS Lab API и проверяет конкретное устройство и его порты без вывода идентификаторов или секрета. Отдельно проверяется доступ из dev API container через `edge` network.
- Временная `oss_test_*` PostgreSQL база проходит миграцию `0011 → 0012`; HTTP тест проверяет engineer-only запуск, CSRF, `If-Match`, повторную проверку прав после внешнего вызова, отдельное подтверждение при `IN_PROGRESS`, историю и аудит в одной транзакции, запрет повторного подтверждения и FK подключения. Оператор и admin не запускают проверку.
- Chromium через dev HTTPS проверяет кнопку в Subscriber 360 и связанной заявке без создания синтетических заявок в рабочей dev базе. При отсутствии утверждённого mapping результат явно `UNKNOWN`, без фиктивного технического статуса.
