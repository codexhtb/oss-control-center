# Acceptance criteria и стратегия тестирования

## Критерии промежуточного шага Phase 1.1

- Compose config валиден: PostgreSQL доступен только во внутренней сети и хранит данные в volume; API опубликован лишь на `127.0.0.1` и работает не от root.
- Liveness отвечает `200` без БД. Readiness выполняет ограниченный по времени запрос к PostgreSQL: `200` при доступной БД, `503` при недоступной.
- Пустая базовая миграция применима к чистой PostgreSQL БД и оставляет только служебную таблицу Alembic.
- Unit тесты конфигурации и health, интеграционные тесты соединения и миграции, Ruff запускаются в Docker. Отсутствие доступа к Docker socket фиксируется как ограничение проверки, без обхода прав.
- Не создаются production-данные и подключения к NetUP, Telegram, LibreNMS, Icinga или BDCOM.

## Критерии приёмки Phase 1

1. **Поиск.** Оператор и инженер находят синтетический лицевой счёт через mock BillingProvider. Экран показывает `source=MOCK`, время получения, договор, услуги и доступные подключения. Неизвестный счёт даёт «не найдено», недоступность mock — отдельную ошибку без выдуманных данных.
2. **Типы подключения.** Синтетические сценарии Ethernet, EPON и GPON отображаются по типу. Для Ethernet ONU ID не обязателен. При нескольких подключениях создание заявки требует явного выбора; отсутствующие устройство, порт, VLAN или ONU ID показываются как неизвестные.
3. **Создание заявки.** Оператор добавляет описание и создаёт заявку из сохранённого snapshot без повторного ввода ФИО/телефона. PostgreSQL атомарно сохраняет заявку, историю и аудит. Повтор с тем же `client_request_id` не создаёт вторую заявку.
4. **Работа инженера.** Инженер открывает заявку, начинает работу, добавляет комментарий и ручной диагностический snapshot, записывает решение и закрывает заявку. Закрытие без решения, с чужим `decision_id` или не инженером отклоняется.
5. **Права.** Оператор не может записывать решение, ручную диагностику или закрывать заявку; монтажники не могут войти в приложение. Запрет обеспечивается API, даже если запрос отправлен без интерфейса.
6. **Разделение данных.** Billing snapshot, ручная проверка и будущие автоматические наблюдения различаются по происхождению. Финансовые сведения не превращаются в технический статус; отсутствие наблюдений отображается `UNKNOWN`.
7. **Source of truth.** После перезапуска приложения заявки, комментарии, решения, история, аудит и диагностические snapshots читаются из PostgreSQL. Приложение не создаёт и не закрывает записи в ServiceDesk Plus и не синхронизирует их.
8. **Границы интеграций.** Phase 1 не обращается к реальному NetUP, Telegram, LibreNMS, Icinga или BDCOM. Все данные mock явно синтетические; секреты и полные персональные данные отсутствуют в общих технических логах.
9. **Конкурентность.** Конфликт версии при изменении статуса возвращает `409` без потери истории. Закрытая заявка остаётся доступной для чтения и не принимает новые комментарии или решения в Phase 1.

## Стратегия тестирования при реализации

### Phase 1.2B — Ticket Engine

- Миграция `0002_identity_rbac → 0003_ticket_engine` сохраняет существующих пользователей и добавляет snapshot, ticket, comment, decision, history, audit и manual diagnostic таблицы. Тесты используют только временные базы проекта.
- Оператор создаёт заявку из действующего snapshot, принадлежащего ему. Несколько подключений требуют явного выбора; повтор `client_request_id` с тем же содержимым возвращает исходную заявку, с другим — `409`.
- Инженер назначает активного инженера, начинает работу, фиксирует причину выездных работ отдельным событием, ручную проверку и решение, затем закрывает заявку. Статус проходит `OPEN → IN_PROGRESS → CLOSED`; событие выездных работ статус не меняет.
- Изменения сериализуются строковой блокировкой, версия проверяется для назначения, начала, запроса выездных работ и закрытия. Заявка, история и аудит откатываются вместе при ошибке записи. Закрытые записи остаются только для чтения.
- API проверяет права, CSRF, строгий ввод и пагинацию. `admin` не читает и не меняет заявки. Чтение `GET /tickets` и детальной карточки доступно operator/engineer в единственном контуре Phase 1.
- Phase 1.2B не содержит HTTP поиска абонента; mock BillingProvider и Subscriber 360 добавляются следующим шагом Phase 1 без изменения модели заявки.

### Phase 1.3 — Subscriber 360 и mock BillingProvider

- Контракт mock покрывает Ethernet, EPON, GPON, несколько услуг и подключений, отсутствующие ONU/порт/VLAN, ненайденный счёт, отказ источника, устаревшие и конфликтующие поля. Все значения явно синтетические; нет реальных IP, телефонов, лицевых счетов и сетевых идентификаторов.
- `POST /subscriber-lookups` сохраняет нормализованный snapshot и аудит атомарно; `GET /subscriber-lookups/{id}` возвращает исходный снимок только его автору. `404` и `503` различаются, при отказе источника snapshot не создаётся. Размер тела запроса ограничен 2048 байт, лицевого счёта — 100 символов.
- Карточка содержит `subscriber_id`, лицевой счёт, ФИО/организацию, контакт, адреса, договоры, услуги, подключения, источники, времена и качество полей. Неизвестные и конфликтующие идентификаторы не угадываются, биллинг не меняет `technical_state=UNKNOWN`.
- Оператор создаёт заявку по `lookup_id`; при нескольких услугах/подключениях выбор обязателен. Клиент не может подменить сохранённые PII или сетевые данные. Проверяются срок 15 минут, владелец снимка, идемпотентность `client_request_id` и конкурентное создание.
- Миграция `0003 → 0004` сохраняет существующие заявки и пустые новые поля. Полный mock-поиск → решение инженера → закрытие проходит с PostgreSQL. Роли `operator`/`engineer` могут искать, `admin` не имеет доступа; PII не выводится в общие логи.

### Phase 1.2A — Identity & RBAC

- Миграция `0001_foundation → 0002_identity_rbac` создаёт только таблицы идентификации; основная БД не получает фиктивных пользователей. Первый администратор создаётся интерактивно при пустой таблице.
- Вход с верным паролем выдаёт серверную сессию; неправильный пароль и неактивный пользователь получают `401`. Истёкшая, отозванная или деактивированная сессия не даёт доступа; logout отзывает её в PostgreSQL.
- Роли и permissions соответствуют [матрице](rbac.md). Оператор и инженер не создают пользователей и не меняют роли, включая собственную. Самостоятельной регистрации нет; `admin` не имеет прав на заявки.
- Все изменяющие identity запросы проверяют CSRF, `Origin` и `Host`; production cookies имеют `HttpOnly`, `Secure`, `SameSite=Strict`. HTTP допустим только для явного dev loopback.
- Неудачные попытки входа ограничены по логину и прямому адресу источника в PostgreSQL и остаются ограниченными после перезапуска клиента/API. Поддельный `X-Forwarded-For` не меняет ключ лимита.
- Деактивация/понижение последнего активного администратора запрещены на уровне сервиса и БД, включая конкурентные операции. Изменение роли и деактивация отзывают сессии цели.
- Аудит входов, смены роли, деактивации и отзывов не содержит пароль, токен или полный IP; ошибки API не возвращают хэши. Интеграционные тесты используют только временную БД Compose.

| Уровень | Проверки |
| --- | --- |
| Unit / contract | Один набор контрактных проверок для BillingProvider и mock: найдено, не найдено, недоступно, неполные поля, три типа подключения, несколько связок. Проверка доменных переходов и `UNKNOWN`. |
| API + RBAC | Табличные положительные и отрицательные проверки всех методов для `operator`, `engineer`, `admin` и неаутентифицированного запроса. Отдельно проверить подделанный `decision_id`, устаревший `If-Match`, повтор `client_request_id`. |
| PostgreSQL integration | Миграция с чистой БД; внешние ключи и уникальность; атомарность заявки/истории/аудита; сохранность после перезапуска; append-only решений и событий. |
| End-to-end | Оператор ищет mock абонента и создаёт заявку; инженер фиксирует ручной результат, решение и закрывает; оператор видит итог. Проверить отсутствие повторного ручного заполнения ФИО/телефона. |
| Security / privacy | Сессия и CSRF, серверное RBAC, отсутствие секретов и полного PII в технических логах, отказ доступа монтажнику. |

Для Phase 3 отдельно проверяются дедупликация Telegram обновлений, сопоставление ответа по `chat_id`/`message_id`, независимость состояний доставки/работ/заявки и запрет автозакрытия по «Готово». Для Phase 4 отдельно проверяется происхождение каждого наблюдения и корректное `UNKNOWN`. Эти проверки не требуют подключения реальных систем в Phase 1.

Для NetUP provider 1.0 дополнительно проверить синтетически: канонический
ЛС и отказ для ведущих нулей без подтверждённого правила, отсутствующий и
неоднозначный счёт, удалённые связи, несколько счетов/услуг/строк группы,
конфликт нескольких троек, сохранение `UNKNOWN` для типа доступа и IP-кода,
отказ БД без секретов в журнале. Миграцию `0004 → 0005` проверять на
временной PostgreSQL базе с существующим snapshot. Интеграционные проверки
UTM5 требуют отдельного lab read-only канала и не используют
исследовательский wrapper как runtime API.
