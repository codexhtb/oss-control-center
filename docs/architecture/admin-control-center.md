## Service Desk: путь сотрудника и пробелы

Оценка основана на коде и утверждённом workflow. Экономия времени и частота использования без телеметрии остаются гипотезами.

| Действие | Подтверждённое текущее поведение / лишний шаг | Улучшение и ограничение |
| --- | --- | --- |
| Создать во время звонка | Отдельный экран; ручное и связанное обращение, тема из справочника либо свободная | Сохранить свободную тему; проверить частые пути с операторами до изменения формы |
| Найти заявку | Поиск и фильтры в URL; новая навигация начиналась с общего списка | Личная очередь по умолчанию для пустого `/tickets`; прямые ссылки с фильтрами сильнее предпочтения |
| Увидеть повторное обращение | Перед созданием связанной заявки показываются активные обращения; нужна причина отдельной заявки | Существующую проверку не обходить; для ручных заявок полнота совпадений не подтверждена |
| Взять в работу | Есть отдельная очередь и атомарное claim | Сохранять серверную защиту от конкурентного захвата |
| Передать инженеру | Назначение и переназначение разрешены по RBAC; занятая заявка требует admin | Правило автоматической раздачи без метрик и согласования не вводить |
| Сохранить решение | Структурированная причина + текст; редактор и новая версия в заявке | Шаблоны текста возможны после хранилища и прав; шаблон только вставляет редактируемый текст |
| Передать на выезд | Работа во вкладке заявки, Telegram handoff отделён от статуса заявки | Нужна UX-проверка на реальных сценариях; не менять доставку |
| Выполнить обзвон | Серверная очередь callback с кратким решением; NO_ANSWER остаётся RESOLVED | Личное открытие этой очереди сокращает навигацию |
| Вернуть неисправную | STILL_BROKEN возвращает в IN_PROGRESS без исполнителя | Сохранять историю решений и обзвонов |
| Закрыть | CONFIRMED закрывает связанную заявку; у иных типов отдельное закрытие с причиной | Не вводить обход контрольного звонка |
| Найти зависшие | Есть статус, даты, очереди и фильтры; отдельной настраиваемой SLA-очереди нет | Порог и правила эскалации требуют отдельной продуктовой постановки |

## Проект серверных настроек после отдельного разрешения на миграцию

Не нужен универсальный JSON-движок. Каждая предметная группа получает типизированную таблицу, Pydantic-схему и узкий API. Первая кандидатная сущность — `decision_reason_catalog(id, code, name, sort_order, is_active, version, created_at, updated_at)`. `code` неизменяем; удаление заменено отключением. Старое решение сохраняет исходный `reason` и отображаемое на тот момент название; новые решения принимают только активный ID. Для обратной совместимости существующие enum-значения мигрируются в каталог с сохранением кодов; старый API поддерживается до согласованной версии контракта. План миграции: добавить каталог и связь без удаления старых колонок, заполнить из существующего enum, перевести чтение/запись, сверить исторические решения, лишь затем обсуждать удаление старой схемы. Миграция не создана и не применена.

Для шаблонов — отдельные `text_templates` с фиксированным назначением (`decision`, `comment`, `callback`), plain text, максимальной длиной, автором, версией и флагом активности. Только выбор и вставка в редактируемое поле; никакого исполнения кода, SQL, сетевых запросов или автоматического статуса. Нужны отдельные разрешения `settings.read` и `settings.manage`, миграция реестра прав, серверная проверка активного пользователя, CSRF/Origin, `If-Match` и ответ `409` с повторной загрузкой при конфликте. Критические workflow-правила, если когда-либо вводить, требуют отдельного проектного решения, ограничений и подтверждения владельца.

Для каждой мутации: транзакция с блокировкой строки, проверка версии, запись старого и нового типизированного значения, автора и времени в audit, изменение версии и commit вместе. Откат — новая проверенная версия через тот же API и аудит; не прямое изменение БД и не стирание истории. Чувствительные значения не попадают в журнал. Для небольшого каталога сервер читает актуальные значения из PG без перезапуска контейнера, с `Cache-Control: no-store` или инвалидируемым кэшем. UI различает `403`, `409`, `428` и ошибки валидации.

Секреты NetUP, PostgreSQL, Telegram, TLS/Caddy, ACL, Docker/Compose, SQL-запросы, команды BDCOM и выключатели проверок безопасности остаются инфраструктурным процессом владельца согласно `docs/operations/secret-management.md`.

## Первый этап и следующие шаги

Реализован маршрут `/settings`: существующие темы, сотрудники/permissions и аудит открываются по прямым ссылкам в `/users`; новая реализация CRUD отсутствует. Личная очередь по умолчанию применима лишь к пустому `/tickets` и лишь при `tickets.read.all`; явные URL-фильтры и серверный RBAC сильнее. Изменение хранится в браузере, переживает обновление страницы, не синхронизируется между устройствами. Исторические заявки, причины и workflow не меняются.

Далее: подтвердить с сотрудниками потребность в шаблонах и персональных представлениях; согласовать версионированные миграции и отдельные права; реализовать каталог причин и шаблоны целевыми API; после этого оценить SLA-представления по фактической работе. Приоритеты и правила переходов остаются отдельными решениями.

## Phase 2: подготовленная реализация

`0036_service_desk_settings` добавляет типизированные `decision_reason_catalog` и `ticket_text_templates`, снимок `ticket_decisions.reason_name` для новых версий и право `settings.manage` в ограничение реестра прав. Девять существующих кодов причин сохраняются и заполняют каталог; код нельзя менять или удалить. Отдельная запись шаблона содержит назначение `decision`, `comment` или `callback`, текст до 10 000 символов, активность, порядок и версию. Текст является буквальным plain text: выбор вставляет его в редактируемое поле и сам не вызывает API изменения заявки.

Администратор с персональным `settings.manage` редактирует причины и шаблоны на `/settings`. Право не выдаётся существующим сотрудникам автоматически. Чтение активных причин требует `tickets.resolve`; чтение активных шаблонов требует соответствующее `tickets.resolve`, `tickets.comment` или `tickets.callback`. Мутации проверяют активную сессию, CSRF, Origin, роль администратора, `settings.manage` и версию `If-Match`; сохраняют старое и новое значение в аудите в той же транзакции. Отключённые записи остаются для истории. Темы заявок, сотрудники/права и журнал аудита используют уже существующие экраны `/users`.

Существующие `ticket_decisions` защищены триггером неизменности, поэтому миграция не обновляет их. API возвращает исходное название старой причины из фиксированного словаря кодов, а новые версии хранят название на момент решения в `reason_name`. Переименование каталога не переписывает исторический ответ. `ResolutionReason` и старые значения API сохраняются. Статусы, callback и правила закрытия не меняются.

Рабочий `oss-control-dev` нельзя обновлять кодом Phase 2 до отдельного разрешения на миграцию `0036` и проверенной внешней резервной копии с восстановлением. До этого новый UI/API остаются только в рабочем дереве.
