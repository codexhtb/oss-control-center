# Предложение: исключение из контрольного обзвона для связанной заявки

Статус: **проект, не реализован**. Действующее правило для `SUBSCRIBER_LINKED` остаётся прежним: после `RESOLVED` заявка закрывается только результатом обзвона `CONFIRMED`.

## Правило

Добавить отдельное персональное разрешение `tickets.close_without_callback`. Оно не должно выдаваться вместе с обычным `tickets.close` по умолчанию. Действие доступно только для `SUBSCRIBER_LINKED` в статусе `RESOLVED`, при наличии актуального `resolved_decision_id` и обоих разрешений. Обычный обзвон остаётся основным маршрутом.

Сотрудник выбирает одно из утверждённых оснований (например, подтверждение во время текущего разговора или исключение по регламенту) и вводит обязательный содержательный комментарий. Пустой текст и произвольный код основания отклоняются. Нельзя закрыть заявку, если версия заявки или решения изменилась после открытия формы.

## Контракт и хранение

Предпочтительно отдельное `POST /api/v1/tickets/{id}/close-without-callback` с `If-Match` и идемпотентным ключом запроса. Payload: `reason_code`, `comment`, `resolved_decision_id`. Сервис проверяет сессию, CSRF, RBAC, тип, статус и текущую версию решения в одной транзакции с закрытием. В PostgreSQL сохраняются способ закрытия, основание, комментарий, автор, время и связь с решением; событие и аудит фиксируются в той же транзакции. Не создаётся запись `TicketCallback` и не подставляется `CONFIRMED`. Повтор того же запроса возвращает сохранённый результат; конфликтующий повтор отклоняется. История и API карточки явно различают закрытие после обзвона и исключение.

Для явного хранения способа закрытия и причины нужна версионированная миграция PostgreSQL с обратной совместимостью исторических `CLOSED`. До её применения требуются backup DEV и проверка восстановления. Потребуются изменения API contract, RBAC matrix, workflow и acceptance criteria вместе с целевыми тестами. Все существующие переходы `CONFIRMED → CLOSED`, `STILL_BROKEN → IN_PROGRESS`, `NO_ANSWER → RESOLVED` сохраняются.

**Нужное решение владельца процесса:** утвердить основания исключения, круг сотрудников для отдельного разрешения и формат обязательного подтверждения. До этого исключение не включать и миграцию не применять.
