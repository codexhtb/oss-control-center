# Итоги архитектурного ревью Phase 0

## Утверждённые решения

1. OSS Control Center — самостоятельная система заявок. PostgreSQL — единственный source of truth для обращений, комментариев, решений, истории, аудита и диагностических snapshots.
2. ServiceDesk Plus остаётся только в AS-IS и временно при миграции. В TO-BE нет создания, закрытия или синхронизации заявок с ним.
3. Phase 1 разрабатывается на mock BillingProvider; отсутствие production API NetUP не блокирует mock-based MVP. Production NetUP доступен только для чтения с Phase 2.
4. Монтажный сектор общается через Telegram без кабинета OSS Control Center. Ответ монтажника не закрывает заявку; решение и закрытие выполняет инженер OSS.
5. Статус заявки, состояние Telegram-доставки и состояние выездных работ независимы.
6. Порядок фаз утверждён в [roadmap](roadmap.md): Service Desk, NetUP, Field Dispatch, Network Diagnostics, массовые аварии/аналитика.
7. В продукте две роли: оператор call-центра и сетевой инженер OSS; оба инженера имеют одинаковую роль. Новые подразделения и маршруты эскалации не вводятся.

## Готовность Phase 1

Для **разработки mock-based MVP блокирующих вопросов нет**. [API contracts](api-contracts.md), [data model](data-model.md), [RBAC](rbac.md), [план](phase-1-plan.md) и [критерии приёмки](acceptance-and-testing.md) задают достаточно конкретные границы. Локальные предварительно созданные учётные записи — реализационный базовый вариант Phase 1; выбор конкретного фреймворка и библиотек выполняется при начале реализации.

Перед **production запуском Phase 1** нужно утвердить только эксплуатационные параметры, которые нельзя выбирать из доменной модели: ответственного и порядок выдачи/отключения учётных записей; сроки хранения персональных данных и несвязанных lookup snapshots; порядок ручного cutover со старого ServiceDesk Plus для открытых заявок. Это не повод откладывать код mock-based MVP и не требует синхронизации с ServiceDesk Plus.

## Вопросы следующих фаз

- **Phase 2:** согласованный read-only интерфейс NetUP, реальные поля, кратность и сопоставление услуг/подключений.
- **Phase 3:** источник адреса, минимальный шаблон сообщения, разрешённый Telegram чат и отправители, альтернативный ручной канал, выбор webhook/`getUpdates`, сверка неопределённой отправки, вложения и срок хранения сообщений.
- **Phase 4:** доступные параметры LibreNMS, Icinga и BDCOM collectors, свежесть и подтверждённые правила сопоставления с подключением.
- **Phase 5:** правила массовых аварий, корреляции и аналитики.

Эти вопросы не блокируют Phase 1. Реальные NetUP, Telegram и мониторинг не подключаются в mock-based MVP.
