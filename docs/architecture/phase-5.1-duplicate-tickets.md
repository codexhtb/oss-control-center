# Phase 5.1 — проверка повторных обращений

При создании `SUBSCRIBER_LINKED` сервер проверяет активные заявки по точному
ключу `(subscriber_snapshots.source, subscriber_snapshots.subscriber_id)`. Если
источник не предоставил `subscriber_id`, применяется точный ключ
`(source, account_no)` только среди snapshots без `subscriber_id`. ФИО,
телефон, тема, описание, VLAN и сетевые адреса в сопоставлении не участвуют.
`MANUAL` и `INTERNAL` не связываются с абонентом эвристически.

Активные статусы действующего workflow — `OPEN` и `IN_PROGRESS`.
`CLOSED` и soft-deleted заявки не блокируют создание и не входят в предупреждение.
Это проверка повторного обращения, а не автоматическое объединение заявок.

При выборе абонента форма сразу запрашивает страницу активных заявок. Сотрудник
видит только заявки в пределах `tickets.read.all` либо собственные с
`tickets.read.own`. Если существуют другие активные заявки, API возвращает
лишь `has_hidden_active=true`: ни номер, ни текст, ни исполнитель недоступной
заявки не выдаются. Повторный звонок в этом случае можно передать инженеру
OSS для проверки в пределах его собственных прав; доступ оператору не
расширяется.

`POST /tickets` повторяет проверку внутри транзакции. Транзакционный advisory
lock сериализует создание по точному ЛС и по известному `subscriber_id` (в том
числе при нескольких ЛС одного абонента). При активной заявке запрос без
`duplicate_reason` получает `409 active_ticket_exists`. Создание другой
проблемы требует явного выбора и непустой причины до 500 символов. Причина
записывается в `ticket_history` события `ticket_created` в той же транзакции,
поэтому отдельная миграция не требуется. Существующий `client_request_id`
сохраняет идемпотентность: повтор того же запроса возвращает ту же заявку.
Причина доступна только через защищённую историю заявки, в общие access logs
она не передаётся. Бэкенд не доверяет предварительной проверке браузера:
если после неё появилась заявка, создание отклоняется и форма обновляет список.

Проверка относится к состоянию исторической NetUP Lab на момент lookup;
совпадение ключа не доказывает текущую актуальность биллинга. При
недоступности BillingProvider связанная заявка не создаётся, а `MANUAL` и
`INTERNAL` остаются независимыми сценариями.
