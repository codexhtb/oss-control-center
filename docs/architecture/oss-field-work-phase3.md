# OSS Field Work — этап 3: публикация и запуск через Telegram

## Разделение состояний

Миграция `0048_field_work_publication` добавляет `PUBLISHED`, `published_at` и
`published_by` к существующей передаче. `PUBLISHED` означает доступность в общей
очереди Mini App и **не** подтверждает доставку сообщения в группу: `sent_at` и
`telegram_message_id` остаются пустыми. `SENT` по-прежнему означает подтверждённую
доставку Telegram Bot API с `message_id`. Старые передачи не изменяются.

Инженер сначала фиксирует причину прежним `POST /tickets/{id}/field-work-request`.
Черновик можно либо отправить боту прежним способом (основное действие до
регистрации монтажников), либо опубликовать в Mini App. Одновременно выполнить
оба действия для одного handoff нельзя. Повторная публикация с тем же направлением
идемпотентна; конфликт направления и публикация после начала Telegram-доставки
отклоняются. Новый выезд по той же заявке остаётся отдельным handoff.

## API и workflow

`POST /api/v1/tickets/{ticket_id}/field-work-handoffs/{handoff_id}/publish` принимает
`{direction: SUKHUM|OCHAMCHIRA, visit_address?: string|null}`. Действуют
`tickets.field_work`, OSS-сессия, CSRF/Origin, проверка доступа к заявке,
блокировка handoff и проверка статуса заявки `IN_PROGRESS`. Сервер проверяет
необходимые данные из заявки/snapshot, записывает автора, время, событие и аудит
в одной транзакции. Bot API не вызывается. Клиент не передаёт chat ID.

Mini App читает `SENT` и `PUBLISHED`. Открытые сортируются по времени отправки
или публикации от старых к новым. Отчёт и перенос допускаются в обоих состояниях;
для `PUBLISHED` синхронизация Telegram-карточки не требуется. Для `SENT` работают
прежние callback, ForceReply и обновление карточки. Общий переход отчёта
`AWAITING_REPORT → REPORTED → VERIFIED` не меняет статус Service Desk заявки.

## Точка запуска и внедрение

Адрес приложения: `https://sd.oss-ab.net/field-work`. Меню существующего OSS
Service Bot в личном чате можно назначить через Bot API `setChatMenuButton` с
`MenuButtonWebApp` и этим HTTPS URL либо через @BotFather `/setmenubutton`.
Размещение кнопки в группах не требуется. Монтажник открывает личный чат с ботом,
нажимает «Выездные работы» и получает подписанный Telegram `initData`; сервер
допускает только активный Telegram ID из реестра и разрешённое направление.

Для внедрения: восстановить backup на отдельной PostgreSQL; проверить миграции
`0046–0048`; обновить рабочую схему без пересоздания volume; согласованно обновить
API/WEB и существующий poller; проверить HTTPS/здоровье; зарегистрировать реальные
Telegram ID монтажников через OSS API под `users.manage`; открыть приложение в
Telegram на Android и iOS. До регистрации сотрудников новые задания продолжают
отправлять через прежнюю кнопку «Отправить боту».

## Примечание и сохранённое ФИО (0052)

`FieldWorkRequest.note` хранится в `field_work_handoffs.note` отдельно от причины. После миграции `0055` причина и примечание принимают до 10 000 символов; поддерживаются многострочный текст, CR/LF, табуляция, кириллица, технические символы и emoji. Пустая причина и прочие управляющие символы отклоняются. Старый `PATCH /tickets/{ticket_id}/field-work-handoffs/{id}/note` с `expected_note` сохранён для подготовки DRAFT/FAILED; после публикации используется редактирование задания ниже.

Очередь и подробности Mini App возвращают `name`: для SUBSCRIBER_LINKED — из сохранённого SubscriberSnapshot, для ручных и NEW_CONNECTION — `caller_full_name`. Нет дополнительных запросов к NetUP; отсутствующее имя отображается как «Не указано». Проверка: оба направления, сохранение/конфликт примечания, доступ монтажника и сохранность Telegram preview.

Миграция 0052 добавляет только nullable note с проверкой длины. Перед внедрением — защищённый backup и проверенный restore/upgrade; обновляются только API/WEB. При откате вернуть прежние API/WEB, оставив nullable-колонку и историю на месте.

## Редактирование и дополнения (0055)

`PATCH /api/v1/tickets/{ticket_id}/field-work-handoffs/{id}/details` принимает
`{reason, note, visit_address, additional_information?, expected_version, client_request_id}`.
Все три основных поля передаются вместе; `note` и адрес могут быть `null`.
Дополнение — отдельная запись до 10 000 символов, адрес — до 500. Действуют
`tickets.field_work`, видимость заявки и Origin/CSRF. Редактировать можно
только `AWAITING_REPORT` в DRAFT/FAILED/PUBLISHED/SENT. REPORTED/VERIFIED и
неопределённая/начатая доставка запрещают изменение (`409`).

Блокировка handoff и `details_version` защищают от конкуренции с другой правкой,
отчётом и Telegram callback. Повтор идентичного `client_request_id` возвращает
существующий результат; изменение payload с тем же ключом отклоняется. API
не меняет направление, доставку, отчёт, расписание и статус/версию основной заявки.
В `ticket_history` сохраняется `field_work_details_updated`: автор, время,
before/after и дополнение. Технический аудит хранит только факт операции.
`GET .../changes?page=N` выдаёт историю по 20 записей с той же защитой доступа.

Mini App возвращает актуальные причину, адрес и примечание из PostgreSQL,
последние 20 изменений и постраничную историю `/miniapp/handoffs/{id}/changes`
(также `/miniapp/staff/handoffs/{id}/changes`). Список и открытая карточка
обновляются каждые 15 секунд и при возврате фокуса; введённый отчёт сохраняется
в форме. Новые персональные уведомления об изменении используют существующий
outbox `RESCHEDULED` и настройку «Изменения задания и переносы». В личное сообщение
не входят причина, адрес или примечание, только HTTPS-ссылка на защищённое задание.

Публикация Mini App не зависит от лимита Telegram и не вызывает Bot API.
Для Telegram текст длиннее 4096 единиц UTF-16 заменяется краткой карточкой
со ссылкой из `FIELD_WORK_MINIAPP_URL`; переменная нужна API и poller.
Редактируемый перед отправкой Telegram-текст по-прежнему отправляется дословно.
Ранее отправленная карточка и `message_text` не переписываются при правке
задания; уведомление направляет монтажника к актуальной версии в Mini App.

INTERNAL не требует данных абонента. Публикация или отправка сотрудником с
доступом к внутренней заявке устанавливает `internal_dispatch_approved`.
Только такой handoff открывается монтажникам разрешённого направления; сама
внутренняя заявка и административные API не открываются. Исторические INTERNAL
без явного подтверждения сохраняют прежнюю недоступность. Оператор OCC
по-прежнему не получает INTERNAL через ticket API.

Миграция `0055_field_work_details` следует за `0054_subscriber_password`, расширяет
текстовые ограничения и добавляет версию деталей и флаг явной публикации INTERNAL.
Backfill старых заявок отсутствует. Проверка внедрения: backup с restore на отдельной
PostgreSQL, upgrade только нужной revision и сравнение старых данных/количеств;
обновить API/WEB с полным набором действующих Compose overlays. Poller не требует
обновления: тип outbox и формат сохранённой Telegram-карточки совместимы.
Для отката вернуть прежние образы, сохранив новую схему и историю. Автоматический
downgrade запрещён; миграция откажется сужать поля при наличии длинных текстов
или утверждённых внутренних выездов.
Старый API не поддерживает preview длинных заданий; откат образа сохраняет
данные, но такие задания потребуют совместимого API. Их нельзя обрезать или
удалять ради возврата к старой версии.
