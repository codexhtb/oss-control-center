# Notification Center

Центр уведомлений портала объединяет поручения и отчёты монтажников в одну
хронологическую ленту. Источник истины — существующие таблицы PostgreSQL;
новых сервисов, очередей и миграций нет.

## Аудит и решения

- Раньше колокольчик загружал две независимые страницы, включавшие прочитанные
  записи. Их отдельные счётчики и повторные запросы давали несогласованный UI.
- Теперь `/notifications/center` возвращает общую страницу и общий счётчик из
  одного SQL snapshot, с устойчивой сортировкой `created_at DESC, source, id DESC`.
  Фильтрация выполняется до пагинации. Счётчик охватывает все страницы.
- Подтверждённая первопричина ложной ошибки чтения: FastAPI сохраняет заголовок
  `application/json` у пустого ответа 204. Общий API-клиент вызывал `json()` до
  проверки статуса, получал SyntaxError и показывал «Не удалось связаться с
  сервером», хотя PostgreSQL уже сохранил прочтение. Теперь 204 обрабатывается
  до JSON-декодирования; отдельный тест проверяет настоящий Fetch Response.
- Старое открытие поручения продолжало переход даже после ошибки сохранения
  прочтения. Теперь при ошибке запись и счётчик сохраняются, показывается ошибка,
  переход выполняется только после успешного POST.
- Завершение с ответом — один `COMPLETED` с `body`, одна notification другому
  участнику. `MESSAGE` создаётся только отдельной кнопкой «Ответить».
  Повтор запроса с тем же `client_request_id` не создаёт второе событие.
  После потери ответа UI сохраняет request ID для повтора того же текста и
  действия: повторная отправка не создаёт ещё одно сообщение/уведомление.
  После успешного ответа следующее самостоятельное сообщение получает новый ID.
- Исторические `MESSAGE` с тем же task, actor и точным body, предшествующие
  `COMPLETED`, скрываются как повтор ответа. Разные сообщения сохраняются.
  Это единая политика для центра, старого task inbox и `is_unread` поручения.
  События, аудит и исходные notifications физически не удаляются.
- Исторические self-notifications скрываются. Будущие напоминания не входят
  в список, счётчик и массовое прочтение. Напоминания завершённых поручений
  больше не требуют внимания; исходное расписание и события сохраняются.

## Доступ и прочтение

Поручение видят только его получатели с актуальным `tasks.create` или
`tasks.execute` и правом чтения заявки. Удалённые заявки скрыты; оператор не
видит INTERNAL. Администратор не получает чужие поручения только из-за роли.
Отчёты доступны engineer/admin с `tickets.field_work` и чтением заявки
(`tickets.read.own` ограничивает выборку создателем). Собственный отчёт
определяется по staff user ID или связанной Telegram identity и скрывается.
Telegram-доставка, подтверждение отчёта и статус заявки независимы от прочтения.

`state=unread` — основной список, `state=read` — история прочитанных. История
использует те же правила доступа. Read receipts существующего field inbox и
`internal_task_notifications.read_at` общие со старым API и карточкой поручения.
Повторное прочтение идемпотентно и не переписывает исходный timestamp.
«Прочитать все» фиксирует доступный набор обеих лент в одной транзакции, включая
другие страницы; будущие напоминания и поступившие позже события остаются новыми.

UI использует один polling каждые 15 секунд для непрочитанных; историю запрашивает
только при открытой вкладке. Возврат фокуса запускает обновление. На успешном
прочтении отменяются запросы, начатые до завершения POST, запись удаляется из
кеша непрочитанных, счётчик уменьшается, затем данные сверяются с сервером.
AbortSignal передаётся до fetch. Локального хранилища read/unread нет:
перезагрузка, другой браузер и повторный вход читают сохранённые данные PostgreSQL.
Чтение в открытом диалоге поручения также инвалидирует запрос центра.

Переход открывает `/tickets/{ticket_id}?task={task_id}` для поручений и
`/tickets/{ticket_id}` для отчётов. В UI нет отдельных секций источников,
всплывающих toast и повторяющих счётчик подписей. Вкладки, компактная строка,
дата, номер заявки, пагинация, error/loading/empty states остаются в дизайн-коде.
