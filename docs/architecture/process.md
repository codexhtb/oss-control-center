# Процесс интернет-провайдера OSS

## AS-IS — подтверждённый текущий процесс

1. Абонент звонит в call-центр с жалобой на интернет.
2. Оператор call-центра открывает NetUP UTM5 и находит абонента.
3. Оператор вручную создаёт обращение в ServiceDesk Plus, указывая ФИО, лицевой счёт, номер телефона и описание проблемы.
4. Два сетевых инженера OSS получают обращение.
5. Инженер повторно открывает NetUP UTM5, находит абонента по лицевому счёту и изучает сервисную связку.
6. Из сервисной связки инженер получает коммутатор или OLT, порт, VLAN и доступные параметры подключения.
7. Инженер вручную подключается к Ethernet-коммутатору либо BDCOM EPON/GPON OLT и выполняет диагностику.
8. Инженер записывает результат и решение в ServiceDesk Plus.
9. При необходимости заявка передаётся в монтажный сектор.

## TO-BE — утверждённый целевой процесс

1. Оператор ищет абонента непосредственно по лицевому счёту в OSS Control Center.
2. ФИО, телефон, договор, услуги и подключения получаются через BillingProvider: в Phase 1 из mock, с Phase 2 из согласованного read-only интерфейса NetUP.
3. Оператор вводит описание проблемы и создаёт заявку без повторного ручного заполнения данных абонента.
4. Инженер получает карточку подключения с доступными сведениями о коммутаторе или OLT, порте, VLAN и идентификаторах ONU, если они существуют и доступны.
5. С Phase 4 система собирает доступные диагностические данные из LibreNMS, Icinga и специализированных коллекторов. При отсутствии автоматических данных явно показывает UNKNOWN.
6. Инженер при необходимости вручную проверяет оборудование и сохраняет результат диагностики в заявке; окончательное решение фиксирует после необходимых работ.
7. При необходимости заявка передаётся в монтажный сектор через проверенное инженером сообщение Telegram; ответ монтажника попадает в историю заявки для проверки инженером.
8. Поддержка массовых аварий и корреляции обращений вводится в Phase 5.

## Уточнение: выездные работы через Telegram

**AS-IS.** После диагностики инженер OSS при необходимости вручную отправляет монтажникам в Telegram ID заявки, ФИО, контакт, адрес и описание. Монтажник отвечает там о выполненной работе. Инженер получает ответ, записывает выполненные действия в решение ServiceDesk Plus и закрывает заявку.

**TO-BE, Phase 3.** Монтажникам не нужен кабинет OSS Control Center. Инженер выбирает «Передать в монтажный сектор», проверяет сформированное из данных заявки сообщение и отправляет его через Telegram Bot API. Система сохраняет связь `ticket_id` с `chat_id` и `message_id`; ответ на исходное сообщение импортирует как внешнее сообщение в историю заявки и уведомляет инженера. Инженер проверяет результат, фиксирует решение в OSS Control Center и закрывает заявку. Сообщение «Готово» и любой другой ответ не закрывают заявку автоматически. При недоступности Telegram предусмотрен ручной fallback с фиксацией факта передачи и ответа; конкретный альтернативный канал согласуется перед Phase 3.

## Участники и границы

- Абонент сообщает о проблеме.
- Оператор call-центра ищет абонента и создаёт заявку.
- Два сетевых инженера OSS получают обращения и проводят диагностику. Описание не задаёт различий между их полномочиями.
- Монтажный сектор получает сообщение в Telegram при необходимости выездных работ и отвечает там; кабинет OSS Control Center ему не требуется.
- NetUP UTM5 — источник данных об абоненте, договоре, услугах и сервисной связке.
- ServiceDesk Plus используется для обращений и закрытия заявки в AS-IS и временно при миграции. В TO-BE обращения, комментарии, решения, история и закрытие принадлежат OSS Control Center с PostgreSQL как source of truth; синхронизация с ServiceDesk Plus не разрабатывается.
- LibreNMS, Icinga и специализированные коллекторы — потенциальные источники доступных автоматических диагностических данных; конкретное покрытие не подтверждено.

Возможные типы подключения: Ethernet, EPON, GPON. Наличие ONU нельзя предполагать для каждого абонента. Финансовое состояние абонента не является техническим состоянием подключения.
